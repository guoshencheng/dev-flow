# 设计走查与测试验收职责回溯

日期：2026-10-08。依据用户报告，读取当前 Skill/配置与相关会话进行回溯。范围为阶段/对象路由的文档及职责配置修正；没有修改业务项目、向其他会话发消息、派发子 Agent 或执行新的应用验收。

## 观察与根因

在会话“Web 运动短视频产品与 OpenCut 方案讨论”（ID `01a11b89-307f-7823-bda0-ae8716d16584`）看到：

- 用户当前任务是“整体的产品设计和 UI 交互设计”；随后 Agent 明确表示“接下来按 dev-acceptance 做原型走查”。这一记录证明设计阶段原型走查实际采用了测试 Skill；不据此声称原生测试角色已派发。
- 用户问“让测试对文档做走查？”后，Agent 将提问理解为执行要求并发起 `design_document_review`；用户进一步说明是在质疑职责，Agent 随后停止该走查。这是另一个提问意图判断错误，不能全部归因 Skill 路由。

原描述存在具体歧义：

| 原入口 | 问题 |
| --- | --- |
| 测试 Skill 的“测试设计、接口/UI 验证”与“前端与界面” | 没有限定设计原型、实现候选及各阶段责任，容易按 UI/验证关键词选择测试 |
| 总纲“研发实现，测试实际操作” | 没有设计/实现阶段限定，容易把设计原型的实际操作也交给测试 |
| 测试读取交互原型，并将原型/Mock 证据分别记录 | 只约束证据真实性，未说明谁主责设计走查，不能阻止角色误路由 |

产品 Skill 已有 P06 原型操作与可用性走查，但各入口没有把该主责同测试的宽描述明确对齐。模型该次路由与对问句的误解共同促成偏差；描述漏洞是可修正的诱因，不能从单次会话推断唯一原因。

## 修正与语义复核

实施前由主 Agent AI 自查本次小范围修正：保持测试早期参与及实际实现/UI/API/E2E 验收能力，澄清阶段与对象，沿用用户显式指定范围；不增加人工审批或用测试角色替代设计责任。随后同步总纲/流程、产品/视觉入口、测试触发描述与原生配置、策略/界面参考及状态说明。

| 请求/对象 | 修正后的默认主责与限制 |
| --- | --- |
| 完成产品/UI 设计及原型实际走查 | 产品负责流程/规则/交互，视觉负责呈现 |
| 检查原型失败后输入保留、取消与恢复是否合适 | 产品原型走查，必要呈现由视觉复核 |
| 判断产品/UI 设计文档的方案是否合理 | 对应设计职责，不默认启动正式测试验收 |
| 从产品/UI/ARC 形成用例、检查可测性/覆盖 | 测试可读取设计资料并反馈具体缺口 |
| 验证可运行 UI 实现，部分 API 采用 Mock 隔离 | 测试可执行实现的界面验证，说明 Mock 边界 |
| 用户明确指定测试检查原型 | 测试限定到指定对象/预期，单列原型证据，不升级实现/交付验收 |

以上为主 Agent 的语义复核矩阵，不是独立模型行为评测。工具不决定职责；设计原型由产品实际操作不妨碍使用浏览器/自动化。测试阅读设计作为依据与主责评审设计方案分别处理。
