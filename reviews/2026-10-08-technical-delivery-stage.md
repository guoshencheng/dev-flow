## 实际规则推演

用假设性“保存条目”需求逐项对照本次协议；这些是解释边界的桌面案例，没有启动业务应用或登记测试通过。

| 输入场景 | 对照后的处理与成立依据 |
| --- | --- |
| 产品要求编辑保存/读回、查看者拒绝、失败保留输入；架构已有接口/数据/权限契约 | 技术方案按 OUT 说明页面/动作/接口/业务/存储/读回及拒绝/恢复，产品和架构实际 Review；测试综合原规则与 OUT 设计保存/读回、拒绝与恢复用例，AI Review 后交人工确认，再计划/AI 复核和编码 |
| 技术方案列保存功能，却漏掉产品已定查看者权限 | 产品从原 RULE/AC 反查缺口，阻断方案并回研发；即使错误地交给测试，测试仍读取原产品并反馈遗漏，不能删掉拒绝用例来配合方案 |
| 用例只看保存 201 或把查看者预期改为允许写入 | 用例 AI Review 分别识别缺少最终持久化结果和违背原权限规则，修正并复核后才交用户；不修改产品预期来让当前设计通过 |
| 技术方案与用例 AI Review 已通过，用户尚未确认 | Review 记录不能替代人工确认，不进入依赖此基线的正式编码；独立调查/候选准备可继续，未答复保持待确认 |
| 方案为避免约束提出跨域直接写表，违背重要 ARC | 架构 Review 阻断，修正到原契约；确需改变重要架构时提供受影响候选并确认，不用内部计划自主调整绕过决定 |
| 纯 API 新功能；或既有有效方案/用例内局部修复 | API 从调用到业务/数据结果定义 OUT/TC，无需虚构页面；局部修复复用有效 Review/确认，仅更新变化与计划，避免重新审批全套设计 |

技术实现方案与后续实施计划分别说明产出/完整链路和执行切片/依赖，项目可同一记录分节但保留 Review/确认版本。新增阶段没有赋予测试设计原型走查主责；用户指定检查范围仍按共同协议处理。
