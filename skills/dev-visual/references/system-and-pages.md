# 设计系统、组件与页面

读取产品规则与信息优先级、现行视觉系统、代码主题、已验证组件和目标内容。新方案在本次范围内改善，已有项目局部设计不自动扩展为整体换肤。

## 可实现的视觉规则

| 对象 | 写到规格与代码映射中的内容 |
| --- | --- |
| 布局 | 导航、主要内容、辅助信息和行动区域；对齐、宽度、阅读顺序及相关滚动行为 |
| 排版 | 标题/正文/辅助文本层级、字重、行高、长度与截断策略；关键信息如何完整可读 |
| Tokens | 语义颜色、间距、尺寸、圆角、边界和层级；权威代码位置与必要主题差异 |
| 组件 | 官方组件/项目组件/共享组合的选择、公开属性、变体、真实源码和使用边界 |
| 状态 | 相关加载、空、错误、禁用、只读、权限、成功和结果未知的具体呈现 |
| 窗口与内容 | 实际目标窗口、窄屏/长文字/大量数据变化下的规则与必要案例 |
| 反馈与动效 | 实际触发、持续时间、完成与中断，必要 reduced-motion 替代；不影响任务完成 |

Tokens 必须能定位到 ConfigProvider、CSS 变量或实际主题模块。B 端从 Ant Design 的官方 Token、公开属性和组合扩展；不要复制一份脱离实际代码的数值表，也不要为了风格自建已有基础控件。C 端使用项目 shadcn/Tailwind 基底，复制参考源码后由项目维护。

## 结合交互语义

产品定义入口何时可见、何时可执行，视觉确定显示、禁用/只读说明、位置和相关状态的呈现。状态颜色、标签、说明和可操作反馈结合，关键含义不能只依赖颜色。禁用与错误原因保持可理解；基础控件的键盘、焦点和可访问名称保留。

例如批量操作：数量和范围由产品定义，视觉使范围与主操作清晰；零选择、处理中、部分失败、结果未知用对应呈现。未知结果不能只换成通用红色“失败”。纯布局取舍无需重写业务规则。

## 原型与工程复用

同一项目、相同运行环境的设计稿持续维护在已有应用的隔离路由或一个稳定的 React 设计工程中。新任务先定位现行页面、组件、主题和已确认版本，更新受影响部分；新会话、职责切换和新迭代都不是重新初始化工程、复制整页或重做设计系统的理由。没有合适入口时才新建 Vite + React + TypeScript 工程；已有非 React 工程按局部范围复用，不强制迁移。

独立设计工程统一放在 `docs/dev-flow/visual/prototype/`，与设计文档一起在 `docs/dev-flow/` 下维护；复用正式应用隔离路由时，业务源码留在实际工程位置。项目索引登记稳定源码路径、启动命令、页面/场景入口和组件/主题位置；现行页面规格、组件说明与设计规范按[视觉资产协议](project-assets.md)在项目级持续维护。迭代索引只关联输入、变更和确认版本；改动较多时按需拆出 `visual/changes.md`，未变或变动很小时不创建独立 UI 文档。普通历史由 Git 追溯，需并存的重要候选保留独立场景或按项目方式从对应提交启动。

无有效工程且需要完整多端设计入口时，随包[React 设计稿模板](../assets/design-workspace/README.md)提供桌面/移动独立视图、组件展示、规范原文、真实主题、注册表、总览及 iframe 尺寸容器。通过 `scripts/design-template.mjs init --project <项目绝对路径> --dir docs/dev-flow/visual/prototype` 复制自包含源码与锁文件，目标已有内容时拒绝覆盖；后续直接维护项目副本。模板的 antd 订单任务仅为候选示例，采用时替换实际品牌/页面/规则；C 端沿用已有 shadcn/ui 基底并复用组织方式。现行规范统一维护在项目的 `docs/dev-flow/visual/` 下；模板自带的规范仅供初始化参考，采用时合并到该权威位置并调整展示导入，不保留两份现行文档。

## 模块化 React 设计稿

按页面语义和变化边界组织 React 模块，设计稿也体现组件组合、属性、状态与数据流。仅把所有 HTML 搬进一个 `App.tsx` 没有解决复用问题。独立原型采用下面的统一目录，模块结构按项目需要裁剪，只创建本次需要的模块：

```text
docs/dev-flow/visual/prototype/                 # 仅在需要独立设计工程时采用
├── package.json、锁文件、index.html # Vite 入口与依赖；HTML 只承载应用挂载
└── src/
    ├── app/                      # 页面导航、场景选择与应用入口
    ├── theme/                    # 主题接入；优先引用项目实际 Tokens
    ├── components/               # 跨页面布局和已有共享组合
    ├── features/orders/
    │   ├── components/           # 订单筛选、列表、摘要等领域区域
    │   ├── views/
    │   │   ├── DesktopOrderPage.tsx # 桌面端页面组合
    │   │   └── MobileOrderPage.tsx  # 移动端页面组合，按实际需要
    │   └── scenarios.ts          # 代表数据、状态与方案差异
    ├── preview/
    │   ├── registry.ts           # 各端页面、组件与规范展示的入口映射
    │   ├── DesignOverview.tsx    # 单页整合，引用各模块，不复制其实现
    │   ├── DeviceViewport.tsx    # 移动端屏幕尺寸容器
    │   └── DesignSystemPreview.tsx # 引用真实 Tokens/组件展示设计规范
    └── mocks/                    # 多模块共用的模拟接口/数据，按需
```

| 层次 | 设计与复用要求 |
| --- | --- |
| 主题与基础控件 | 使用项目主题、antd 或已有 shadcn/ui；不为每张设计稿复制一套颜色或 Button/Form/Table |
| 共享布局与组合 | 相同导航、页面框架、操作区等引用同一实现，保留明确属性和适用边界 |
| 业务模块 | 围绕稳定领域区域拆分；模块特有组件与状态就近维护，不强求所有组件全局通用 |
| 页面 | 组合组件、传入数据与回调，协调相关状态；不堆积全部布局、模拟接口与业务规则 |
| 场景与候选 | 加载、空、失败、权限、长内容等通过数据/属性或模拟行为复现；相同结构共用组件，结构确有差异时才增加候选组合 |
| 总览与预览外壳 | 维护入口映射、筛选、组合展示与尺寸控制，引用独立页面/组件/规范，不承载各端的业务布局 |

组件的主要输入、变体、回调与状态含义在规格中关联真实源码。可操作原型按最小必要状态建模，派生信息由已有数据计算，多个组件共享的状态由合理的共同上层协调；静态设计稿用数据/属性展示即可。该拆分方法参考 [React：Thinking in React](https://react.dev/learn/thinking-in-react)，目录名称是项目组织建议，不是框架要求。

优先直接导入实际项目组件和主题，按工程现有包、别名和依赖方式接入。需要隔离数据时在页面或适配层注入模拟数据与回调，保持展示组件的复用；无法直接接入时只复制或参考必要源码，并登记来源和差异，避免长期维护两套同名现行组件。设计代码进入生产前，研发核验真实契约、依赖与工程质量，视觉检查实际集成页面。

Markdown 维护规则、来源与决定，MDX 适合规则旁的局部 React 示例；完整模块化设计稿由自身 React/Vite 工程运行，从文档索引关联。已有 Storybook 或组件目录可补充相关组件状态；页面组合和核心流程仍在实际页面检查，不为简单设计强制搭建另一套工具。

## 多端独立维护与总览整合

以“源码与规范分开维护、展示入口组合渲染”为原则。同一业务的桌面 Web、移动 Web、其他目标端分别维护页面组合或视图组件，公共组件、数据和语义按实际相同部分复用。端特有的导航、信息密度和操作布局留在对应视图，不用一个巨型组件中的条件分支混合所有端。B/C 是产品定位，桌面/移动是展示端，不把两组分类固定绑定。

项目提供一个稳定的设计总览页，按实际范围组合页面展示、组件状态和设计规范；可用分区、标签页或对照区，保证同一入口能查看相关内容。各端可有独立路由，也可作为独立组件嵌入总览；两种入口引用同一实现，不能为总览再复制一套页面。主题或全局样式不同的视图保持样式作用域，必要时在 iframe 中加载独立入口，避免并排展示时互相污染。页面数量大时按需加载选中内容，避免为了“单页整合”一次渲染全部页面和场景。

`preview/registry.ts` 或项目已有入口清单按需要记录页面/组件 ID、展示端、标题、独立路由或组件引用、场景、视口尺寸、现行规格路径和候选/确认版本。总览负责选择和展示，各端模块负责内容；模拟数据与每个展示实例的交互状态保持边界，切换或并排展示不意外共用一个可变状态。重要候选明确标记，不以总览里的显示顺序判断哪个已确认。

设计规范独立维护在现行 `system.md` 或项目设计系统目录，颜色/字体/间距/组件等展示通过 `DesignSystemPreview` 引用真实主题和组件，并关联规范源文件。总览不硬编码另一套 Token 数值、组件契约或页面规则；规范、组件和页面变化时更新各自权威位置，入口只更新引用。

## 移动端屏幕尺寸预览

移动端设计稿统一放在独立的 `DeviceViewport` 或等价容器内。容器只提供屏幕宽高、边界和内部滚动，可按目标尺寸切换或自定义；尺寸以 CSS 像素明确显示，例如 `390 × 844` 仅是展示预设，不宣称模拟某个具体设备。默认保持 1:1 布局，展示区域不够时用总览滚动或明确标注的缩放，不能悄悄改变内部布局尺寸。

本次默认范围只模拟屏幕尺寸，不增加触摸手势、虚拟键盘、设备 API 或操作系统模拟。原型本身需要的点击/输入仍由页面实现；尺寸容器不承担业务行为。外壳装饰放在内容区域外，屏幕内部保持目标宽高，长内容在内部滚动，相关固定导航和弹层也在该预览边界内检查。

对依赖视口媒体查询、`vw/vh`、固定定位、全局样式或挂到 `body` 的弹层的页面，优先在指定宽高的 iframe 中加载该端独立路由；路由继续引用同一页面组件与场景，不复制源码。只有已按容器尺寸适配且样式/弹层有明确边界的组件，才直接嵌入容器；需要按容器宽度响应时使用项目支持的容器查询。窄 `div` 只限制元素宽度，不会自动改变整个浏览器视口。依据：[MDN iframe](https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements/iframe)、[MDN 容器查询](https://developer.mozilla.org/en-US/docs/Web/CSS/Guides/Containment/Container_queries)。

屏幕尺寸预览验证当前渲染，不代表真实移动浏览器或原生平台行为已验证。按声明尺寸检查内部排版、溢出、滚动、固定元素与弹层边界；记录外部浏览器窗口、内部视口与展示缩放，避免只记录总览页的大窗口。

## 持续修改与验证

1. 定位有效工程、现行页面/组件规格和设计规范，列明复用资产以及本轮新增或修改的部分；在迭代索引记录基线，先不复制文件。
2. 在同一工程修改对应端与业务模块，现行规格定向更新并标明候选；用户反馈继续修订当前候选。新增页面先复用布局与组件，新增规范进入设计系统，新增展示入口进入总览清单。
3. 检查受影响组件状态、各端独立页面和总览集成；移动端在声明内部视口下检查。共享组件/主题变化时补查实际消费者，可操作原型还需走查相关流程与恢复。
4. 提供总览与必要独立页面/场景的真实地址和源码版本；迭代只保存资产引用、设计增量、确认范围、检查结论及遗留，不每轮重写 UI 文件。只有不相关的既有有效决定可直接沿用，受影响证据需复验。

候选设计与正式基线分别维护。只有存在明确重复任务、边界与代表验证时提取共享组合；项目特殊权限、数据接口、配额和文案由项目注入。视觉提出通用规则与呈现改进，研发核验实现与依赖，测试检查行为。
