# 实际视觉检查与持续修正

针对当前候选源码与有效规格检查，选择能回答本次问题的页面、状态、窗口和数据。先确认实际服务、路由、主题与资源已加载；HTTP 200、构建成功和 CSS 存在不等于视觉检查通过。

## 记录可比较条件

保留页面/原型 ID、源码版本或文件哈希、输入产品/视觉版本、浏览器、窗口、主题、数据、状态及实际 URL。截图关联这些条件；不要把旧截图当作修改后的证据。外部加载失败、字体替代、平台差异等影响结论时写明实际情况。

## 根据场景检查

- 布局与信息：核心内容和行动可识别，层级、对齐、间距、阅读宽度与滚动符合规格；长文案与真实数据量不遮挡关键内容。
- 组件与状态：正确使用现有组件和 Tokens，相关状态、错误与恢复信息表达准确；禁用/只读理由和反馈可理解。
- 窗口与内容变化：在声明目标尺寸下检查溢出、断行、菜单/抽屉、表格和模态等相关区域。必要的横向表格滚动与整页意外溢出分别判断。
- 相关可访问性：实际检查文本可读性、可访问名称、键盘/焦点路径及返回、必要对比和动效替代；覆盖范围按任务说明，不声称未执行的完整合规验收。

行为检查与静态呈现分别记录。原型需要实际操作关键路径；产品可用性、真实用户观察、独立功能验收仍由实际证据证明。视觉检查发现规则歧义时回到产品，发现数据/操作实现问题时交给研发和测试。

## 问题与复验

问题包含 ID、预期规格、实际版本和场景、预期/实际、影响与截图/操作证据。定向修改对应 Token、布局或组件，再复验原问题和必要关联页面。不能为使当前画面通过而删掉有效功能规则或隐藏失败状态。

自动截图差异可定位变化，但最终结合语义和场景判断。执行者自查、独立视觉复核和用户偏好分别登记。实际生产集成、字体或数据变化后重新检查相关页面，原型证据不自动覆盖生产。
