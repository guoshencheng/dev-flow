# 各类工程的架构与交付约束

与[技术栈选型](technology-stack.md)配合，只读取当前工程对应小节。下面细化首版候选的职责分离与验证；不把某一项目的 SDK、平台和指标要求套用到其他项目。

## React Web 与全栈 Web

Vite + React + TypeScript 用于独立交互客户端和原型；B 端采用 antd，C 端 Web 优先 shadcn/ui。页面/路由管理呈现和交互，业务规则进入领域/用例，网络与存储进入适配，入口完成装配。服务缓存与本地交互状态按职责划分，复用现有方案，不默认叠加全局状态库。

Next.js 用于明确需要的全栈/SSR 单元；标清 Server/Client 边界。数据库、服务端凭据和内部服务放在相应服务端适配；客户端交互入口限定 `'use client'` 的依赖范围，接口或 server action 继续调用用例，不成为第二套业务规则。[Next 服务端与客户端组件](https://nextjs.org/docs/app/getting-started/server-and-client-components)

验证实际核心操作、相关拒绝/异常、路由直达与刷新、目标屏幕和交付构建；SSR 验证客户端水合及服务端依赖，B 端验证权限/数据范围对应结果。交付同时说明浏览器入口与实际服务，不能只提交截图。

## 独立服务、Worker 与数据工程

轻量 TypeScript HTTP 服务可评估 Hono，已有 Next/其他服务保持有效方案。[Hono Node 适配](https://hono.dev/docs/getting-started/nodejs)

HTTP/队列/定时触发只负责编解码、身份与请求生命周期并调用用例；事务、幂等、一致性等由适当的业务/应用边界定义。数据库适配实现用例消费的端口。Worker 有独立启动入口，实际需要时持久化任务状态、重试/取消和恢复；按部署规模决定队列，不把 HTTP 客户端断连默认等同任务取消。

内外网、管理端、公共站或多数据面工程分别说明权威事实、可公开字段、同步协议、版本兼容和写入方；使用同一 ORM 不等于允许任意跨库读写。验收覆盖实际存储/迁移、进程退出后的恢复以及适用的重复/失败场景，交付描述各进程、依赖和配置。

## 内容与静态网站

Astro 静态内容站优先保持内容 schema、路由、RSS/SEO 和构建输出；有交互需求才增加对应 UI 单元。React 是可选择的交互岛，既有纯 CSS/无 UI 框架约束继续有效。[Astro Islands](https://docs.astro.build/en/concepts/islands/)

营销站、产品客户端和设计原型分别登记。营销页面可用于品牌信息，不能未经判断成为复杂产品的操作规范。验证内容 schema、生成链接、静态构建和核心浏览入口，交付静态目录及托管/启动方式。

## Flutter、C++ 核心与原生客户端

通用原生 UI 可评估 Flutter；View/ViewModel 等展示层模式与整洁架构结合，复杂业务用例独立，平台服务通过适配注入，按项目复杂度决定实际分层。[Flutter 架构指导](https://docs.flutter.dev/app-architecture/guide)

C++ 核心复用时标明语言 ABI、数据布局、对象所有权、释放责任、线程和回调边界、错误传播及目标平台工具链。核心算法、渲染和 UI 分工依据实际职责；渲染机制不冒充业务事实源。有预览/导出一致性要求时统一明确的时钟、字体/资源版本和输入契约，再验证结果，具体指标由项目给出。

分别交付并检查目标平台包/应用、原生库和实际启动路径；纯 Dart 测试不足以证明 FFI、打包、资源或真实系统集成。明确现行平台与退役客户端，新增功能使用有效入口。

## iOS AR 与原生图形

明确 AR/相机/空间追踪与实时图形需求时复用 Swift、ARKit、RealityKit/Metal 等系统能力；UIKit/SwiftUI 根据工程入口选择，不引入通用 Web/游戏运行时来替代项目已确认能力。[Apple ARKit](https://developer.apple.com/documentation/arkit)

业务身份/规则、资产契约、时间/随机等必要一致性与场景呈现、ARSession/相机生命周期分别定义；Web 展示与 iOS 渲染可共享数据和版本化资产，不能假定 API/行为完全等价。线程、资源内存和恢复由对应适配负责。模拟器检查和真机集成、性能/持续运行分别报告，设备、构建模式和指标沿用项目实际验收要求。

## Electron 与设备 / SDK 集成

Renderer 负责 UI，preload 提供窄的类型化桥接，主进程/受控 Worker 承担设备 IO、SDK/FFI 和生命周期。核验实际调用的适配器，不能从依赖或名称推断正在使用哪个硬件 SDK。端口表达业务需要，不直接向 UI 暴露任意原生调用。

新工程遵循 Electron 的上下文隔离、Node 集成、沙箱及 IPC 来源/参数核验建议；已有例外记录事实、理由和本次影响。[Electron 安全指导](https://www.electronjs.org/docs/latest/tutorial/security)

设备连接、占用、拔插、操作失败/超时与资源释放按实际能力验收；SDK ABI 和系统架构兼容需要目标机器证据。交付包含可安装应用、所需原生依赖和真实操作入口，浏览器预览只能验证相应 UI 部分。

## 浏览器扩展

WXT + React + TypeScript 可作为起点，按 entrypoints 分别处理 background、content 和 popup/options，消息契约连接上下文。[WXT 入口规则](https://wxt.dev/guide/essentials/entrypoints.html)

业务用例与扩展消息、浏览器存储、网页 DOM 和模型供应商分开；核验后台重启、状态持久化、存储升级、权限和目标浏览器差异。凭据方式由产品/架构决定，区分用户自带配置与服务端凭据；不将受信任服务密钥打入公开包。

实际加载扩展并完成页面操作和配置/恢复场景；普通 Web 组件测试不证明注入、消息或权限成立。交付目标浏览器包、加载/安装说明及对应检查状态。

## 参数化 3D 编辑器与游戏

编辑器的几何/参数规则、领域模型与导出语义独立于视口和工具 UI；Three.js 或 React Three Fiber 适配渲染，Canvas/WebGL 资源生命周期明确。专业视口使用适合的渲染器；属于 B 端的表单、工具栏、数据管理仍优先 antd，而不是用 antd 替代三维画面。[Three.js 文档](https://threejs.org/docs/)

游戏先根据玩法和目标平台选引擎。Godot 可以负责玩家展示/输入，规则可在 Godot 或独立核心中维护，具体事实源须由项目决定；已有 TS 权威规则时，Godot 消费版本化快照/输入，不另造结果。涉及存档/回放/脚本执行时细化版本、确定性和信任边界。

验证规则、视口/交互、必要渲染性能和导出/回放一致性；交付真实播放器或编辑器入口。Godot Web 导出核验所用版本、资源路径和托管要求；启用线程的导出才涉及 SharedArrayBuffer 与相应跨源隔离要求，不能统一添加到所有 Web 工程。[Godot Web 导出](https://docs.godotengine.org/en/stable/tutorials/export/exporting_for_web.html)

## 小程序、小游戏与 Canvas 工具

先识别普通平台页面应用、小游戏或 H5 工具。普通应用以平台 SDK/页面能力为基线，有明确共享 UI 收益时再比较 Taro 等 React 方案；“希望尽量 React”需要和包体、宿主能力、现有入口共同判断。

全 Canvas 工具/小游戏可共享 JS/TS 规则与渲染核心，将触摸、文件、生命周期和宿主 API 留给平台适配；Vite 可用于 H5 预览，不能据此登记为已实现的小程序。原型中的云函数/数据 schema 或实现计划继续标为目标。

交付宿主需要的包/目录和实际运行步骤，验收平台输入、授权、文件/存储和关键恢复；H5、开发者工具、真机分别记录。平台审核或发布状态与代码实现分开。

## AI Runtime、CLI 与 MCP

运行核心拥有项目规定的任务/消息事实与执行状态，HTTP/UI/CLI/MCP 通过公开接口消费；供应商 SDK、模型配置、工具 IO 和存储留在适配层。持续任务明确取消、预算、重复结果、恢复与幂等语义；协议连接和业务运行生命周期分别定义。

SDK 按项目能力与有效限制选择：需要 Next 集成的服务可以评估 AI SDK，已有自有 Runtime 和指定 provider 的项目保持自己的约束。核验 MCP SDK 的包名/版本及匹配文档，不能把新一代 API 套入旧版本。[MCP TypeScript SDK](https://github.com/modelcontextprotocol/typescript-sdk)

薄 CLI/MCP 入口不重复业务实现，输出和错误协议可供自动化消费。核验目标客户端/协议的真实握手及必要断连/恢复，交付可调用命令或服务与实际配置方式；替身供应商只证明隔离逻辑。

## 媒体管线、Python 绑定与 IoT 部署

媒体任务可用 Python 组织处理、FFmpeg/Pillow 做实际媒体步骤、独立 React 控制面；输入/输出 schema、资源和工具版本明确。模型供应商、文件/对象存储、外部命令适配用例，任务事实和可恢复的阶段按需求持久化。实施时探测 FFmpeg 的真实编解码/字体能力，再以产物检查和必要实际播放验收；Web 状态成功不足以证明视频可用。

Python/C++ SDK 绑定按 ABI、头文件、链接库与目标 OS 判断。新 Python 工程采用声明依赖的现代工程配置，旧 `setup.py` 样本先核验工具链兼容，不据此保证现代平台能构建。

IoT 服务和部署工程优先复用官方镜像、Compose/配置和已有操作链路。业务配置、部署装配和设备操作分别记录，说明数据卷/迁移、健康、网络和必要恢复；按授权在目标环境验证并交付操作入口。文档调查和静态配置读取不能登记为已部署，也不需要为这类任务新建 React 应用。
