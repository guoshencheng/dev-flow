# 架构设计、契约与研发对焦

用于新能力、跨模块变化、接口/数据演进和实现计划 AI 复核。先核对有效产品规则、交互/视觉约束与[实际系统地图](system-and-module-map.md)。遵守[整洁架构](clean-architecture.md)，完整确认与自主实施流程引用[执行协议](../../dev-flow/references/execution-contract.md)。

新工程、首次接入或平台/核心依赖变化时，按[技术栈选型](technology-stack.md)恢复并核验项目技术基线：执行形态、实际栈、工具链、运行/数据单元与交付入口。选型与业务模块边界结合，现状、有效约束和候选分别登记；局部变化直接复用有效基线。

## 从规则到模块与契约

把本次能力划分为可验证用例，说明触发者、输入、权限、重要不变量、输出/错误、影响的数据和外部依赖；分配到明确的业务域和模块。每个新增/变化模块说明职责、公开边界、数据所有权与允许依赖。确认目标与现状分别表达，列出达成目标需要的变化。

为必需约束使用稳定 `ARC-<ID>`，关联相关 RULE/AC、责任模块与验证入口。ID 可沿用项目命名，不能与既有权威定义再建平行版本。约束须可判断，例如“退款用例通过结算公开接口请求，不直接更新结算表”，而非“高内聚、可扩展”。

| 契约 | 按实际风险细化 |
| --- | --- |
| API/用例/事件 | 请求和结果语义、状态/错误、调用者、授权位置、兼容版本；适用时明确超时、幂等、重复/乱序与重试 |
| 数据 | 字段语义、所有权、读写路径、状态转换与约束；适用时明确事务、并发冲突、迁移、保留/删除 |
| 跨域协作 | 公共入口和依赖方向、同步/事件选择、失败处理、数据一致性及补偿责任 |
| 运行与交付 | 真实启动/部署入口、必要依赖与配置、目标环境；适用时明确健康、可观察性、恢复与升级兼容 |
| 技术与平台 | runtime/工具链和锁定安装、前后端/原生/渲染/SDK 边界、支持平台与产物；关联技术基线及改变重要选择的依据 |
| 质量与信任 | 用户已有性能/可靠性/成本目标、测量环境和不确定性；身份/租户边界、数据访问与相关拒绝检查 |

OpenAPI、schema、类型定义、迁移或现有文档已是权威源时直接引用；架构文档解释语义、责任与选择，避免复制生成第二套易漂移契约。低风险无关项可注明不适用，不编造指标或给每个接口增加事件与幂等体系。

## 重要选择与用户确认

说明核心方案、基于事实的可行替代、选择理由、用户可理解的收益和代价、兼容与运行影响、关键假设。影响用户已确认的系统边界、数据/权限、成本/兼容或运行交付方式时提交具体决定；内部文件、函数和遵守基线的实现调整由 AI 处理。

只对有实际不确定性的点做小型实验，记录环境、结果和未证明部分。必要迁移给出阶段、数据检查、兼容期、切换条件、失败恢复及恢复后验证；不能把代码回滚等同于数据可回滚。候选按[设计模板](../assets/templates/architecture-design.md)裁剪，确认前提供可审阅结果，未答复不视为批准。

## 实现计划 AI 复核与过程检查

实际读取计划、确认基线和受影响工程，检查纵向切片是否覆盖规则/约束/用例，模块责任与写入范围是否明确，接口和数据变化顺序能否成立，关键检查和交付入口是否存在。报告计划版本、复核方式、结论与阻断问题；一次 AI 复核通过后直接进入已授权实施。新的证据使重要假设失效时，定向重审受影响部分。

研发提出新依赖、数据写入、接口变化或测试失败暴露系统边界问题时，结合当前候选检查相关代码和契约；持续对焦反馈包含“版本/证据 → 违反的约束或业务影响 → 最小修复范围 → 复验”。已确认基线内可自主调整方案实现，改变重要基线则按执行协议只确认受影响部分。与研发/测试使用同一缺陷或任务 ID，避免另建互不关联的缺陷账本。

## 验证与交接

按约束选择源依赖检查、独立业务用例、真实适配集成、接口兼容、数据/权限或性能检查，给测试交接场景、数据、拒绝/失败结果与检查环境。模拟检查只证明被隔离的策略；外部服务、持久化和实际交付需对应真实验证。架构静态 Review、AI 计划复核、测试通过和用户确认分别记录。

交付前核对当前候选符合性，有本次必需约束的偏差即推进修复/复验或报告未完成。交付后的现状同步与改进建议按[复盘与演进](retrospective-and-evolution.md)处理。
