# 当前系统与模块地图

用于首次接入、理解既有代码、影响分析和交付后的代码业务复核。地图以实际实现为依据；按本次影响范围读取，首次基线说明尚未覆盖区域。

## 从入口追踪业务

读取项目权威架构入口和版本，结合 `rg --files`、工程清单、启动/构建配置、路由/命令/任务注册、schema/迁移与测试定位候选模块。排除依赖、构建物和生成代码的噪声，但记录生成契约的权威源。目录树、类名和依赖清单不能独自证明业务职责。

选本次核心业务和相关失败分支，沿“入口 → 授权/校验 → 用例 → 业务规则 → 端口/外部适配 → 数据变化/结果”读取实际符号与调用。检查规则是否分散、重复、缺失或被旁路，数据由谁写、事务在哪里、跨模块依赖走哪个公开边界。回调、注册、注入、动态加载和别名引用必要时继续追踪；未解析的边注明未知。

结合产品 RULE/AC、已有契约和真实检查判断代码语义。发现疑似逻辑缺陷时提供条件、实际路径、预期依据和可复现验证；业务预期不清时登记待澄清，不凭架构偏好更改行为。代码评审任务保持其写入范围。

## 地图的必要信息

| 视图 | 需要表达的事实 |
| --- | --- |
| 系统 | 运行单元、真实入口、外部依赖、数据流、部署/运行配置及信任边界 |
| 业务域 | 当前能力、术语与规则、拥有的数据、主要用例、与其他域的公开协作；推测的边界标为候选 |
| 模块/目录 | 稳定模块 ID、全部相关目录或文件、业务域、层次、职责与不负责事项、数据拥有者、公开入口、验证位置 |
| 依赖 | 模块间实际源码依赖、允许方向、运行调用/事件流；装配引用与业务引用分别说明 |
| 业务链路 | RULE/AC → 入口/用例/领域符号 → 数据/适配 → 检查入口；代表覆盖与遗漏 |

一个模块可能跨多个目录，一个目录可能混合多项职责；按事实映射。领域未稳定或跨域共用时保留说明。支撑模块注明技术能力而非假装业务域；模块负责人可登记角色/团队或维护者，未知不造人名。

依赖图标注源码方向或运行方向，不能在同一条无说明的箭头里混用；图旁保留来源路径/符号。可用 Mermaid/表格按清晰程度选择，图不能取代模块表和关键证据。

## 合理性评价

从业务变化的内聚程度、依赖方向、数据所有权、契约稳定性、重复规则、隔离测试能力、故障与权限边界及演进成本评价。判断与当前规模、有效目标、真实变更/缺陷一起考虑；一层目录、多目录模块或具体技术选择本身不是问题。

对每项判断区分：已读到的结构/逻辑事实、实际运行观察、设计约束偏差、尚待验证的风险。给出证据和影响，不以文件行数或抽象层数量评分。合理的现状同样登记其依据；无必要改动时明确复用。

## 来源与覆盖

记录仓库/任务、源提交、工作区是否有相关未提交变化及其文件内容哈希、检查日期、实际读取的路径/业务链路、执行命令和结果。非 Git 工程用本次相关文件的内容指纹。证据与对应源码版本关联；后续 Git 历史保留事实，不回写旧报告让它假装检查了新代码。

资产是否有效依据本次相关源码、规则、配置和契约变化判断，不能仅因日期较新就沿用。说明“本次核验的模块”与“尚沿用旧版本的模块”；未读/未执行区域标明范围，静态 import 检查不宣称掌握完整运行依赖。
