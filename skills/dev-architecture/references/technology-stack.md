# 技术栈选型与项目基线

版本：0.1。更新日期：2026-10-08。用于新项目、首次恢复工程、增加执行平台、替换核心依赖和架构复盘；局部修改只核验受影响部分。用户确认的 UI 偏好沿用[共同 UI 约定](../../dev-flow/references/ui-stack-and-components.md)，本参考补充运行平台、服务、数据与交付选择。

## 先确定项目形态与有效事实

同时识别两个维度：**执行形态**（Web、服务、原生、扩展、游戏、工具、媒体或设备）和**用户任务**（B 端、C 端、内容展示等）。一个仓库可能有产品客户端、营销网站、管理端、Worker 和原型多个单元；分别记录入口和约束。页面样式、目录名和安装了某个依赖都不能单独证明产品类型或实际采用。

选型依据按以下方式处理：

1. 用户本次要求和有效项目决定是目标约束；读取 AGENTS、现行架构/迁移记录，识别在用、原型、历史和明确退役路径。
2. 核对实际启动入口及相关调用，结合 manifest、锁文件、运行版本、CI、镜像和部署脚本建立当前事实。规范描述与源码事实分别记录，冲突保留依据并定向核实。
3. 已有工程优先复用能满足本次目标的有效技术栈；新项目或确有缺口时应用下面的候选默认。样本中的旧依赖和项目专有指标不提升为通用要求。
4. 提议说明相对现状的变化、替代、收益、兼容/数据/成本/交付影响和验证。只确认影响重要基线的选择；遵守现有决定的内部实现按[执行协议](../../dev-flow/references/execution-contract.md)自主推进。

包管理器不能只看 `packageManager` 或锁文件数量。检查同一安装单元的文档、CI 安装命令、workspace 和锁文件是否一致；`npm run` 可以执行 pnpm 安装后的脚本，不等于 npm 安装。多个独立原型/网站各有锁文件可以合理；同一安装单元声明冲突须记录并确定权威链路。调查阶段不清理锁文件或执行升级。

## 首版候选默认

下表是无有效项目选择时的起点；并非将全部现有工程迁移到一套技术栈。按命中的[平台约束](stack-profiles.md)展开，选择满足任务的最小组合。

| 项目形态 | 候选默认与适用判断 |
| --- | --- |
| 交互 Web / 独立原型 | Vite + React + TypeScript；B 端遵守 Ant Design 并优先 antd，C 端 Web 优先 shadcn/ui；专用视口按任务选择 Three.js/Canvas |
| 同仓全栈 Web | 存在 SSR、服务端路由/数据与同仓部署需求时考虑 Next.js + React + TypeScript；普通原型保留 Vite，不因将来可能有后端提前扩张 |
| 独立 API / Worker | TypeScript + Node + Hono 是轻量 HTTP 候选；业务与 SDK/HTTP 分离。长任务需要持久化事实、失败恢复与运行入口，不能依赖请求存活 |
| 内容站 / 静态站 | 内容和 SEO 为主时考虑 Astro + 静态输出，交互区按需引入 React；已明确纯 Astro/CSS 的项目保持该约束 |
| 原生移动 / 桌面 | 先判定设备能力、图形性能、SDK 和发行平台：通用原生应用可考虑 Flutter；iOS AR 使用 Swift + 系统 AR/图形能力；既有 C++ 核心通过受控接口复用 |
| Web 技术桌面 / 硬件控制 | React + TypeScript + Electron 可用于需要桌面/设备适配的工程；SDK/FFI 和进程职责独立，不能仅因为已有 React 就选 Electron |
| 浏览器扩展 | WXT + React + TypeScript 候选；后台、内容脚本、页面 UI 和平台权限分别设计 |
| 3D 编辑器 / 游戏 | 参数化编辑器优先复用 Three.js，React 工程可用 R3F；游戏按玩法、运行和导出需求选 Godot 等引擎；渲染引擎与业务事实源分别判断 |
| 小程序 / 小游戏 | 先区分平台页面应用与全 Canvas 小游戏：前者选目标平台能力，再评估 React 适配方案；后者可以共享 JS/TS + Canvas 核心与平台适配，Web 预览不代表宿主验收 |
| AI Runtime / CLI / MCP | 可独立测试的核心 + 薄协议适配；TypeScript 是现有生态候选，模型供应商和 SDK 按项目约束适配；避免绑定所有项目到同一 AI SDK |
| 媒体 / Python / IoT | 媒体管线可选 Python + FFmpeg/Pillow 与独立 Web 控制面；设备部署复用官方服务、Compose 和配置；SDK 绑定遵循原生 ABI/toolchain，不为非 UI 工程增加前端 |

## 必须落到项目中的要求

- **版本与构建：** 记录实际兼容的 runtime/SDK、包管理器、锁文件、编译工具及目标平台。新 Node 工程选受支持 LTS，首版优先评估 24 系列，实施时重新核验生命周期和依赖要求；工具运行时与项目生产版本分别记录。[Node 发布状态](https://nodejs.org/en/about/previous-releases)、[Vite 运行要求与模板](https://vite.dev/guide/)
- **依赖边界：** 沿用[整洁架构](clean-architecture.md)。领域规则与用例不直接依赖 React/antd、HTTP/ORM、模型 SDK、设备或渲染框架；基础设施适配内层拥有的契约。算法/渲染等技术模块可有明确框架依赖，说明它与业务域的关系；既有耦合如实登记，按本次范围演进。
- **数据与服务：** 不按“全栈”标签默认配置数据库、Redis、队列和微服务。有持久化、事务或多进程共享需求时比较实际方案；单机工具可评估 SQLite，多实例共享事务可评估 PostgreSQL，浏览器离线则评估平台存储。记录数据所有者、迁移、备份/恢复和运行环境，不能用模拟存储的通过证明生产持久化成立。
- **UI 与源码共享：** 按 B/C 规则选择第三方基础组件。自有 React 组合或许可允许的参考源码复制进项目，记录来源提交/哈希与定制；不以内部 npm 包发布为前置。原生/Canvas UI 按平台规则实现，不强塞 Web 控件；其他 C 端按共同约定先研究参考。
- **交付与验证：** 每个运行单元写明开发入口、实际依赖、构建/检查方式、可启动或可安装产物、目标环境和核心验收；涉及设备/宿主/外部服务时区分替身、模拟器与真实集成证据。命令来自项目并核验，不能照抄样本端口、私有地址或部署方式。

## 技术基线与持续建设

沿用已有权威位置；无规范时在 `docs/dev-flow/architecture/stack.md` 使用[技术基线模板](../assets/templates/technology-baseline.md)。小项目可并入当前架构入口。区分“观察到的现状”“有效决定”“候选默认”“未核验”，记录源码/配置版本、适用单元和采用理由；重要平台、数据或运行选择关联 ADR 与 ARC，不复制锁文件和 schema 的完整内容。

新增平台、依赖大版本、包管理/CI 改动、存储或服务拆分、SDK/ABI、交付环境变化，以及确认某条路径退役时，架构 Agent 重核受影响基线和模块地图。研发复盘检查真实入口与决定是否一致，更新偏差、建议和验证状态；未实施的建议保留候选状态。

经过实际交付验证的项目方法可提炼为通用候选，包含来源、适用边界、迁移代价和可重复检查，再更新本参考。2026-10-08 的只读项目调查见[项目技术栈清单](../../../docs/project-tech-stacks/2026-10-08-survey.md)；它提供选型样本，不能代替未来任务核验当前工程。
