# 研发结束后的架构复盘与演进

架构在设计、相关实施变化、交付核验和研发后的复盘参与。更新由实际变更和反馈触发；本 Skill 不提供后台监听服务，也不把每次编辑变成整仓审计。

## 何时参与、看多大范围

| 触发 | 合适的复核范围 |
| --- | --- |
| 首次接入既有项目、用户要求架构 Review | 声明范围内建立当前系统、业务域和模块基线；注明遗漏 |
| 新业务能力、跨模块/跨域变更 | 本次链路、涉及模块、相邻契约、关键数据/依赖及现状地图 |
| 局部修复完成 | 原因相关模块和受影响规则/依赖；资产无变化时记录复用 |
| 迁移、依赖/运行拓扑变化 | 实际切换状态、兼容/恢复、数据和运行契约 |
| 重复缺陷、运行事件、业务规则持续分散 | 依据真实证据扩大到相关边界与变化原因，提出定向演进 |

交付前检查本次必需架构约束，阻断问题按已授权范围修复并复验。实质研发完成后，基于最终候选及实际验收结果做一次范围适当的代码业务复盘，更新现状并识别后续改进。可以合并为一份交付核验/复盘记录，发现属于必需条件的问题仍需回到修复循环；可选演进不阻断已满足条件的交付。

## 完整实现变更评审

方案 Review 检查拟议产出；实现评审检查当前代码是否满足需求及实现质量；复盘整理现状与演进。可合并记录，但不能用方案通过或架构地图替代实际实现检查。局部任务按影响裁剪；完整功能在完整候选就绪后集中检查，可与正式验收针对同一固定版本并行，不逐切片新增实现评审门槛。提前专项仅按[共同执行边界](../../dev-flow/references/execution-contract.md#实施与正式验收的边界)开展。

发起者提供原始要求、有效 RULE/AC/UI/ARC/OUT、任务开始基线、最终候选、基线到候选的完整变更、相关未提交修改、测试证据和已知缺口。开始基线若有相关未提交内容，保存快照/指纹，区分初始内容、本次修改和他人既有修改；不覆盖他人工作。多提交任务不能只审最后一个提交，基线不明确先补核验，不声称完整覆盖。

先核对评审包完整性，再沿真实业务链路阅读变更及必要上下游代码，检查需求遗漏、规则/不变量、权限、副作用、异常恢复、兼容、依赖、可维护性及测试保护。diff 用于定位变更，行为不清楚时追踪实现或针对实验；测试通过也不能替代代码与原要求核对。

分别给出“需求符合性”和“实现质量”的结论（通过、阻断或待验证），附检查范围、依据与未覆盖项。产品核对业务语义，架构承担相关代码质量评审，研发处理修复，验收复验行为；按影响引入视觉/运维，不增加六职责例行审批。

意见使用项目现有 tracker，关联编号、证据、影响、处理决定、修复候选和复评/复验。正确意见修复；错误意见核验反驳证据后记录不成立；模糊意见先澄清；证据不足保留待验证。按[研发意见处理](../../dev-engineering/references/review-feedback.md)定向复评，受影响测试重新执行；阻断项不能凭“已修改”关闭。仅要求评审时不自动改生产代码。

允许且实际能够委派时用独立上下文，提供完整原始输入，核验实际成果；受限时注明主 Agent 自查及独立性缺口。评审者参与过实现时说明限制，不把角色名称当作独立证据。

## 复盘要回答的问题

读取有效设计、确认记录、计划及 AI 复核、最终变更、测试/运行证据和已有架构资产。按[系统与模块地图](system-and-module-map.md)沿真实业务链路阅读，而非只看 diff。明确：

1. 当前系统实际由什么运行单元、入口、模块和数据组成；本次新增、合并、迁移或废弃什么。
2. 各目录属于哪个模块，每个模块属于什么业务域或支撑能力、承担什么层次和分工，公开契约及数据由谁拥有。
3. 实际源码依赖和业务调用是否符合[整洁架构](clean-architecture.md)及确认约束；有哪些合理的现状、例外和未解决偏差。
4. 业务规则在哪里落实，数据/权限/失败/兼容责任是否闭合；测试证据证明了什么，静态阅读或未测假设还有什么。
5. 本次经历暴露了什么结构性原因，有何值得实施的最小改进，收益是否足以覆盖迁移和维护成本。

不使用未经定义的整体“架构评分”。证据不足的风险注明待验证和获取证据的方法；未发现有价值的变化时可以明确无需改动。

## 发现与建议

每项发现记录 ID、状态、版本/路径/符号或实际结果、关联规则/约束、条件与业务影响、判断依据。建议说明目标、具体涉及模块/目录/契约、改动前后、替代与权衡、实施依赖、适用的分阶段/恢复、验收和回归。大小模块调整、共享逻辑提取或技术替换均需实际理由，不以模式偏好推动重写。

| 优先级 | 处理依据 |
| --- | --- |
| P0 | 当前已发生且持续造成重大故障或数据/权限影响，按故障范围处理 |
| P1 | 有证据违反本次必需业务/架构约束，或使约定交付不能成立，关闭前不能登记完成 |
| P2 | 有证据的维护/演进问题或范围外缺陷，需要计划实施；列明收益、代价与验证 |
| P3 | 可选改善或待验证假设，先取得必要证据，避免扩大本次范围 |

严重度依据实际影响，不因一条反向 import 自动定为 P1。已有明确授权的必需修复持续推进；仅要求 Review 时提交具体建议，不自动改生产代码。改变已确认的重要设计才请求对应决定，后续工程任务的实现计划仍由 AI 复核。

## 将结论写回项目

用实际源码更新当前架构和模块地图，保留已确认目标及未实现差距；关联本次复盘、来源版本和检查覆盖。旧决策被替换时记录替代关系；改进登记待办与责任、依赖、验证方式，后续实施后按真实证据关闭。复核无变化的资产可沿用原证据并记录本次核验范围，不改写成全仓已重新检查。

使用[复盘模板](../assets/templates/architecture-review.md)与[项目资产协议](project-assets.md)。共性方法在项目中确有效果后提出通用 Skill 改进候选，未验证的偏好不直接成为所有项目的新要求。
