# 测试先行与回归保护有效性

用例确认确定业务场景与预期，不等于自动化已经编写或在错误实现上失败。研发随实现编写必要局部测试；验收负责覆盖、失败/通过证据核验及实际复验。关联有效 RULE/AC/TC，自动化细节不另加人工确认。实施中新增或改变行为时，先按[需求变更闸门](../../dev-flow/references/execution-contract.md#实施中的需求变更闸门)更新受影响 TC，再为新增行为取得目标失败或最小可重复证据；真实 E2E 可提前准备，但在当前候选中执行后才能形成 E2E 结论。

## 按对象选择执行方式

| 对象 | 方法与证据 |
| --- | --- |
| 新增可自动化业务行为 | 先写最小行为测试，实际运行，确认因缺失行为而失败；实现后观察通过；适用重构后保持通过 |
| 缺陷修复 | 修改生产代码前，以测试或可重复步骤捕获原问题；固定原预期，修复后用相同场景复验，补必要回归 |
| 修复已完成才补测试 | 在隔离副本中将同一测试用于错误旧实现与修复新实现，证明旧失败、新通过；只在新实现通过不能证明保护有效 |
| 低影响修改、文档、探索 | 按对象选择内容/引用、手工步骤或实验；说明适用性，不强制 TDD，不要求全部 E2E 自动化先写完才能编码 |

不能恢复旧实现时记录“回归有效性尚未证明”和缺失条件，保留新实现验证；不补写未发生的失败，不随意向真实环境重新注入缺陷。

## 判断失败是否捕获目标问题

核对测试实际执行到目标行为，断言来自有效契约，失败信息能指出预期与实际差异。语法错误、依赖缺失、服务未启动、错误身份/数据、测试未运行或跳过不能算捕获目标缺陷。先恢复执行条件，再取得目标失败；框架退出码本身不够。

权限拒绝测试同时验证拒绝结果与没有写入等副作用，必要时观察存储而非仅检查 UI 或返回码。测试不应只复述当前实现，或因过宽断言、吞异常、错误替身、只检查准备条件而始终通过。

旧实现和新实现均通过时，先核对是否实际触发缺陷、断言是否足够、用的是否同一候选/数据，以及隔离边界是否遮蔽错误；保护不足的测试修正后重新验证。不要修改旧实现、已确认预期或环境来制造想要的红/绿结果。

## 事后补测的隔离与证据

采用明确的工作副本或 worktree，隔离端口、数据、缓存和依赖状态；保留任务工作区及他人修改。记录旧/新实现候选、测试路径与指纹、身份/数据准备和实际命令/步骤，控制与目标无关的条件。旧版无法运行于当前依赖时明确兼容差异，先排除环境原因，不能将它计为目标失败。

在[计划](../assets/templates/implementation-plan.md)、[工程交接](../assets/templates/engineering-handoff.md)或已有 tracker 关联：目标行为、验证方式、测试位置、失败证据、通过证据、适用边界/未验证项。计划阶段列待取得证据，执行后回填候选和结果，已有运行记录只链接。

修复交回待复验版本；验收按[运行与复验](../../dev-acceptance/references/execution-and-feedback.md)核验保护及当前行为。源码变化使受影响证据待复验，不把研发自测登记为独立验收。
