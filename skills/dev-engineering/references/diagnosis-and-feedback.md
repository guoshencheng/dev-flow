# 诊断、修复与研发测试持续对焦

用于测试反馈、生产或开发异常、重复失败。与[测试执行协议](../../dev-acceptance/references/execution-and-feedback.md)共享缺陷编号、TC、候选和环境；优先更新已有缺陷权威记录，避免研发/测试各建一份状态账本。

## 从证据确定问题

读取原始规则/契约、失败报告、步骤、请求/响应、数据/页面状态与实际版本。核对测试对象是不是当前服务/候选，必要时取得最小复现；不能先改代码再猜问题已经解决。

区分实现错误、测试执行错误、环境/依赖和规格冲突。提出可被日志、断点、请求/数据或针对实验检验的原因，先核验关键链路，再做最小有根据的修复。重复失败时检查版本、身份/数据、异步竞争和依赖，不只重跑或增加等待。

| 观察 | 诊断方向与修复依据 |
| --- | --- |
| UI 显示成功，刷新缺失 | 追踪响应、真实写入和读取/缓存；落实服务端结果后再反馈成功 |
| 按钮禁用但 API 可写 | 检查实际入口授权和拒绝副作用；界面透出不能承担后端授权 |
| 失败后输入消失 | 检查状态/表单重置触发点与恢复契约；成功和失败处理分别落实 |
| 本地通过，集成失败 | 核对候选、配置、身份、代理/浏览器边界和依赖；不把环境问题登记为实现验收通过 |

这些是诊断线索，具体原因仍需实际证据。运行日志及样本按项目边界脱敏；诊断只改变必要可写范围，不覆盖其他人的工作。

## 修复并交回待复验

实现缺陷按原预期修复；选择器、数据隔离或脚本错误可以修复执行方法，并记录为何不改变验收含义。确认的业务、架构或预期有歧义/错误时，引用原始依据并回到受影响决定；不能删测试、换 Mock、扩大容差、忽略失败或改预期以使候选变绿。

修复后执行原场景与受影响回归，相关格式/静态/类型、接口与数据检查按变化补齐。重试通过保留首次失败及诊断，不等于问题消失。临时隔离不稳定用例记录缺口，不登记必需验收通过。

交回缺陷 ID、根因证据、修改位置、候选版本/指纹、实际自测命令/结果和待复验范围。研发标记“已修复待验”，测试实际复验后关闭；同一执行者兼任时分别记录诊断与复验，不声称独立验收。

失败继续依据新证据修复和回归，不每轮要求用户 Review 实现计划。重要计划假设失效时定向 AI 重审；需要新的环境/关键决定时说明具体缺口并推进其他独立工作。必要根因知识和有效回归沉淀到项目，不能将一次具体修复变成所有项目的固定步骤。
