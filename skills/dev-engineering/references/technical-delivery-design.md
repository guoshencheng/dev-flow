# 架构后的端到端技术实现方案

用于完整功能在架构设计之后、测试用例定稿之前，明确本次技术产出及完整链路。研发主责，产品检查需求符合性，架构检查约束，涉及页面/状态时视觉协作；测试可提前反馈可测性，正式用例以经 Review 的方案和原始产品文档共同定稿。共同顺序见[执行协议](../../dev-flow/references/execution-contract.md)。

此阶段产出可审阅的实现方案，尚不登记生产功能已实现。必要可行性实验注明问题/范围与证据，正式编码在用例 Review 和人工确认、实施计划 AI 复核通过后开始。技术实现方案定义要交付哪些行为及链路，后续实施计划安排切片、依赖、写入范围和执行检查；小任务可在同一记录中分节维护，保留各阶段有效状态。

## 有效输入与技术产出

读取项目有效产品 RULE/AC、流程/原型、设计/UI、重要架构确认及 ARC/接口数据契约，核对当前工程与交付要求。尚未存在的实现/地址标为计划，不生成假预览或声称当前服务可用。项目已有有效方案直接复用，只细化本次变化。

按任务粒度沿用项目 ID 或使用稳定 `OUT-<ID>` 标识技术产出，关联以下内容：

| 内容 | 要回答的问题 |
| --- | --- |
| 页面/入口与功能 | 新增/修改/复用哪些页面、路由、API、命令或任务？谁能看见与执行？功能限制/状态与产品规则如何对应？ |
| 端到端链路 | 用户/调用者从何处开始，经过什么操作/状态、请求、业务用例与模块、存储/下游，最终看到什么结果？关联已有 FLOW/页面 ID。 |
| 契约与数据结果 | 依哪个接口/错误/权限与 ARC，谁拥有读写，成功后如何读回、刷新/重新进入，实际需要时如何跨进程保持或完成异步副作用？ |
| 异常与恢复 | 无权限、边界输入、加载/失败/取消/重试、数据保留与恢复如何端到端落实？按产品/架构实际要求选取，不编造新语义。 |
| 技术与交付产出 | 需要哪些前后端改动、资源/配置/样例或迁移，以及可启动源码/产物/目标部署？按已确认架构分配责任，关联实际工程入口。 |
| 测试可观察结果 | 每个关键链路的前置身份/数据/依赖、可观察结果与核验位置是什么？本地替身、真实依赖、目标环境和待决分别说明。 |

只罗列文件、接口或页面截图不足以说明完整功能。无 UI 的接口/CLI/后台任务从实际调用到业务/数据结果描述，不制作虚构页面；纯静态内容到构建页面/资源/访问结果即可，不补虚构后端。

## 产品符合性与架构 Review

先做双向覆盖：从本次每条相关 RULE/AC/流程/页面状态核对有无对应 OUT/既有实现及链路，再从 OUT 回查是否有有效需求依据。未实现的遗漏、与规则冲突、未经确认的缩减/新增范围列为问题；技术可行性不足回架构或方案修正，不把遗漏隐藏为测试不覆盖。

实际读取对应版本，由产品检查使用限制、功能透出、具体逻辑和恢复是否符合预期；视觉检查方案中的页面/状态是否承接 UI 规格；架构检查模块、接口/数据/权限/恢复与重要约束。主 Agent 按可用职责组织 AI Review，同一执行者兼任时分别记录检查范围，不声称独立；可用且获准委派时才采用独立上下文。

记录方案/输入版本、实际 Review 执行者/方式、检查依据、问题、修订和通过/阻断结论。阻断项修正并定向复核通过后交测试，默认不增加人工技术方案审批。原产品/重要架构必须改变时仅请求受影响决定，未答复或查看文档不等于确认。

## 给测试和后续研发的交接

提供有效产品/UI/ARC、方案版本与 Review、OUT/链路清单、对应预期/真实依赖与缺口。测试从原始规则和方案共同设计用例并建立 `RULE/AC/UI/ARC ↔ OUT/链路 ↔ TC ↔ 实际证据`；产品中有而方案中无的行为仍是必须处理的覆盖缺口，不能将 OUT 当作需求全集。

测试用例 AI Review 通过后人工确认场景/结果与范围，研发再按[基线与计划](baseline-and-plan.md)产出实施计划并 AI 复核，沿已审阅 OUT 与确认 TC 自主实施。技术方案和用例变化关联同一输入版本，影响业务/架构/验收基线时重新确认受影响部分；内部实现方式调整只更新方案/计划与必要复核。

项目使用现行技术方案位置；无规范时采用 `docs/dev-flow/engineering/changes/<任务ID>/technical-solution.md`，用[模板](../assets/templates/technical-delivery-design.md)裁剪，项目技术与工程索引关联方案、Review、用例和后续计划。候选方案、Review 通过、人工确认、实现和实际验收分别标记。
