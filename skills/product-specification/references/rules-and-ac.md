# 业务规则与可观察验收：P05

先核对用户要求、产品有效决定和实际领域、接口约定。概念定义、约束和可观察场景使用相同含义；发现来源冲突时记录各自来源和待决问题，不替用户选择未授权的业务政策。

## 规则需要表达什么

- 对象与字段：含义、必填、默认、范围、格式、唯一性、空值与已有数据的处理。
- 操作：前置条件、权限、输入、成功结果与适用失败结果。
- 数据变化：什么时候生效、失败时保留什么、并发或重复动作在用户侧的预期。
- 边界：本次支持与不支持的设备、任务、规模和外部依赖；没有事实时说明假设及影响。

按项目使用的格式维护，简单功能可在现有规格中用短表述完成。领域规则、页面文案与 API 字段不同名时说明映射；不能把字段技术校验直接等同于业务完成。

## 验收写成用户可以观察的结果

保留已有稳定编号。新增编号可以使用 `AC-...`，关联用户目标、规则、流程状态、场景与下游验证方式。

| 信息 | 示例写法 |
| --- | --- |
| 条件与数据 | 用户具备权限，选中包含两条有效和一条错误记录的文件 |
| 操作 | 进入预览并执行已允许的提交方式 |
| 结果 | 实际提交范围、错误保留、界面反馈与后续入口符合该项目规则 |
| 失败与恢复 | 明确失败或结果未知时分别验证输入保留与恢复行为 |
| 验证入口 | 原型走查、实际界面、接口或交付环境，说明尚缺入口 |

示例中的“允许方式”仍以项目事实为准。场景覆盖相关成功、边界、拒绝和恢复；判断点应能定位实际差异，例如提交后数据显示在哪里、重开页面是否仍可继续、错误如何修正。

不要只写“符合预期”“体验良好”“测试通过”。技术质量目标应有项目依据和测量条件；没有明确延迟、规模或研究数据时，提出需要确认的问题或候选指标，不编造精确承诺。

## 变更与反馈

当新要求改变规则，说明决定来源、受影响的流程、状态、验收、原型与其他契约。保留未受影响编号，记录替换或废弃关系；源代码改变不会自动成为产品规则改变的理由。

测试发现偏差时先区分实现缺陷、规格歧义和需求变更。实现缺陷按有效验收修复；确需改规则时由有效决定更新规格并通知相关职责。无法从输入证实的根因保持未知。

产品提交可验证规格，测试选择并执行验证。没有实际运行应用时，记录“规格已完成，实际功能未验收”，并移交对应验证入口与缺口。
