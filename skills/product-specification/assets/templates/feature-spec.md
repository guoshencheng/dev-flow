# 功能产品规格

默认保存于 `docs/dev-flow/iterations/<迭代ID>/product/spec.md`，由迭代索引关联输入版本、Review/确认与结果。已有权威位置通过索引映射，目录组织遵循共同文档协议。

正文先回答有哪些功能、谁使用、从哪里进入、如何操作、得到什么结果。按实际用户任务展开：小功能可用几段文字，大功能可分步骤或任务小节；以下是内容提示，不是必须逐项复制的章节。不要把全局 RULE/AC 大表作为阅读主线，也不要仅将旧规则表搬到功能标题下。用户指定格式或项目有效模板优先；沿用旧模板时核对是否需要按本次目标调整。

## 目标与范围

说明目标用户、当前任务与阻力、期望结果、本次支持和不支持的范围。多功能时可列简短功能导航，写明使用位置、功能名称和结果。区分事实、候选、已确认决定、未知及实现状态，关联实际来源和版本。

## 功能：〈用户要完成的任务〉

直接说明使用者、入口及完成结果。按入口 → 操作 → 反馈 → 结果描述正常路径；步骤多时用顺序列表，简单时用连贯文字。

在对应操作附近说明相关字段的含义、默认和校验，权限与前置条件，计算/排序/筛选口径，限制及超限反馈，保存和生效时点。界面可见、禁用、只读与服务端可执行授权分别说明；不把隐藏入口当作权限拒绝的证明。字段表、流程图或状态表只在有助理解时使用。

把相关的加载、空态、拒绝、错误、取消、重试、数据保留、部分失败及结果未知的恢复写在该功能或步骤附近。异步等待结束或关闭页面不代表服务端动作撤销；需要查询原动作时明确恢复入口。无关分支不机械罗列，未知语义标待决。

在相关功能附近给可读验收例子：具体条件与操作之后，用户会看到什么、数据如何变化、失败后如何继续。覆盖正常及关键边界/拒绝/恢复；明确示例是假设还是实际事实。例子是业务预期，不是已执行证据或正式 TC。

如需要原型，就近关联 PT、源码版本、场景入口、模拟范围及视觉规格；写明页面信息结构、操作、状态和转场。原型中的数值仍须有明确业务来源，不能形成隐含规则。没有原型需要时不制造空成果。

按实际任务继续增加功能，不要求各功能重复相同小标题或表格。共享概念只解释一次并由功能引用，不能把全部规则抽离到全局章节。

## 共用概念、决定与待决（按需）

仅保留理解多个功能所需的术语、关系和重要取舍；说明决定来源、有效版本、未知及影响，不复制功能正文。相关变化注明受影响功能、原型、接口、实现和回归。

## 追溯附录（按需）

已有稳定功能/RULE/AC 编号保留，新增编号按追溯需要采用。可在本文附录或同目录 `traceability.md` 映射编号 → 功能具体段落 → 有效来源/决定 → 下游验证入口；记录替换/废弃关系，不把旧编号复用为新含义。正文无需查编号即可理解；附录只定位，不另写一套业务规范。没有编号也要有可定位的业务预期与验证依据。

参考[功能展开示例](../../references/function-first-example.md)。作者自查、独立 Review、用户确认、实际实现和正式验收分别记录，不以规格完成推定其他阶段通过。
