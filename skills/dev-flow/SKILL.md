# 研发协作流程

首次使用先读[总纲](references/constitution.md)，再按任务读取[任务路由](references/task-routing.md)和[执行协议](references/execution-contract.md)。设计文档和实施计划用中文。项目事实及有效决定从所属项目读取，不从本 Skill 推定。

本 Skill 决定阶段、职责、依赖、授权复用和整体完成条件。具体 Git 操作使用[git-workflow](../git-workflow/SKILL.md)，实际派发、等待及独立性核验使用[subagent-coordination](../subagent-coordination/SKILL.md)，文件组织、预览与归档使用[document-management](../document-management/SKILL.md)。局部 Git、文档或派发任务可单独调用对应 Skill，不因此启动完整研发流程。

## 从目标推进到完成

1. **先建流程文档并确认整体流程。** 开始执行 Dev Flow 时，必须先在本轮迭代创建独立 `Progress.md`，作为由主 Agent 全局维护的整体流程与进度文档。按[总体进度规则](references/progress-management.md)和 [Progress 模板](assets/templates/progress.md)写明最终目标、范围与基线、路径及裁剪、全部阶段、职责与依赖、验证、交付和结束条件。主动向用户展示文档链接及整体路径，取得明确流程确认后再推进后续阶段；只创建文件、声明“按 Dev Flow 执行”或把展示留作下一步都不算完成。已有迭代恢复原 Progress，同范围有效确认直接复用。
2. **明确进入流程的时点。** 按行为、交互、契约和交付变化选择标准、快速、修复、系统变更、故障或探索路径。启动 Dev Flow 或从咨询转入设计/研发等阶段时，先核对同范围有效流程确认；没有时，首条进度说明先告知“拟定整体流程，待你确认后推进”，然后完成第 1 步；已有时说明复用并继续。确认前只允许必要的只读了解及流程草案；不先开始设计、实现或评审。纯查询/解释可直接回答，但一旦明确启动 Dev Flow，不以“轻量调研”跳过文档与确认。
3. 核对设计层业务预期、重要取舍、统一研发设计 Review、计划复核及本次正式实施授权。涉及 UI 时按[UI 方案展示与用户确认](references/execution-contract.md#ui-方案展示与用户确认)先判断变化类型；新增或改变方案（含纯视觉变化）须展示候选并取得用户确认，再进入对应正式实现。恢复已确认设计、明确调整指令、规范内实现细节及明确自主委托按有效依据复用，隔离候选制作不等于正式实现授权。首次进入正式实现前取得明确同意；同范围已有授权直接复用。完整正式 TC 在完整功能候选后维护，不是实施前置。
4. 组织专业职责完成当前阶段。产品/UI 候选接受真实代码技术反馈；研发统一主笔架构与实现设计，独立 Review 后形成实施计划并复核。连续实现、集成、自测后，针对完整候选做完整变更 Review、正式用例及其独立 Review、验收执行和交付核验。问题进入关联修复、定向复评和复验。
5. **持续维护同一份 Progress 直到整体完成。** 阶段切换、Agent 工作交接/回报、验证结果及基线/候选变化后，由主 Agent 更新当前状态、成果入口、阻塞和下一步；索引、设计、计划与 Todo 只引用或投影，不另建总体进度。按需使用[状态格式与只读核验器](references/stage-state.md)核对声明，工具通过不证明实际确认、Review 或交付。判断原确认和证据是否仍有效，结束前核对全部必需结果、技术收尾、约定交付与项目沉淀，向用户提供 Progress 入口与完成说明；缺失项保持未完成。派发结束或等待超时不构成整体完成。

Agent 工作交接发生在实际职责衔接或接续时，由主 Agent 核验后更新 Progress；结束时面向用户提供完成说明，两者用途不同。流程确认、业务设计确认和实施授权分别记录覆盖范围，用户明确合并时复用同次答复。

“开始收尾”按[收尾门槛](references/closeout.md)进入 [iteration-closeout](../iteration-closeout/SKILL.md)：盘点本轮已有资料，取得相关专业结论，实际回写项目级通用文档，再核对已授权的代码保存、交付与归档。Progress 单列文档盘点与回写结果，必需同步缺失时不结束。明确只整理文档时按范围裁剪，不重走功能实施。

## 按对象选择职责

| 对象 | 所需职责 Agent（以宿主实际发现为准） |
| --- | --- |
| 用户任务、流程、规则、原型可用性 | 产品 |
| 布局、Tokens、组件、响应、实际呈现 | 视觉 |
| 边界、契约、技术规范、独立技术 Review 与收尾 | 架构 |
| 技术设计、计划、实现、诊断和自测 | 研发 |
| 正式用例、实现验收、反馈与复验 | 测试验收 |
| 环境、产物、运行、发布与恢复 | 运维交付 |

优先使用宿主实际可用且已加载公共约束与职责正文的 Agent，无需重复读取同一份源提示词。角色未加载时，按[subagent 协调的加载与降级规则](../subagent-coordination/references/host-execution.md)补充所需内容。提示词 Markdown 是配置生成的维护源；长篇专业 reference 与模板未内嵌，仍按任务需要读取。配置文件存在不证明角色已经注册或加载。

职责按对象和问题选择，不因浏览器、Mock 或自动化工具改变主责。产品/视觉主责设计原型走查；测试可在设计期反馈可测性，正式验收面向完整实现与交付候选。需要独立 Review 时作者与评审执行者分离；实际派发受限时如实记录独立性缺口，不把自查登记为独立通过。模型和推理强度遵循用户本次要求与宿主配置。
