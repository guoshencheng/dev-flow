# 多角色研发协作总纲

协议版本：0.34。更新日期：2026-10-26。本版明确 UI 方案确认：新增或改变方案（含纯视觉变化）先展示候选并取得用户确认，再进入对应正式实现；恢复有效设计、明确调整指令、规范内实现细节及明确自主委托按实际范围复用。实施中 UI 偏离回到受影响决定。既有独立 Progress、整体流程确认、设计/实施授权、Review、正式验收及交付条件继续适用；状态 schema 1 和核验算法不变，不能自动发现未声明 UI 确认。用户当前要求和宿主约束优先；设计文档与实施计划用中文。

## 共同目标与层次

以用户要求的实际结果为终点：规划任务验证规划成果，功能任务验证可运行行为，部署任务验证实际部署和约定运行结果。阶段完成不代表整体完成，未执行、失败、受阻或失效的必需条件保持未完成。

本 Skill 只维护任务路径、阶段依赖、参与职责、确认与授权、证据有效性和完成条件。六职责的专业目标与判断由实际加载的 Agent 提示词提供，维护源位于 `agents/prompts/`；已加载公共约束和职责正文时不重复读取同源正文，未加载才按[subagent 协调](../../subagent-coordination/SKILL.md)补充，长篇参考和模板按需读取。Git、文档的具体方法分别见[git-workflow](../../git-workflow/SKILL.md)、[document-management](../../document-management/SKILL.md)。项目当前规则、技术版本、候选和实际证据保存在所属项目，通用协议不替代项目事实。

主 Agent 维护最终目标、完整阶段进度、有效决定与依赖、执行边界和结果集成。专业职责对各自结论负责；Skill 只提供具体操作方法，工具或入口存在不证明成果成立。需要独立 Review 时使用未主笔对象的实际执行者；若无法独立执行，记录限制，不把自查写成独立通过。

## 六个职责与评审对象

| 职责 | 对象与应交接的结论 |
| --- | --- |
| [产品](../../../agents/prompts/product.md) | 用户任务、流程、规则、业务预期、原型可用性；交出按功能组织的有效需求、可观察验收预期、已有编号追溯与未决 |
| [视觉](../../../agents/prompts/visual.md) | 层级、布局、Tokens、组件、状态和响应呈现；交出实际渲染检查及限制 |
| [架构](../../../agents/prompts/architecture.md) | 业务边界、依赖、契约和技术约束；独立技术 Review 与实际架构收尾 |
| [研发](../../../agents/prompts/engineering.md) | 真实代码成本反馈、统一设计和计划、实现、集成、自测与完整候选 |
| [测试验收](../../../agents/prompts/acceptance.md) | 独立业务预期来源、实现后正式用例、验收证据、缺陷和复验结论 |
| [运维交付](../../../agents/prompts/operations.md) | 环境、产物、实际运行/发布、故障恢复及交付可靠性 |

职责按对象和问题选择，不因浏览器、Mock、可点击原型或自动化工具改变主责。产品/视觉走查设计原型；测试可早期反馈覆盖和可测性，正式用例与验收面向完整实现和交付候选。产品核对业务符合性、架构检查技术质量、研发修复、测试复验行为，视觉/运维按影响参与；不例行启用全部六职责。

## 路径与阶段

按[任务路由](task-routing.md)从行为、交互、契约、运行和交付变化选择标准、快速、修复、系统变更、故障或探索路径。快速路径仅用于已有明确有效预期、局部可逆且有验证方式的范围；仍需本次正式实施授权。混合任务逐范围裁剪，不能通过拆分规避完整集成。

完整功能的依赖顺序是：

1. 每轮迭代单独建立覆盖最终目标的 [Progress.md](progress-management.md)，由主 Agent 维护全局进展，恢复有效基线、未知和全部后续阶段。先向用户展示文件入口和整体路径，取得[流程确认](execution-contract.md#流程开始前的用户确认)后再推进；同范围有效确认直接复用。
2. 产品/UI 候选形成时，研发根据真实代码反馈位置、形式和状态成本，架构按影响核对边界；产品/视觉回应。受影响业务规则、可观察成功/拒绝/恢复结果及重要取舍在实现前固定。涉及 UI 时按[UI 确认规则](execution-contract.md#ui-方案展示与用户确认)判断类型，新增/改变方案先展示可审阅候选并取得用户确认，正式实现入口核对有效版本和来源；已有有效确认与明确指令等按覆盖复用。
3. 研发统一主笔本轮架构与实现设计；架构独立 Review 技术，产品/视觉核对需求与呈现承接，阻断项修订并定向复核。研发形成独立实施计划并由未主笔者 AI 复核。
4. 首次正式实现前按[执行协议](execution-contract.md#首次实施的人工同意)取得明确范围授权；设计确认可明确合并授权，已有同范围授权直接复用。完整正式 TC 不是实施前置。随后连续实现、集成、自测，内部切片不增加逐片正式审批。
5. 完整候选就绪后，对任务开始基线至候选的完整变更及相关未提交内容做独立实现 Review；测试依据原产品与有效设计维护正式用例并独立 AI Review。二者可针对同一固定候选并行。正式验收及交付核验使用可运行候选和有效用例。
6. 具体问题关联修复，在新候选上定向复评、复验和受影响回归；核对最终整体集成、实际交付及架构技术收尾，通过[独立收尾 Skill](../../iteration-closeout/SKILL.md)完成已有资料梳理和项目长期文档回写，再按[收尾门槛](closeout.md)结束。

设计原型通过、局部测试、构建成功、用例 Review 或服务可访问只证明其实际覆盖，均不能替代约定的完整链路和交付。无 UI、局部修复和纯文档任务按对象裁剪，不制造空成果或未要求的生产验收。

## 授权、变更与证据

用户明确确认的整体流程、业务预期、重要取舍和正式实施范围分别记录对象、版本与覆盖；用户可明确合并确认与授权。只认可流程不自动成为业务确认或开工授权；需求表达、查看资料、局部答复或 AI Review 不自动授权开工。同范围跨会话或切片不重复询问。推送、合并、发布和发送通知等外部动作沿用实际授权，不能从设计确认推定。

实现中新增或改变行为、失败恢复、重要契约、已确认 UI 方案或交付边界时走[变更闸门](execution-contract.md#实施中的需求变更闸门)：识别影响，更新受影响的规则、设计和计划，取得必要 Review/确认/授权后再实施。纯视觉方案变化同样适用；既有 TC 按影响修订，尚未形成的完整正式 TC 仍在完整候选后维护；业务含义不能延到实现后决定。

每次基线、候选、设计或环境变化都判断先前确认、Review、测试与交付证据是否仍覆盖当前范围。只复用未受影响且有来源的结果，失效、未知和未执行如实保留。[结构化状态与只读核验器](stage-state.md)可检查已声明的版本依赖，不证明真实执行或专业质量。

## Agent 工作交接与完成说明

Agent 工作交接是执行者之间对工作、上下文及责任的移交，发生在职责/阶段衔接、中断或换执行者时，按[派发与结果核对](../../subagent-coordination/references/dispatch-and-lifecycle.md)明确交出方、接收方、输入/候选版本、授权和写入边界、结果、未完成项及下一动作。接收方核对输入和进入条件，主 Agent 核验后更新 Progress；不以发送消息或自报完成代替接续成立。

完整候选的实现 Review、正式 TC 中全部必需检查、真实交付和技术收尾均按当前版本核对；任一必需检查失败、受阻、跳过、未执行或判断所需实际观察未完成，所属 TC 和整体不能通过。截图等证明附件可选，不能只因没有附件否定已实际完成的验证；执行表及附件留在忽略目录，不提交。取消或被替代的目标按真实结束原因处理，不虚构验收。主 Agent 汇总范围、有效版本、实际 Review/验收/交付、项目成果入口、未覆盖和遗留承接。派发成功、单个子任务结束或等待超时不构成整体完成。
