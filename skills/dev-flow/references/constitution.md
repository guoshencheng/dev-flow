# 多角色研发体系总纲

版本：0.29。更新日期：2026-10-21。共同协议覆盖设计期跨职责技术反馈、研发统一设计与独立 Review/计划/架构收尾、Harness 专业 subagent 默认执行、覆盖最终目标的唯一进度、实现后正式用例维护/Review/验收及交付核验，以及候选、授权、变更与资产收尾。

本总纲随 `dev-flow` Skill 提供，项目资产保存在所属项目。安装和更新见[插件维护指南](../../../docs/plugin.md)，流程不依赖 Agent 初始化。

本总纲规定多角色研发体系的共同目标、协作与交接、持续测试、交付和项目沉淀。按本次任务选择实际可用的职责和专业指导。

总纲是共同协议的维护入口；[职责能力目录](role-capabilities.md)定义职责与交付边界，[项目资产维护](project-asset-maintenance.md)指导持续沉淀，[职责执行说明](codex-agent-configuration.md)指导主 Agent 和可用子 Agent 使用专业 Skills。用户当前指令和宿主约束始终优先。

## 共同目标

任务以用户要求的实际结果为终点。研发交付优先保证严肃的 UI 与交互设计、连续实现与整体测试验收，以及能够使用、快速启动或已要求部署的成果。设计和计划服务于交付，专业指导逐步增强。

每项任务明确交付范围。要求规划、评审或文档时验证对应成果；要求可运行功能时实际启动并完成核心任务；要求上线时验证实际部署和约定运行结果。以范围内必需验收条件是否成立判断完成。

体系覆盖需求、设计、实现、测试、交付、运行、维护和退役。按任务种类、工程对象、风险与当前阶段选择工作路径，每次只启用有实际作用的职责。

## 总纲和执行组件的关系

| 组件 | 职责 |
| --- | --- |
| 总纲 | 维护共同协议、验收和项目沉淀原则 |
| 主 Agent | 维护最终目标与完整阶段进度、范围/确认/依赖、原生派发、唯一写入者与资源边界，集成证据并推进整体交付 |
| 专业职责与执行者 | 标准跨职责任务默认由实际可用且允许的 Harness subagent 专注执行设计、实现、评审、验收和收尾；受限时如实降级，模型由本次策略选择 |
| 专业 Skills 与参考 | 承载按需读取的操作方法、案例、专业工具和评测 |
| 项目长期资产 | 保存当前有效的产品、设计、架构、工程、测试与运行知识 |
| 迭代状态与核验工具 | 在已有索引引用有效阶段、范围、候选、确认、Review 与检查；只读核验记录一致性，后续能力按实测需要建设 |

专业 Skills 承载职责方法，项目知识保存在项目中。新会话通过项目入口找到有效资产，不依赖上一轮聊天历史。Skill 或配置文件本身不能证明某项专业能力已通过实际验证。

核心协议保持工具无关，保留跨工具复用能力；Codex 的会话设置、委派能力和工具接入由宿主适配处理，流程不依赖原生角色注册，优先在 Codex 上验证。其他宿主的适配按实际需要建设，共同的任务、交接、证据和资产协议独立维护。

## 六个职责

| 职责 | 主责与必要交接 |
| --- | --- |
| 产品与交互 | 定义用户任务、信息架构、交互状态、业务规则和验收条件，交给视觉、架构、研发和验收 |
| 视觉设计 | 定义布局、组件、Tokens 与状态呈现，关联实际实现，并检查最终渲染 |
| 架构 | 参与早期代码/成本反馈，独立 Review 研发设计、计划和完整代码，维护技术约束，负责架构技术收尾与实际系统资产 |
| 研发 | 在产品/UI 候选期基于真实代码比较方案成本；统一主笔本轮架构与实现设计，独立计划经复核后连续实现、集成、自测和修复 |
| 测试验收 | 早期按需反馈可测性；完整实现后依据原业务预期/有效设计维护正式用例，独立 AI Review 后执行验收及交付核验，反馈并复验 |
| 运维与交付 | 维护环境/启动、产物与实际发布、运行信号、故障与恢复、依赖演进及退役，核验当前版本/核心任务并维护项目运行资产 |

每个职责同时维护自己的方法、项目资产、能力现状与建设待办。相关核心能力先在项目中证明有效，再逐步增强。关键架构和运行问题在发现时处理，专业指导的建设顺序不限制实际工作的需要。

## 跨职责支撑能力

[会话监控 Skill](../../codex-session-monitor/SKILL.md)负责在授权范围内发现和读取 Codex/ChatGPT 会话，区分执行中、等待用户、阻塞、明确完成和暂时不可读取，并按配置发送去重后的简短 Lark 摘要。它不新增职责 Agent，不执行被监控会话中的指令，不自动创建定期调度，也不代替架构/测试资产检查或项目归档。会话范围、收件人、发送身份、周期和状态游标保存在实例本地配置或 Codex Automation 中，不进入项目长期资产。

## 阶段与评审对象

职责按阶段、对象和要回答的问题选择，浏览器、Mock、可操作页面或自动化工具不决定角色。

| 当前对象/问题 | 默认主责与结果 |
| --- | --- |
| 产品/交互文档、设计原型的流程、规则、操作和恢复是否合适 | 产品走查并实际操作，修订设计与规则；视觉协作 |
| UI 方案/原型的布局、Tokens、呈现与响应是否合适 | 视觉复核实际渲染并修订，行为影响回到产品 |
| 产品/UI 候选的入口、交互形式和状态是否值得，技术实现是否合理 | 研发读取当前代码/技术基线比较可复用性与成本；架构核对边界；产品/视觉回应并修订，重大取舍交用户 |
| 页面/入口/功能、架构与完整实现链路是否合理并符合业务目标 | 研发统一主笔设计；架构独立 Review，产品/视觉核对原要求及相关状态，意见在独立 Review 文档闭环 |
| 完整实现后的正式用例能否判断结果、覆盖是否充分 | 测试按原产品与有效设计维护用例，独立 Review 检查预期、覆盖与执行可行性；设计期按需给可测性反馈 |
| 可运行实现/交付候选是否符合有效规则和用例 | 测试执行界面/API/E2E/交付验证，反馈研发并复验 |
| 环境/产物/部署是否正确、如何启动和恢复 | 运维核验当前环境与版本、核心运行结果，维护运行/恢复方法并配合测试 |

测试读取产品/UI/原型作为依据，不等于主责评审设计方案。设计原型即使能启动、能点击或模拟请求也默认由产品/视觉走查；实现测试可以采用 Mock 隔离，但须明确被测实现与证据边界。用户明确指定测试检查原型时按指定范围执行，报告原型/模拟证据，不升级为实现或交付验收，也不自动对整个设计增加测试审批。

## 任务入口

具体步骤与裁剪条件见[任务路由：bugfix 与正常需求](task-routing.md)。bugfix 默认恢复有效预期，正常需求默认按完整功能流程；重大契约变化与线上故障采用相应路径。

主 Agent 从用户最终目标、项目事实和有效决定形成最小简报，明确范围、业务完成标准、工程对象、风险、当前阶段、有效资产与未知。按[进度管理](progress-management.md)在可用 Todo 或持久 Progress/既有索引建立完整阶段计划，包含尚未开始的后续工作、每阶段完成条件、当前目标与下一步。阶段成果不代替整体目标，不能只列本次会话已完成的事项；进度唯一权威，其他文档引用或投影。

| 工作路径 | 使用条件 | 必需结果 |
| --- | --- | --- |
| 快速路径 | 目标清楚、已有明确预期或有效设计、局部可逆、有验证方式，无未确定的行为/交互/重要契约决定 | 简短范围与裁剪依据、用户实施同意、实现或修复、针对验证及约定交付 |
| 标准路径 | 涉及完整用户行为或多个模块 | 必要设计、连续实现与集成、完整候选集中验收、实际交付及项目沉淀 |
| 系统变更路径 | 涉及重要接口、数据、权限或运行兼容 | 增加相应契约、迁移与恢复验证 |
| 故障路径 | 服务正在产生实质影响 | 在授权范围内恢复、验证恢复、定位原因并完成后续修复 |
| 探索路径 | 当前目标是消除不确定性 | 明确问题、实验、观察和后续选择 |

先按行为、交互和契约变化判断路径，再看规模、可逆性和验证成本。新增且未确定的动画、参数交互、预览/恢复等结果属于设计决定；“既有功能内扩展”或“可以回退”不能省略相关前置。纯封装且保持行为/契约时可局部处理；复用基线须说明具体对象、版本、确认及覆盖差异。分别判断路径和当前可执行步骤，快速路径不自动取得实施资格。

重要未知问题通过具体问题澄清，其他独立工作继续。首次正式实现前按[实施授权协议](execution-contract.md#首次实施的人工同意)展示具体范围、验证和交付，取得用户同意；快速路径同样适用。已有同一范围实施授权内的实现、必要修复与复核持续推进；改变范围、行为或重要契约时只确认受影响部分。

## 设计确认与自主实施

完整功能按[执行协议](execution-contract.md)推进：建立全局进度 → 产品/UI 候选与真实代码技术反馈 → 研发统一架构/实现设计及跨职责 Review → 业务预期/重要取舍确认 → 独立实施计划与 AI 复核及有效范围授权 → 连续实现、集成、自测 → 完整候选的实际变更 Review 与正式验收用例维护/独立 Review → 验收执行和交付核验 → 关联修复及定向复评/复验 → 独立架构技术收尾、保存与整体结束。

技术在产品/UI 确认前，基于当前入口、组件、接口、数据和状态比较功能位置、交互形式的实现代价与替代方案。产品/UI 解释业务收益并修订；有争议状态说明真实触发、用户操作价值与维护成本，保留必要的等待、错误、权限和恢复反馈。技术不能单方降需求，设计也不能忽略已证实工程约束。重要分歧交用户决定，不新增例行技术审批。

研发在 `engineering/design.md` 合并本轮架构与技术实现方案，先用中文讲清目标、现状、核心链路、模块/契约、具体逻辑和验证交付。架构独立检查技术合理性，产品/视觉复核业务目标、需求覆盖及呈现承接；正式发现和结论写在独立 `engineering/review.md`，作者修订后定向复核。计划独立放 `engineering/implementation-plan.md`，架构收尾放 `architecture/closeout.md`；主设计引用区持续关联各文档有效版本、状态和简短结论，执行阶段仅引用唯一进度。

实施前固定受影响的业务规则、边界、可观察成功/拒绝/恢复结果、重要约束与交付形态，取得相应有效决定及明确范围实施授权；已有同一范围授权直接复用。独立计划根据有效设计与真实工程形成并实际 AI 复核，完整 TC 的维护、Review 和人工确认不再是实施前置。设计确认可明确合并为“计划复核通过后按此范围开始”，技术设计和计划不额外要求用户逐文件审批。

完整实现后测试从原始产品与有效设计推导正式用例，实际代码只用于定位入口、数据和观察点，不能决定正确预期。用例覆盖正常、边界、拒绝、恢复、必要回归及交付，独立 AI Review 后执行；已确认预期内的细化不增加例行人工审批，发现歧义或改变业务含义才确认受影响部分。研发局部测试、缺陷复现与回归随实现开展，不能因正式用例后置停止测试保护。

每次基线/候选变化更新权威进度、相关设计/Review/计划与用例（已形成时）的有效性。未形成的正式 TC 在完整候选后维护；改变业务预期仍在受影响实现前完成决定。只复用有依据且未受影响的确认和证据，不倒填历史执行，也不为适配当前实现修改验收预期。状态核验只证明声明一致性，不能代替真实 Review 和验证。

## 工程执行选择

采用[分支、worktree、验证与合并建议](git-and-worktree.md)：开始写入前核对任务基线和已有修改，独立任务默认使用任务分支；需要并行或隔离环境时使用 worktree。研发自测贯穿实现、修复与集成，正式 Review 与验收面向完整候选，当前候选的必需检查和实际变更 Review 通过后，按项目策略和已有授权集成；合并与实际交付分别判断。

采用[Harness 原生派发](subagent-guidance.md)：标准功能与跨职责任务的设计、技术调查、研发、Review、验收和收尾默认使用实际可用且允许的专业 subagent；主会话协调最终目标、依赖、决定和集成，大任务不委派时记录具体原因。任务包使用必要原始要求、权威文件/版本和明确写入范围，避免默认继承整段聊天。六职责不等于六个常驻 Agent；作者和独立评审分离，共享文件/资源有唯一负责人。

## 派发和协作协议

派发给职责 Agent 的任务包含：任务编号、当前目标与范围、主责能力、有效输入和资产版本、依赖、可写范围、成果位置、验收条件、交接方式与停止条件。模型和推理强度属于执行策略，遵循用户最新要求和宿主可用配置。专业 Skills 不固定模型与强度，沿用宿主派发默认或父会话设置；用户为某次任务指定选择时，由调用方在该次派发中提供。验证记录保留实际执行设置，不将一次评测的选择固化为通用要求。

专业派发以实际可用的 Harness 能力执行，不用角色扮演替代进程。宿主或用户限制委派时由主 Agent 读取 Skill 承担工作，记录自查与独立性缺口；用户明确要求独立评审时保留待评审，不能自查后登记独立通过。

同一文件或共享接口由一个写入者负责。依赖任务顺序执行；独立任务在可控写入范围内并行。共享原始事实和有效契约，最终集成成果重新验收。当前会话的实际并发与委派约束优先。

角色分歧依据用户目标、有效决定、契约和证据处理。变更需求或契约时通知受影响角色，更新有效版本和相关检查；不能只修改验收来使当前实现通过。需求变更的分类、受影响确认和验证层级按执行协议记录，不将“已实现”或“局部测试通过”当作新的验收基线。

主 Agent 委派后保持整体任务运行，继续独立工作、集成或使用宿主等待工具。派发成功、阶段结果和一次等待超时不能作为结束主会话的理由；只在整体完成、用户明确暂停/停止或自主调查后确需用户输入时交还本轮。平台强制中断保存恢复信息，不声称完成。详见[主会话协议](execution-contract.md#主会话的运行与结束)。

## UI 与交互最低协议

含界面任务由产品维护任务、流程、规则与业务完成标准，视觉维护布局、呈现、Tokens、组件和响应；确认前研发/架构基于实际代码反馈交互位置/形式成本和状态必要性。设计阶段实际操作与检查渲染，实现后产品检查业务覆盖、视觉检查集成呈现、测试执行正式验收；原型通过不代替生产验收。

现行 UI 规范、各端页面/组件规格与源码独立持续维护，通过总览组合展示；迭代引用基线与资产并记录设计增量、确认和结果，不重写完整 UI 文件。专业目录与内容采用[视觉资产协议](../../dev-visual/references/project-assets.md)，多端组织与移动端屏幕尺寸预览采用[设计稿方法](../../dev-visual/references/system-and-pages.md#多端独立维护与总览整合)。

专业方法分别见[产品 Skill](../../dev-product/SKILL.md)和[视觉 Skill](../../dev-visual/SKILL.md)，规格内容由各职责维护。UI 基准与共享组件采用视觉维护的[UI 指南](../../dev-visual/references/ui-stack-and-components.md)，技术选型采用[架构基线](../../dev-architecture/references/technology-stack.md)，总纲不复制专业参数或工具操作。

## 架构参与与研发复盘

架构在产品/UI 候选、研发设计、计划复核和契约变化时参与；完整候选 Review 覆盖实际代码，交付前核对必需约束。验收与交付证据就绪后，架构独立形成技术收尾，更新系统/模块地图、契约和实际设计差异，登记有依据的改进。产品/视觉/研发/测试/运维提供各自结果，主 Agent 综合整体完成判断。局部修复按影响裁剪，阻断回修复，可选演进入待办。

域/模块拆分、整洁架构、技术规范、契约和代码复盘的方法及专业资产以[架构 Skill](../../dev-architecture/SKILL.md)和其参考为准。共同流程只规定参与时点、交接与完成关系，不另建平行架构标准。

实际实现评审按[完整变更方法](../../dev-architecture/references/retrospective-and-evolution.md)核对原要求、有效契约、任务开始基线至最终候选的全部变更及相关未提交内容，分别给需求符合性和实现质量结论。意见沿用项目 tracker，按[意见处理](../../dev-engineering/references/review-feedback.md)核对依据、修复/反驳/澄清/待验证；修复候选定向复评和必要行为复验后关闭，阻断项不能凭“已修改”关闭。

## 连续实现与集中验收

内部切片是研发组织单位，不设逐片正式 Review/验收门槛。研发连续实现、集成、自测和必要回归；完整候选满足本轮范围、真实核心任务和研发检查后，架构 Review 全部变更，测试维护正式验收用例并交独立覆盖 Review。用例通过后执行界面/API/数据及适用真实 E2E，运维与测试核验实际启动、产物或约定部署和交付任务。正式 TC 与正式验收结果不作为研发候选就绪条件，却仍是整体完成条件。

发现具体问题立即反馈，研发按共同根因/关联范围修复下一候选；定向复评、复验原问题及受影响回归，最后核验整体集成和交付。变化先更新业务预期和受影响设计/决定，已形成用例同步，未形成完整 TC 在实现后维护。专项提前检查仅用于明确阶段交付或阻断后续的关键风险，按[执行边界](execution-contract.md#实施与正式验收的边界)裁剪；不能降预期、删场景或用模拟代替必需真实链路。

[研发](../../dev-engineering/SKILL.md)主责实现、诊断、自测，[测试验收](../../dev-acceptance/SKILL.md)主责实现后正式用例、独立 Review、执行与复验。工具案例、Mock、本机、目标部署、原生派发和真实项目证据分别登记；重要独立 Review/验收使用未参与被审对象主笔的实际可用上下文，不能委派时如实记录缺口。

按[测试先行与回归有效性](../../dev-engineering/references/test-first-and-regression.md)，新增可自动化行为先取得目标失败再实现，缺陷修改前捕获原问题，事后补测在隔离旧/新实现上证明旧失败、新通过；环境/语法失败不算目标失败。研发随实现编写必要局部测试，验收核对覆盖/证据并实际复验。低影响修改、文档和探索按对象裁剪，不强制全部 TDD 或全部 E2E 自动化先写完。

根因诊断按[实验方法](../../dev-engineering/references/diagnosis-and-feedback.md)从同条件复现、正常对照和边界取证提出可反驳假设，以必要变量实验取得原因证据后最小修复。假设—实验—结果保存在现有缺陷记录；多次失败触发契约/共享状态/架构边界检查，次数本身不证明架构错误。

## 交付和完成条件

入口明确可启动源码、可安装产物、预览/生产部署或其他约定成果；没有部署目标时优先可启动交付。运维提供当前环境、源/产物版本和运行证据，测试验收约定任务；具体启动、构建、发布、观测和恢复采用[运维 Skill](../../dev-operations/SKILL.md)，验收方法采用[测试验收 Skill](../../dev-acceptance/SKILL.md)。

已有外部动作授权持续有效；缺少决定时完成可审阅候选与独立准备，只确认缺失部分。结果未知的发布/迁移先查询实际状态，不盲目重复执行。

实现、提交、业务预期确认、实现后用例 Review、研发自测、正式验收、可运行交付、部署与当前业务正常分别记录。只有当前候选的必需检查通过、阻断问题关闭、约定交付成立、必要资产已更新，才结束本轮。没有执行的检查、失效证据、未知结果和资源缺口如实报告，继续其他可完成工作；必需 E2E 未执行或受阻时不能登记完整交付完成。

验证记录采用[最小记录协议](execution-contract.md#最小验证记录)，复用现有 runner 输出；截图、资源哈希和视觉基线按实际证明需要补充，不默认建立独立取证与证据合规评审阶段。历史整理和无关工具维护默认后置。

完成先逐必需检查汇总 TC，再形成整体结论；服务调用、原型、真实界面和交付各证明实际观察到的范围，测试数量不补齐缺失证据。必需项尚未闭合时报告实际完成范围和未完成，不以“实现完成”关闭整个任务；结束同步项目入口及当前迭代状态。详见[完成结论](execution-contract.md#必需检查与完成结论)。

## 项目沉淀协议

项目版本保存源码、测试、现行规范、重要决定与必要交接。测试结果与必要证据在测试报告中维护；正式跨职责 Review 与架构收尾独立保存重要结论和问题闭环，普通运行/重试过程不要求单独沉淀。中断、换人或跨机器时通过既有交接入口说明当前状态与接手方法。[目录协议](design-document-contract.md#agent-文档控制)约束文档创建、更新、委派和归档。

项目事实与长期资产保存在所属项目。开始明确项目根路径，从索引定位本次迭代、有效产品/UI/架构/工程/验收/运行资料及版本，核验并复用；过程中更新变化，交付登记资产与缺口，下一任务重新核验。

正常交付结束执行[迭代收尾](document-archive.md#一条指令收尾当前迭代)，用户也可直接说“开始收尾”补做，默认覆盖[代码收尾](git-and-worktree.md#代码收尾)和文档沉淀。主 Agent 核对完整变更 Review、当前候选的必要验证/构建与交付，完成原授权范围内的阻断问题修复，同步有效资产、总结、遗留及入口；相关成果按项目约定保存，无其他约定时形成本地提交，保留无关改动，远端动作按已有授权执行。核验后逻辑归档，不逐项重新确认已授权更新。提交、验收、集成/部署、资源清理与文档状态分别判断，必需结果或归档条件缺失时保留真实未完成状态。

[共同文档协议](design-document-contract.md)维护项目级长期资料与迭代产物的边界、目录、索引、状态、权威来源与归档。长期文档和独立事件无需创建迭代；本轮阶段产物集中在 `docs/dev-flow/iterations/<迭代ID>/`，跨迭代基线保留在 `docs/dev-flow/` 的项目级职责目录；项目文档和独立设计原型统一在该根目录下维护，持续复用的原型工程位于 `docs/dev-flow/visual/prototype/`。目录外的旧文档/独立原型按共同文档协议整理迁移；正式业务、测试和工具源码保留真实工程位置，`.dev/` 仅保存本地运行状态。架构与测试长期资产可在需求进行中、重要变更后、发布前或维护窗口手动检查，也可在用户授权后定期检查；检查先把有效架构事实和稳定回归用例同步到当前基线，再按[整理协议](document-archive.md)归档迭代或被替代候选，不能把仍有效的最新资产移入 `archive/`。调度另需授权。专业规格内容、记录细节与模板由对应职责维护：

| 主责 | 专业内容与资产入口 |
| --- | --- |
| 产品 | [产品资产](../../dev-product/references/project-assets.md)：用户任务、规则、原型与有效决定 |
| 视觉 | [视觉资产](../../dev-visual/references/project-assets.md)：UI、设计系统、Tokens、组件与渲染证据 |
| 架构 | [架构资产](../../dev-architecture/references/project-assets.md)：系统/模块现状、契约、决定与复盘 |
| 研发 | [工程资产](../../dev-engineering/references/project-assets-and-delivery.md)：方案、计划、实现、自测与诊断 |
| 测试验收 | [测试资产](../../dev-acceptance/references/project-assets.md)：策略、用例、运行、缺陷与回归 |
| 运维交付 | [运行资产](../../dev-operations/references/project-assets-and-evolution.md)：环境、产物、发布、runbook 与恢复 |

跨职责文档使用同一[项目预览入口](document-preview.md)，不同专业不重复建服务；维护 Skill 本身使用源文件与内容/引用检查，预览工具验证或用户明确要求时才启动。

成熟度与当前有效性按[持续沉淀指南](project-asset-maintenance.md)分别管理。长期记录可追溯来源与可重复方法，通用候选经过适用边界和行为验证才进入插件；本轮无关建设进入待办。

## 统一交接结果

角色结果使用以下结构；小任务允许简短表达，但关键信息可核验：

1. 当前结论和实际完成范围。
2. 成果位置、候选版本和有效输入。
3. 验收条件覆盖、实际证据和未执行项。
4. 问题状态、限制、依赖与下一步。
5. 项目资产复用和更新、能力缺口与候选经验。

主 Agent 综合原始成果和证据，再形成用户可直接使用的交付说明。子 Agent 自报成功作为待核验结果。
