# 项目文档、原型与归档协议

版本：0.9。日期：2026-10-09。供产品、视觉、架构、研发、验收与交付共同使用。文档属于当前业务项目，通用 Skill 提供方法与模板。先按用途和生命周期分类，再确定专业主责；项目已有有效目录时继续维护，通过索引映射。阶段产物按功能迭代归纳，长期文档可以单独维护。持久目录只保存重要产品/交互、UI 设计、技术文档与正式交接；测试策略/用例属于技术验证文档，结果/总结属于交接结论。事件或决定仅在形成有维护价值的上述文档时持久保存。所有临时运行文件统一进入 .dev，下面是默认布局，只创建当前任务需要的文件。

## 先定位项目和任务范围

先明确业务项目根路径、任务对象和已授权范围，从项目入口 `docs/dev-flow/index.md` 定位相关权威来源。维护长期规范、操作指南或独立事件不要求创建迭代。需要保存一轮交付过程时明确迭代 ID、功能 ID，以 `docs/dev-flow/iterations/<迭代ID>/index.md` 集中关联产品、交互原型、UI、架构、技术方案、用例、计划、验收与交付。新上下文读取相关索引和必要基线，不默认加载全部历史。

一次迭代表示围绕一个可交付目标的一轮工作，可以是功能、缺陷修复、重构、迁移或运行改进，不等同于一次聊天或每个测试重试。ID 使用稳定且唯一的名称，例如 `2026-10-09-order-batch-edit`；日期用于定位，不自动表示发布。后续独立增强使用新迭代 ID，继续关联同一功能 ID；同轮修改、评审反馈和复验继续在原迭代下维护。

本轮交付的阶段文档默认按迭代集中，不散落在项目级职责目录。项目已有有效规范时，在本次迭代索引链接实际权威位置；按用户要求迁移时修正资源与反向链接，避免复制出两套现行规格。

## 默认目录与阶段产物

```text

├── AGENTS.md                            # Agent 约定，引用文档协议与专业入口
├── docs/dev-flow/                       # 项目知识、工作产物与正式交接；可提交
│   ├── index.md                         # 现行来源、活动/历史迭代、交接与结果入口
│   ├── project/
│   │   ├── overview.md                  # 项目目标、范围与当前事实
│   │   ├── glossary.md                  # 共同术语
│   │   └── documentation.md             # 本项目采用的文档与提交约定
│   ├── product/                         # 现行功能入口、共用规则与跨功能流程
│   ├── visual/                          # 现行设计系统、Tokens、通用组件与状态
│   ├── architecture/                    # 实际系统/模块地图、契约与技术约束
│   ├── engineering/                     # 代码地图、开发规范与可复用指南
│   ├── acceptance/                      # 通用策略、回归与自动化/样本入口
│   ├── operations/                      # 当前环境与启动/发布/恢复 runbook
│   ├── decisions/<决策ID>.md            # 需要长期保留的重要决定及取舍
│   ├── records/<事件ID>/                 # 有持续价值的事故/调查/专项结论
│   └── iterations/<迭代ID>/
│       ├── index.md                     # 范围、输入、当前阶段、确认与交接/结果
│       ├── product/
│       │   ├── spec.md                  # 本轮产品规格或相对现行规格的变更
│       │   ├── references/              # 实际采用的设计参考，按需
│       │   └── prototypes/<方案>/       # 原型源码；已有独立工程原位引用
│       ├── visual/design.md             # 本轮页面、组件变化及呈现要求
│       ├── architecture/
│       │   ├── design.md                # 本轮结构/契约/迁移设计
│       │   └── review.md                # 影响后续维护的架构结论与改进
│       ├── engineering/
│       │   ├── technical-solution.md    # 实现方案与符合性结论
│       │   ├── implementation-plan.md   # 切片、依赖与计划复核结论
│       │   └── handoff.md               # 待验/中断/换人交接与复跑入口
│       ├── acceptance/
│       │   ├── strategy.md              # 本轮验证范围与策略增量
│       │   ├── cases.md                 # 用户可读用例及确认
│       │   ├── technical-checks.md      # 对应技术验证、断言与复跑入口
│       │   ├── defects/<缺陷ID>.md      # 无现有 tracker 时记录有效问题与承接
│       │   └── result.md                # 阶段/最终验收结论或验收交接
│       ├── operations/delivery.md       # 实际产物/发布结果与操作交接
│       ├── summary.md                   # 结束总结；简单时合并在 index
│       └── archive/                     # 必须并存的替代方案；普通历史使用 Git
├── src/、tests/、fixtures/、tools/、infra/ # 实际源码、测试、固定输入与工具；可提交

    ├── runs/<迭代ID>/<职责>/<runID>/

    │   └── artifacts/                   # 截图、trace、raw 帧、生成媒体和探针结果
    ├── evidence/                        # 原始截图、机器摘要、诊断及转交材料
```

只创建本次需要的目录与文件。小任务可以在迭代索引内合并范围、方案和验证记录，不强制六套文档。迭代内包含多个需要独立规格的功能时，按需使用 `product/features/<功能ID>/spec.md`、`visual/features/<功能ID>/design.md` 和 `acceptance/features/<功能ID>/cases.md`；它们仍在同一个迭代根下，由迭代索引关联。

复杂原型可在迭代的 `product/prototypes/` 放完整 Vite/React 工程；已有独立原型工程或设计文件继续在其真实位置维护，由迭代索引关联源码、方案、模拟范围和启动命令。业务实现、自动化测试、fixture、配置和基础设施代码留在项目实际源码位置，迭代文档引用它们。

## 索引、权威来源与长期沉淀

项目级目录回答“当前有效的是什么、日常工作怎么做”，迭代内目录回答“本轮改变什么、如何完成、实际结果如何”。同名文档不能独立维护两套现行内容；边界如下：

| 主责/目录 | 项目级长期内容 | 迭代内内容与同步条件 |
| --- | --- | --- |
| 协调者，`project/` | 整体目标/范围、现状、共同术语和文档约定 | 本轮范围/状态放迭代索引，通常不另建 project；整体事实变化时同步项目资料 |
| 产品，`product/` | 当前功能与规格入口、共用规则、跨功能流程 | 本轮规则增量、方案与原型；明确沿用/修改/废弃范围，生效后更新现行来源 |
| 视觉，`visual/` | 当前设计系统、Tokens、通用组件/布局/状态及代码映射 | 本轮页面和局部变化、走查；正式采用的共用变化同步设计系统 |
| 架构，`architecture/` | 实际系统/模块地图、有效契约、技术基线与约束 | 目标结构、契约变化、迁移与复盘；实施后同步实际现状，目标不能冒充现状 |
| 研发，`engineering/` | 代码地图、工程约定、构建/集成和可复用指南 | 本轮技术方案、计划、实现、自测与交接；工程结构/方法变化时同步长期资料 |
| 验收，`acceptance/` | 通用策略、稳定回归及自动化/数据入口、覆盖缺口 | 本轮风险/覆盖增量、用例、执行和复验；持续保护场景进入回归，结果绑定原候选 |
| 运维，`operations/` | 当前环境与可重复的启动/发布/恢复方法 | 本轮产物/环境版本、操作与核验结果；运行条件变化时同步手册 |

重要决定放 `decisions/` 或已有专业决策目录，有持续价值的独立事件结论放 `records/` 或已有事件系统；完全属于本轮的持久结论留在迭代，其他入口引用；原始事件流和调查过程默认本机私有。位置不改变专业主责。源码、契约定义、测试和可执行工具保留真实工程位置。

每个规格对象选择一种权威方式：项目级稳定规格加迭代变更记录，或迭代内完整规格加项目级现行索引。两者不能各自维护完整现行副本。规则分散多轮且难以确定现状时整合稳定规格，保留来源和替代范围。

项目入口记录项目识别信息、迭代列表及状态、功能当前有效来源和长期资产入口。本次迭代索引记录目标/非目标、关联功能、前序迭代与依赖、输入基线版本、阶段文档实际路径、维护职责、设计/用例确认和 AI Review 来源、候选与交付版本、测试结果、遗留项和长期资产变更。使用[项目索引模板](../assets/templates/project-document-index.md)与[迭代索引模板](../assets/templates/iteration-index.md)裁剪；不存在的文件标为缺口，不把默认路径当作已有成果。

产品维护本迭代功能规则与原型；视觉维护对应 UI；架构维护本次设计/实现复盘；研发维护技术方案、实施计划和交接；验收维护策略、用例和执行报告；运维维护本次交付。逐次执行与 Review 过程默认本机私有；重要确认、符合性结论、未关闭意见与影响后续维护的取舍在对应方案、结果、交接或既有 tracker 中提炼，不要求为每次重试另建持久报告。相关专业细节见[产品资产](../../dev-product/references/project-assets.md)、[视觉资产](../../dev-visual/references/project-assets.md)、[架构资产](../../dev-architecture/references/project-assets.md)、[工程资产](../../dev-engineering/references/project-assets-and-delivery.md)、[测试资产](../../dev-acceptance/references/project-assets.md)和[运行资产](../../dev-operations/references/project-assets-and-evolution.md)。Review 可写在对应文档中，复杂时在该阶段目录下拆出记录，保留对象与版本；目录调整不新增人工审批。

迭代产物保存本轮范围、决定和执行结果；跨迭代资产保存当前有效事实与可复用方法。完成后定向更新现行架构/模块地图、设计系统、工程索引、回归和 runbook，并在项目入口标明功能最新有效来源。规格没有变化的部分引用已有权威源；新规格替代旧规格时明确替代范围，不以日期最新自动推断所有旧规则失效，也不把候选覆盖已确认/已交付基线。

产品规格是用户任务、功能行为与规则的权威位置；视觉规格引用产品规则编号，维护呈现、Tokens 与代码映射。原型表达规格中的候选或已确认行为，原型与截图本身不自动替代规格；发现冲突时记录依据并回到相应主责更新。多人协作时同一文件明确一个写入者。

迭代索引集中关联本次产品、视觉、技术、原型、验收、交付与证据；项目主索引关联迭代和现行长期资产，指向该业务项目的成果。使用稳定功能/资产 ID 和项目内相对链接；常用当前规格路径保持稳定，浏览入口通过源文件路径生成。已有模板参考 [产品规格模板](../../dev-product/assets/templates/feature-spec.md)和[视觉规格模板](../../dev-visual/assets/templates/design-spec.md)。

## Agent 文档控制

持久文档回答项目行为、技术约束、操作方法、工作范围、重要决定或如何接手；本机记录回答本次执行发生了什么。创建前先判用途和生命周期，不以目录存在、模板可用、Agent 数量或执行次数决定产文档。

| 时点 | 对 Agent 的约束 |
| --- | --- |
| 任务开始 | 读取现行索引与有关基线，确定主责、权威位置和写入范围；优先更新已有资料，不另建平行规格/账本 |
| 每次运行/Review | 原始日志、单次报告、截图、探针和逐文件指纹默认写忽略目录；执行事实照常记录，不能因不提交而省略验证或宣称通过 |
| 创建持久文件 | 明确它支持哪项维护、验证、决定或交接；与已有内容重复则合并/引用，没有持久用途则留在本机。不要求所有职责产出一套文件 |
| 多 Agent 协作 | 明确一个权威写入者；子 Agent 默认返回结论、候选版本、问题和本机证据入口，由主 Agent 核验后更新对应资产/交接，不按 Agent 或每轮 Review 建持久目录 |
| 中断/换人/跨机器 | 提炼到 handoff/result 或已有交接入口：可取得的候选与差异、有效输入、完成/未完成、问题、复跑命令、限制、下一步。不能用私有路径或整套日志代替交接 |
| 阶段完成/交付 | 更新当前结果与相关长期资产，保留重要决定、确认及未关闭项；原始证据仍放 .dev，必须转交时单独提供，交接文档注明用途、候选版本与取得方式 |
| 提交前 | 检查真实待提交文件及忽略规则；不得批量暂存整个工作目录而带入 runs/缓存/私有资料，文档索引不得依赖私有日志作为唯一恢复入口 |
| 整理与归档 | 先提炼结论和承接，再迁移过程资料并修正引用；不用 archive 整套复制运行历史，不以标为 archived/evidence 绕过提交边界 |

专业 Skill 规定内容和质量，不能把本机过程默认升级为仓库资产。用户或项目已有明确的 CI/审计/制品要求时按实际范围保留，不自行引入审计要求、专用存储或固定留存周期。持久资产的历史通过 Git 追溯；阶段结果更新时保留版本和范围，不让新结论冒充旧候选的验证。

## 专业规格的权威位置

产品规格的内容要求见[产品规格协议](../../dev-product/references/specification-contract.md)，视觉规格见[视觉规格协议](../../dev-visual/references/specification-contract.md)。共享目录协议只规定成果位置、索引、状态和交接关系，不重复定义专业内容。架构、研发、测试与运维同样使用各自专业资产协议；同一规则只有一个现行权威来源，其他职责以版本和编号引用。

## 状态、版本与归档

Markdown/MDX 推荐 YAML 元信息：`id`、`title`、`status`、`version`、`owner`、`related`；`iteration` 只对相关文档适用；被替换资产增加 `supersededBy`（现行文件的项目相对路径）。其他格式由索引中的记录或相邻说明承载同样的信息。状态采用 `candidate`、`current`、`needs-review`、`superseded`、`archived`，设计状态与实现/生产验收状态分别记录。

手动整理、已授权定时检查、迭代总结和逻辑归档采用[文档整理与归档](document-archive.md)。工作结束与整理状态分开记录；归档不自动使其中有效规格失效，也不自动删除历史。

测试结果与必要证据由测试报告维护；其他过程资料不要求额外创建文档或归档。源码、固定测试输入和复用脚本保留在实际工程位置。

- 迭代进行中维护本轮有效版本，Git 保存普通修订历史，不为每次改字或复验复制整套文档。
- 已完成或取消的迭代默认保持原目录，在索引记录结束状态、版本、总结与遗留承接，满足归档条件后转入项目历史列表。物理迁移仅按项目已有规则或用户明确要求执行，并核验引用。后续独立工作建新迭代并引用旧来源，补充旧记录只增加更正/证据说明，不改写当时的验收结论。
- 放弃的候选保留必要取舍和来源。需要保留完整方案或里程碑时进入本迭代的 `archive/<阶段>/<资产ID>/`（长期资产自身的完整替换快照仍可放在其 `archive/` 下），标明原路径、版本、归档原因及替代入口。
- 被替换文件标为 `superseded`/`archived`，索引明确指向现行资产。移动文件时修正相对资源链接和受影响反向引用；历史证据绑定当时版本，不改写为本轮验证。
- 原型普通迭代由 Git 追溯；需要并存的方案保留各自目录和 ID，索引标明当前选择。大二进制按项目实际 Git/LFS/资产存储约定维护。
- 需求、组件或环境变化使证据失效时标记相关内容 `needs-review`；更新日期不能替代复验。归档预览仍显示其历史状态，不能因可打开就当作当前规范。

## 文档格式与预览地址

业务规则优先使用 Agent 可直接读取的 Markdown、结构化数据或源码；可交互说明采用 MDX/React 或原型 HTML。已有 Office、PDF 和设计文件保留原件，建立有来源、同版本的可读说明或预览导出。渲染衍生产物不产生第二套权威规则。

按[文档预览指南](document-preview.md)实际启动 Vite。运行记录保存当前 origin、项目、允许目录与进程，长期索引保存源路径、启动命令和场景路由；本机端口不作为永久链接。Agent 通过 `preview.mjs url --project <项目> --file <项目相对文件>` 核验服务与文件并取得实际地址。

确定性地址规则为 `实际 origin + /view/ + 逐段 URL 编码的项目相对路径`。原文件入口为 `/__docs/file/` 加同样编码路径。Markdown 相对链接和资源链接在预览中解析；可操作 HTML 的状态参数来自其实际场景定义。文件移动或服务重启后重新生成并验证地址，不凭历史端口猜测服务已启动。
