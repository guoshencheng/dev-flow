# 分支、worktree、验证与合并建议

本指南补充[任务路由](task-routing.md)的工程执行选择，采用项目已有分支、CI、保护规则和交付约定。以下是默认建议，不增加设计、用例或实施计划的人工审批；用户当前指令和宿主约束优先。非 Git 项目使用明确的工作副本和候选指纹，不为流程强行初始化 Git。

## 开始：先确定基线，再选择工作位置

只读调查不需要新分支。开始写设计、原型、测试或代码前，核对项目指引、当前分支/提交、未提交内容、已有 worktree、目标合并分支和已有任务/PR；记录任务开始基线与本次写入范围。需要远端最新基线时先 fetch 并核对差异，不默认把当前分支或远端默认分支当作正确起点。

| 情况 | 建议选择 |
| --- | --- |
| 已有属于本任务的分支、PR 或 worktree | 核对基线与内容后继续使用，测试反馈留在原任务分支 |
| 独立 bugfix 或正常需求 | 在首次写入前建立任务分支；设计与实现通常在同一分支推进，不必按职责分六条分支 |
| 工作区干净、单任务顺序执行 | 原 checkout 加任务分支即可，不必创建 worktree |
| 当前 checkout 有其他任务修改，或需要同时保留正在运行的环境 | 优先另建 worktree，保留原 checkout 的修改和服务 |
| 多个可独立实施的子任务、隔离旧版/新版回归、独立候选验收 | 根据实际并发与环境需要使用 worktree；只读评审通常不需另建 |
| 紧急修复发布版本 | 从实际受影响发布提交/维护分支起步；修复后按项目策略同步到主开发线并验证，不能只修错版本 |
| 用户明确要求在当前分支修改或直接交付 | 在授权范围内沿用，仍核对他人修改、验证和最终目标 |

分支名称优先遵循项目与当前宿主约定；Codex 无既有约定时采用 `codex/<任务简名>`，例如 `codex/fix-save-refresh`；其他宿主按其约定选择，不将 Codex 前缀强制用于所有宿主。一个迭代可以包含多条任务分支，但每条都有确定的基线、所有者与合并目标；不要求一个微小文档修订也新建迭代。

新 worktree 默认只含所选 Git 基线，不自动包含当前 checkout 的未提交内容。确需带入相关修改时先明确文件、来源与归属，通过可追溯提交、补丁或宿主支持的方式转移并检查差异；不默认 stash、reset 或覆盖原工程。宿主提供受管 worktree 工具时优先使用，并复用属于本任务的有效 worktree。

worktree 隔离文件，不自动隔离数据库、端口、缓存、云环境或外部副作用。运行前核对工作目录、依赖/配置来源和数据；并行服务分配端口及必要测试数据，避免多个执行者操作同一共享目标。真实密钥保持项目已有安全入口，不复制到版本化成果。

## 过程中：按阶段验证并保存候选

| 时点 | 应验证什么 |
| --- | --- |
| 调查/设计阶段 | 相关现状与可行性；设计原型由产品/视觉实际走查，不登记实现验收 |
| bugfix 修改前 | 取得原问题失败证据；适合自动化时补最小回归，区分目标失败与环境失败 |
| 内部切片完成 | 研发自测当前行为和相关静态/类型/契约，继续集成与实现；不逐片启动独立正式 Review/验收 |
| 完整候选就绪 | 按共同交接条件核验全部范围、必要消费者及真实核心链路，集中实现 Review 与正式验收 |
| 修复测试反馈后 | 用原预期实际复验原问题与受影响回归；源码变化使相关旧证据失效 |
| 子任务集成、冲突解决或基线更新后 | 检查实际集成差异，重跑受影响行为/契约/构建与必要核心链路；单个分支通过不等于组合通过 |
| 合并前 | 对最终候选完成范围内必需检查、实际变更 AI Review 和阻断项关闭；CI 对应当前候选，不沿用更早提交结果 |
| 合并/交付后 | 核对目标分支实际结果、CI 和产物身份；按交付约定验证实际安装/运行/部署环境的核心任务 |

检查由对象和风险决定：文档采用内容/引用检查，局部实现采用针对性验证，完整功能采用约定链路和相关约束；不无差别跑所有检查或强制使用浏览器。相同内容与环境已有有效证据时可复用；冲突、配置、依赖或目标环境变化后定向重验。合并后即使文件内容等价，也要核对目标提交/产物关系；部署要求成立时在目标环境重新取证。

形成有意义的切片后建议提交，便于交接、回退和评审；小任务可以一个提交。提交前检查 diff 与暂存范围，保留无关修改，记录尚未通过的检查；未完成候选可用明确标注的 WIP 提交/草稿 PR 保存，不因此宣称可合并。交接优先使用确定提交；未提交候选必须附相关差异/指纹，验证期间明确写入者。

## 集成与合并：先验证实际组合，再更新目标

1. **准备评审候选**：列明原始要求、有效设计/用例、任务开始基线、基线至候选的完整差异、相关未提交内容、实际检查与缺口。默认通过 PR 展示；仅需要本地成果或项目已有直接集成方式时使用对应记录，不为小任务强制建 PR。
2. **同步与集成**：核对目标分支当前状态。个人未共享的任务分支可按项目规则 rebase；多人共享分支优先采用不改写他人历史的 merge。子任务按依赖顺序集成到主任务分支，处理冲突后重新检查行为和契约。远端变化时重新核对，不用强推覆盖目标。
3. **完成合并条件**：有效确认已具备；当前候选的必需验证/CI、实际变更 AI Review 和相关架构检查通过；阻断项关闭，未覆盖项与交付安排清楚。运维/测试针对实际环境的后续步骤有明确入口；合并前能执行的必需验收先完成，必须部署后执行的检查留在交付阶段。技术方案/计划已 Review 不代替最终实现检查。
4. **选择合并方式并执行**：遵循项目已有策略。无既定策略时，小型单目标任务建议 squash；需要保留有意义的切片/多分支历史时建议 merge；只需前移且满足项目线性历史策略时可 fast-forward。保护规则和 required checks 始终适用。推送、合并及其 CI 发布副作用按用户已有授权执行；缺少授权时先完成可审阅候选，再只请求缺失的动作决定，不增加例行审批。
5. **核对结果与清理**：确认目标实际包含预期变化、提交/树/产物映射与 CI 结果，完成约定交付验证。失败继续修复，必要回退按项目策略处理；合并成功不等于已部署或交付完成。

worktree 只有在成果已集成或已按约定保存、没有未交接修改/未推送成果、相关服务已停止、必要证据与忽略文件已保留后才清理。受管 worktree 使用宿主归档入口；本地分支确认无独有待保留成果后删除，远端分支沿用项目策略。取消任务也先保存需要保留的内容，不强制删除未知归属目录。

## 记录位置

在迭代索引/实施计划/交接的现有位置记录：任务基线、目标分支、任务分支与工作目录、隔离选择及原因、写入者、候选版本、验证阶段与证据、合并方式/结果、实际交付及清理状态。小任务合并记录，不新增独立 Git 台账。执行者安排见[subagent 使用建议](subagent-guidance.md)。
