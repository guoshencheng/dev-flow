# 任务路由：bugfix 与正常需求

本指南规定未来业务项目中如何选择和推进流程。共同确认规则见[执行协议](execution-contract.md)，阶段产物按[迭代目录协议](design-document-contract.md)保存。本插件不要求 setup；专业职责由主 Agent 或已获准委派的可用子 Agent 读取对应 Skill 承担。

## 先判断任务性质

- **Bugfix**：恢复已明确的业务行为、契约或运行预期，不改变功能含义。入口请求本身可以提供有效预期，但需要核对项目事实与既有决定。
- **正常需求**：新增或改变用户行为、业务规则、界面、接口能力或交付结果，采用标准流程；不涉及 UI 的任务裁剪产品表达与视觉阶段。
- **系统变更**：涉及数据迁移、公共接口、权限或兼容性的重要变化，在对应流程中补充架构取舍、影响、迁移/恢复与验证。
- **线上故障**：先按已授权范围恢复并核验实际业务，再开展根因修复与回归，保留事故与修复的关系。

名称不决定路径。标为 bug 的工作如果实际需要改变规则或重要架构取舍，转入受影响部分的设计和确认；小需求已有完整有效设计与用例时可以复用，不重新制造审批。

## Bugfix：复现 → 诊断 → 修复 → 复验 → 交付

1. **恢复上下文并登记迭代**：读取项目索引、有关规格/契约、代码与已有用例。建立或复用 `iterations/<迭代ID>/index.md`，记录问题、受影响范围、有效预期、候选版本与环境。同一轮测试反馈的修复留在当前迭代，独立修复任务可以新建迭代。
2. **复现与预期核对**：研发/测试保留步骤、预期/实际及证据；补充最小失败用例或其他能判断原问题的检查。无法复现时记录事实和限制，继续调查，不宣称修好。预期存在冲突时由产品或契约主责澄清；产品/视觉参与体验问题，架构参与域/依赖/数据问题，运维参与环境问题。
3. **根因与修复方案**：依据证据定位实现、测试执行或环境原因，选择范围内的修复。研发写简短实施计划并由 AI 复核预期、影响、相关约束、回归与交付方法；小修复可合并在迭代索引或缺陷记录中，不强制单独技术方案与整套阶段文档。
4. **实现与自测**：修复根因，运行原问题和受影响回归，检查有关架构契约。普通内部实现调整自主推进；改变已确认行为、重要架构取舍或验收含义时，只确认受影响部分，必要时升级为标准/系统变更路径。
5. **测试复验与持续对焦**：验收职责针对修复候选实际复验原场景和必要回归，适用时验证真实 API/数据、界面及端到端结果；失败带版本和证据反馈研发，继续诊断修复。执行者相同时如实记录自测/复验，不冒充独立验收。不通过降低预期或删用例关闭问题。
6. **交付和沉淀**：按约定核验可启动源码、实际产物或目标部署及核心行为，登记证据、未覆盖与遗留项。更新相关回归、诊断、运行方法或模块地图；局部架构复盘只覆盖受影响部分。

**默认无需重新确认完整产品/UI/架构或已有验收预期，也不新增人工计划审批。** 新的测试覆盖在既有预期内由 AI Review；确实需要人决定的新预期、重大取舍和额外外部动作按执行协议处理。

普通修复的最小记录是：迭代目标/范围、问题与有效预期、根因、修复计划/AI 复核、变更候选、复验/回归结果、交付方式及必要资产变化。复杂时再拆到 `engineering/`、`acceptance/`、`architecture/` 或 `operations/`。

## 正常需求：设计确认 → 技术方案 → 用例确认 → 实施 → 验收交付

| 阶段 | 主责与具体结果 | Review 与确认 | 本迭代默认位置 |
| --- | --- | --- | --- |
| 目标与范围 | 主 Agent/产品明确用户任务、交付、边界、输入基线及未知 | 需要人决定的取舍具体澄清，已有决定复用 | `index.md` |
| 产品/交互 | 产品细化流程、原型、限制、透出、业务规则与 RULE/AC | 产品走查原型；用户确认相关设计 | `product/spec.md`、`product/prototypes/` |
| UI | 视觉细化布局、组件、Tokens、响应与状态，检查实际呈现 | 用户确认相关 UI，可与产品确认合并 | `visual/design.md` |
| 架构 | 架构依整洁架构拆业务域/模块、依赖、API/数据/权限和运行约束 | 用户确认重要取舍；已有约束直接复用 | `architecture/design.md` |
| 端到端技术方案 | 研发列页面/入口、功能、OUT、完整链路与技术产物 | 产品符合性及相关 UI/架构 AI Review，通过后交测试；不增加人工审批 | `engineering/technical-solution.md` |
| 测试策略与用例 | 测试综合原产品及经 Review 方案，设计正常/边界/拒绝/异常/恢复/交付与相关架构检查 | 用例先 AI Review，再由用户确认验收预期和覆盖 | `acceptance/strategy.md`、`acceptance/cases.md` |
| 实施计划 | 研发拆可运行切片、依赖、变更位置、验证与启动交付 | 一次实际 AI 复核；通过后自主实现，不做人工计划 Review | `engineering/implementation-plan.md` |
| 研发测试对焦 | 研发提交可运行候选；测试验证界面/API/真实数据/E2E，反馈缺陷并复验，视觉核验相关呈现 | 内部修复自主推进；改变确认基线才确认受影响部分 | `engineering/handoff.md`、`acceptance/runs/`、`acceptance/defects/` |
| 交付与复盘 | 运维核验启动/产物/部署；测试验收约定链路；架构复盘实际代码业务与约束，更新现状 | 必需条件实际通过、阻断问题关闭、约定交付成立；可选改进入待办 | `operations/delivery.md`、`architecture/review.md` |

正式实现依赖有效的设计与用例确认及计划 AI 复核；等待确认时继续独立调查、候选准备和已有授权工作。原型可操作不等于实现验收，开发服务可访问不等于已部署。完整依赖、确认来源和自主调整边界以[执行协议](execution-contract.md)为准。

## 工程执行与执行者选择

具体采用[分支/worktree、验证与合并建议](git-and-worktree.md)和[subagent 使用建议](subagent-guidance.md)。两类流程都在首次写入前明确基线、任务分支/目录和写入范围；测试反馈通常留在当前任务分支，独立修复通常另建分支。单任务顺序执行可沿用原 checkout，需要隔离或并行再使用 worktree。

bugfix 默认主 Agent 完成，必要时加入独立调查/Review/复验；正常需求按稳定契约并行可分离切片，并在关键评审和验收节点按需使用独立执行者。遵守当前委派权限，不按职责数量固定启动子 Agent。集成/冲突/基线变化后定向重验，当前候选符合合并条件且动作已获授权再更新目标分支，随后完成约定交付核验。

## 裁剪与结束

修复、需求和系统变更都按实际风险选测试层级，不强制所有验证都用浏览器。已有设计、技术方案、用例或计划有效时引用并核对本次差异；不涉及的阶段标不适用，不生成空文档。局部快速路径与标准路径的选择原因记录在迭代索引。

完成结论针对当前候选与约定交付，说明已经执行的检查及未覆盖项；必要资产更新完成后登记本轮结束。目录、Skills 或角色名称的存在都不能代替真实工作与证据。
