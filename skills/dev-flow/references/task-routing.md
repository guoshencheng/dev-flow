# 任务路由：从最终目标到交付

按对象、行为/契约变化、风险和当前阶段选择流程；确认、Review 和完成依赖以[执行协议](execution-contract.md)为准。开始即按[进度管理](progress-management.md)建立完整阶段计划，显示未开展的后续工作、当前目标与下一步。标准跨职责任务默认由实际可用且允许的 Harness subagent 执行专业工作，主 Agent 协调与集成。

用户要求“开始收尾”时采用[迭代收尾](document-archive.md#一条指令收尾当前迭代)，默认包含[代码收尾](git-and-worktree.md#代码收尾)；只整理文档时按明确范围裁剪，不重启功能流程。

## 判断任务性质和有效起点

- **正常需求**：新增/改变行为、规则、交互、接口能力或交付结果，采用相关标准阶段；无 UI 的功能裁剪 UI 表达。
- **Bugfix**：恢复有效预期；先复现与诊断，复用设计和决定，形成修复候选后补齐/复用验收用例并复验，不重做全套设计。
- **系统变更**：在适用路径中补充接口/数据/权限、消费者、迁移、兼容与恢复的取舍及验证。
- **运行故障**：在授权内优先恢复并核验服务，再根因修复、回归、交付和复盘。
- **探索/文档**：明确要消除的问题或文档结果，专业调查、综合方案、独立 Review 和适用内容/引用或实验验证，不虚构生产验收。

先看变化含义，再看规模与可逆性。标为 bug 或“既有功能扩展”不代表能裁掉新行为设计；已有完整有效设计则引用并核对差异。混合请求逐范围说明路径和依赖，共同契约与整体集成仍要核验。

## 快速路径的边界与实施资格

只有目标清楚、局部可逆、已有明确有效预期/设计、无未定行为/交互/重要契约且有验证方式时采用快速路径。说明具体基线、版本、决定、差异和裁剪依据，不只写“很小”。新增动画/参数交互/恢复结果仍须定清受影响行为。

首次进入本次正式实施前，按[范围授权](execution-contract.md#首次实施的人工同意)展示范围、结果、验证与交付，取得明确同意；同范围已有授权持续有效，快速路径不重复询问也不自动豁免。标准任务可与设计确认明确合并授权，技术设计/计划和实现后正式用例不增加例行人工技术审批。

## 正常需求：设计与技术反馈 → 计划 → 实现 → 用例/验收及交付 → 收尾

### 1. 完整进度与产品/UI 候选

主 Agent 确定最终目标、交付范围、起点与未知，列出到实际交付和收尾的全部阶段。产品/视觉形成适用候选，研发读取真实代码/技术基线比较功能入口、交互形式、可复用性与维护成本，架构核对边界与约束。对多余状态说明触发和用户价值，必要等待、错误、权限、数据保留/恢复反馈保持完整。产品/UI 回应并修订；有证据的取舍提交用户，不能任何一方单方改业务。

### 2. 研发统一设计与独立 Review

研发编写 `engineering/design.md`，合并本轮架构与实现方案；架构独立 Review 技术，产品/视觉核对目标、业务覆盖和相关 UI。重要发现与复核在 `engineering/review.md`，主设计引用有效版本和结论。用户确认受影响规则、边界、可观察完成标准及重要取舍，已有决定直接复用。项目现行架构基线保持原权威位置，无需先写平行同义方案。

### 3. 实施计划、复核与有效授权

研发独立编写 `engineering/implementation-plan.md`，说明依赖、写入者、实施步骤、集成、自测、回归与启动/交付。架构/相关研发独立 AI 复核，阻断项修订复核。确认设计层预期、Review 和明确范围实施授权有效后实施；完整正式 TC 的维护、Review 或人工确认不是前置。

### 4. 连续实现、集成与自测

专业执行者在稳定契约与唯一写入范围内实施，主 Agent 持续集成并更新进度。研发局部测试、缺陷复现、契约检查和必要回归随实现开展，不逐切片设置正式验收门槛。改变已确认行为/契约时先走[变更闸门](execution-contract.md#实施中的需求变更闸门)，更新设计层预期与受影响决定；已存在 TC 同步，未形成正式 TC 在完整候选后维护。

### 5. 完整候选、实现 Review 和正式用例维护

满足[研发交接条件](execution-contract.md#完整候选交接条件)后，独立架构 Review 从开始基线到最终候选的全部变化；测试依据原需求、有效设计与实际入口维护 `acceptance/strategy.md`、`cases.md`、`technical-checks.md`，独立 AI Review 覆盖、预期和执行可行性。产品/UI 核对真实行为和呈现。用例和代码可以同候选并行 Review，代码不能成为正确预期来源。

### 6. 验收执行与交付核验

用例 Review 通过后在固定候选执行适用界面/API/数据/真实 E2E；运维提供并核验实际启动、产物或已授权目标部署，测试执行交付相关场景。已确认预期内细化不例行等待 TC 人工审批，歧义/业务变化只确认受影响决定。问题带版本和证据反馈，研发关联修复，检查者定向复评/复验及必要回归；最后核验整体集成和交付。

### 7. 架构技术收尾与整体结束

架构在 `architecture/closeout.md` 核对实际设计差异、完整 Review、验收/交付结果、长期地图/契约及遗留；主设计关联独立 Review、计划、收尾版本与结论。主 Agent 按项目约定保存成果、总结并满足条件后归档。任何本轮必需项缺失保持未完成，不能因实现、单个派发或方案阶段完成就结束整体任务。

## Bugfix：复现 → 诊断/计划 → 修复自测 → 验收复验/交付 → 定向收尾

恢复有效预期与候选，同条件复现并保留失败证据；研发明确根因、影响、简短计划及必要复核，核对有效实施授权后修复。一个明确写入者负责根因修改；跨边界或关键风险分派独立调查/Review。修复候选形成后测试补齐或复用原场景/必要回归用例，经相应覆盖 Review 执行复验和约定交付核验，架构按影响更新实际地图/约束。反复失败继续诊断，不能降低预期。

小修复可在既有任务或缺陷记录中保留目标、根因、计划/Review、候选、复验与交付，不强制四篇空文档。改变业务预期或重要契约时回到受影响设计与决定，按需升级路径。

## 系统变更、故障和探索

系统变更按风险补充专题与早期可行性/迁移/恢复实验，不把标准正式验收前移成逐片审批。运行故障只有一个发布/迁移/共享数据操作负责人，独立取证可并行；记录服务恢复与最终根因修复的不同状态。探索和文档任务按成果做内容/引用或实验验证，整体计划保留接下来要实现/交付的工作；仅当用户目标本身止于研究或文档时，才把该成果视为整体终点。

## 工程执行与裁剪

按[Git/worktree](git-and-worktree.md)确定基线、隔离和集成；按[原生 subagent](subagent-guidance.md)选择实际执行者。标准跨职责阶段默认委派，大任务不委派说明原因；简单局部改动按收益裁剪。独立评审不检查自己主笔的对象并冒称独立。共享文件、端口/数据和外部操作分别指定负责人。

已有设计、用例、回归、实际 Review 或运行证据有效时核实差异后复用；无关阶段标不适用，不生成空成果。过程和完成事实更新到唯一 Todo/Progress/索引，具体专业内容仍在其原来源；命令成功、目录或角色名存在不能代替真实结果。
