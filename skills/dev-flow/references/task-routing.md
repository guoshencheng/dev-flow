# 任务路由：从最终目标到交付

按对象、行为/契约变化、风险和当前阶段选择路径；授权、Review 与完成依赖见[执行协议](execution-contract.md)。开始即按[总体进度](progress-management.md)列出直到最终目标的全部阶段。具体 Git、派发和文档操作分别调用[git-workflow](../../git-workflow/SKILL.md)、[subagent-coordination](../../subagent-coordination/SKILL.md)、[document-management](../../document-management/SKILL.md)。

各路径均先按 [Skill 入口](../SKILL.md#从目标推进到完成)创建或恢复独立 Progress，展示整体路径并取得[流程确认](execution-contract.md#流程开始前的用户确认)，有效确认直接复用。只读了解与流程草案可先做。未启动 Dev Flow 的查询、解释或独立局部操作不因此新建完整迭代；一旦明确宣布启动 Dev Flow，不以“轻量调研”省略文档和确认。咨询转入设计/研发且没有有效确认时，首条进度说明明确进入待流程确认阶段，再完成文档、展示和确认。

用户要求“开始收尾”时按[收尾门槛](closeout.md)调用 [iteration-closeout](../../iteration-closeout/SKILL.md)，明确包含已有资料盘点和项目级通用文档实际回写。沿用本轮有效流程确认；没有有效确认则先展示剩余路径确认。明确仅整理文档则按范围裁剪，不重新进入功能设计与实现。

## 判断任务性质和有效起点

- **正常需求**：新增或改变用户行为、规则、交互、接口能力或交付结果，采用相关标准阶段；无 UI 时裁剪 UI 成果。
- **Bugfix**：恢复有效预期；复现与诊断后形成修复候选，执行相应 Review、复验和交付，不重做未受影响设计。
- **系统变更**：在适用路径中补接口/数据/权限、消费者、兼容、迁移与恢复决定及验证。
- **运行故障**：在授权内先恢复并核验服务，再处理根因、回归、交付与复盘；恢复服务与最终修复分别记录。
- **探索或文档**：明确问题和成果，用实际内容/引用或实验验证；仅当用户目标止于研究/文档时以其为整体终点。

先判断变化含义，再看规模和可逆性。“Bug”“既有功能扩展”“可回退”都不能代替对新行为、UI 方案或重要契约的决定。涉及 UI 先按[UI 确认规则](execution-contract.md#ui-方案展示与用户确认)区分新方案、恢复已确认设计、明确指定调整、规范内实现细节及无 UI；一般功能授权不自动覆盖后来形成的视觉取舍。混合请求逐范围说明路径、有效基线和依赖，最终仍核对共同契约与整体集成。

## 快速路径的边界与实施资格

仅当目标清楚、局部可逆、已有明确有效预期/设计、无未决行为/交互/重要契约且有验证方式时采用。记录具体基线、版本、决定、差异及裁剪依据。新增动画、参数交互或恢复语义仍须先定清受影响行为。

快速路径同样在首次正式实现前展示范围、结果、验证和交付并取得[明确实施同意](execution-contract.md#首次实施的人工同意)；同范围已有授权直接复用。新增或改变 UI 方案（含纯视觉变化）即使局部可逆，也须先展示候选并取得用户确认；仅恢复有效设计、明确指令、规范内细节或明确委托按来源复用。标准路径可与设计确认明确合并授权。技术设计、计划和实现后正式用例不增加例行人工审批。

## 正常需求的阶段依赖

1. **整体流程确认与产品/UI 候选**：主 Agent 在独立 Progress 明确最终目标、未知和完整阶段，展示入口和路径并取得流程确认；随后产品/视觉形成适用候选，研发依据真实代码比较入口、形式、状态与复用成本，架构按影响核对边界。产品/UI 回应并修订，重要分歧由用户决定。
2. **统一研发设计与独立 Review**：研发主笔本轮架构和实现方案；架构独立核对技术，产品/视觉核对原要求与呈现。重要发现经修订、定向复核；业务规则、可观察成功/拒绝/恢复及重要取舍在受影响实现前固定。
3. **计划复核与有效授权**：研发形成独立实施计划，由未主笔者 AI 复核。设计层预期、相关 Review 和本次范围授权有效后进入正式实现；主 Agent 核对 UI 候选的实际展示/用户答复或有效复用、委托，缺失或失效时受影响部分待确认。完整正式 TC 的维护及 Review 不是前置。
4. **连续实现、集成和自测**：研发按稳定契约推进，局部测试与必要回归随实现开展；内部切片无逐片正式验收门槛。行为/契约/交付变化走[变更闸门](execution-contract.md#实施中的需求变更闸门)。
5. **完整候选、实现 Review 和正式用例**：满足[候选交接条件](execution-contract.md#完整候选交接条件)后，独立评审完整变更；测试从原要求和有效设计形成正式用例，独立 AI Review 预期、覆盖及可执行性。两者可对同一固定候选并行，代码不是正确预期来源。
6. **验收、交付与修复**：执行适用界面、API、数据、真实主链路与约定交付检查；运维核验实际产物/运行版本。问题关联修复、定向复评复验及受影响回归，最后核对整体结果。
7. **技术收尾与结束**：架构依据最终源码、Review 和验收/交付事实完成技术收尾；主 Agent 通过 [iteration-closeout](../../iteration-closeout/SKILL.md)完成已有资料盘点、长期文档回写和保存，按[收尾门槛](closeout.md)判断结束。必需结果缺失保持未完成。

## Bugfix 与其他路径的裁剪

Bugfix 先恢复有效预期和复现证据，诊断根因、影响及所需计划/Review，在有效授权范围内修复并自测。形成完整修复候选后，测试补齐或复用原场景及必要回归用例，执行相应覆盖 Review、复验和约定交付；架构按影响核对现状与约束。小修复可以在既有记录中保留必要依据，不强制成套空文档。改变业务预期或重要契约时回到受影响设计和决定。

系统变更增加适用的兼容、数据迁移、消费者及恢复实验和验证；入口及依赖具备时可尽早执行小范围真实冒烟，它是集成自测而非需关键风险阻断才能提前的专项。其他专项仅在关键风险阻断后续时提前进行，不把正式验收变成逐片审批。故障处理中共享数据、发布目标只有一个操作负责人，独立取证可并行。探索任务只报告实际消除的不确定性和后续选择，不虚构生产验收。

## 执行裁剪与证据复用

按阶段和对象选择实际专业职责；标准跨职责任务默认用实际可用且允许的专业执行者，作者与独立评审分离。无法派发时如实记录，不用角色名称代替执行事实。已有设计、用例、Review、回归和交付证据在版本与影响仍有效时复用；无关阶段标明不适用。命令成功、目录存在或阶段成果不能代替当前整体交付。
