# 文档整理、资产检查、迭代总结与归档

适用于用户要求的项目资产检查、文档整理、迭代总结，以及已授权的定时检查。目录与权威来源遵守[共同文档协议](design-document-contract.md)，专业内容由对应职责维护。整理历史不自动扩大为工程修复、重新发布或删除资料。

## 触发与职责

手动触发时明确项目根路径、检查/整理范围和目标；可检查当前架构与测试资产、整理单个迭代、若干历史迭代或指定长期资产。正常交付结束时在原迭代索引完成相关总结即可，不强制另建整理迭代。

定时检查只有在用户授权创建调度后启用；本指南不自行创建自动任务。保存项目、范围、频率和允许写入的动作。只读检查可以报告候选问题；已授权整理时可执行状态明确的资产同步和逻辑归档。状态矛盾、关键决定缺失或无法核验来源时保留原状态，列出待决事项；长期无活动不能自动认定完成或取消。无变化或无可行动问题时保持安静，只在有意义的变化、失败或需要用户决定时通知。

主 Agent 负责范围、归档条件、索引与总结集成；产品、视觉、架构、研发、验收和运维分别核对本领域权威来源、资产变化与未完成项。主 Agent 可以顺序承担所需职责，不要求派发六个 Agent；同一文件只有一个写入者。

维护检查不以“需求结束”作为唯一触发点。它可以在需求进行中、重要版本变更后、发布前、用户指定的维护窗口手动触发，也可以由用户另行授权定期触发。定期检查的项目、范围、频率、允许写入的动作和通知条件必须保存；没有授权时只提供检查建议或只读结果，不自行创建调度或写入长期资产。

实施中的需求变更仍按[需求变更闸门](execution-contract.md#实施中的需求变更闸门)即时处理，不能等下一次维护检查；维护检查负责发现遗漏、核对长期基线、补齐跨迭代资产和整理历史，两者互不替代。

## 架构与测试资产联合检查

维护检查至少以同一源码/候选版本和项目索引为入口，联合核对架构现状与测试回归资产。检查的目标是把已验证且仍有效的内容同步到当前基线，不是把最新内容移入 `archive/`。

| 检查对象 | 必查内容 | 检查后的写回与状态 |
| --- | --- | --- |
| 架构基线 | 系统/模块地图、业务域与依赖、公开接口、数据不变量、权限/失败恢复、技术基线与本次实际代码是否一致；目标设计是否仍未实现 | 更新项目级 `architecture/` 当前入口、模块地图、契约/决策、复盘或债务；事实、目标、`needs-review` 与 `superseded` 分开记录 |
| 测试基线 | 稳定 TC、用户预期与 RULE/AC/UI/ARC/OUT/链路的关系；本次新增行为、边界/拒绝/恢复、真实 E2E、自动化、数据、历史缺陷和回归覆盖是否齐全 | 将已验证且跨迭代有效的用例/检查和入口同步到项目级 `acceptance/` 回归与自动化索引；新增、待验证、失效和被替代用例保留来源及状态，不删除稳定编号 |
| 架构—测试关系 | ARC/接口/数据变化是否影响 TC、消费者、夹具、环境和实际证据；TC 预期是否仍忠于当前架构和产品规则 | 在迭代索引、技术拆解、架构复盘或现有 tracker 中记录影响、复用、补充、未覆盖项与责任；需要行为确认时只请求受影响范围 |

联合检查可以是只读盘点；是否执行局部回归或真实 E2E 由风险、当前候选和授权决定，不因整理任务默认重跑全部历史测试。检查至少形成可定位的检查记录，包含触发来源、范围、代码/资产版本、架构变化、用例新增/修订/失效情况、实际证据、长期资产写回、归档状态和遗留承接。活动迭代写入其 `index.md` 的检查/总结章节，复杂时拆出同目录 `summary.md`；独立维护检查写入项目索引的维护章节或 `records/reviews/<记录ID>.md`，不另建平行账本。

## 归档条件与状态

归档前核对：

- 迭代已完成、取消或被替代，有明确结束原因和结果来源；实施中、待验收或结束事实不明的迭代保持活动或待整理。
- 实际交付、验证范围、未执行项与证据版本已记录。取消的迭代无需补出不存在的验收或交付。
- 已生效变化已同步到长期资产或现行来源索引；无需更新时说明仅复用。候选与未实施目标不能成为当前事实。
- 遗留项已关闭或有可定位的承接任务、主责和状态。归档不意味着全部问题解决，也不自动创建未授权的新任务。
- 总结、权威来源、必要证据及相关链接可访问；无法访问的资料保留明确缺口，不宣称满足归档条件。

迭代工作状态（如进行中、完成、取消、被替代）与整理状态（待整理、待决、已归档）分开记录。文档的 `current`、`superseded` 等有效性以及确认、验收、部署结论也独立记录。整个迭代归档不能批量将其中仍有效的规格标为 `archived`。

## 执行步骤

1. **盘点**：从项目和专业索引定位范围内迭代、现行规格、重要决定、事件及证据；核对真实状态、版本、重复来源、断链和未承接事项。已有结论有有效来源时直接复用，不为整理重跑全部历史测试。
2. **分流**：逐项判断当前有效事实、待核验内容、历史过程、被替代候选和临时数据。冲突回到主责及原始来源核查；不能按日期较新直接覆盖有效规则。
3. **联合检查**：按上表核对架构基线、测试回归基线及两者关系；先确定哪些内容仍是 `current`，哪些需要补证、替代或承接。
4. **沉淀**：定向更新规则、设计系统、系统/代码地图、回归与 runbook。可以保留迭代内有效规格，由专业索引引用；规则散落多轮且难以确定现状时整合为稳定规格，保留来源与替代范围。
5. **总结**：在迭代索引的结束章节写入下述内容。复杂迭代可拆为同目录 `summary.md` 并由索引链接；总结引用原证据，不复制整套方案和报告。
6. **归档**：满足条件后登记归档日期、整理者、工作结束状态、来源版本和总结入口；项目索引将其归入历史列表。尚未满足时登记具体缺口，不提前标记已归档。
7. **核验与交接**：检查变更差异、现行入口、相对链接、资源和承接关系。报告整理/归档范围、架构与测试长期资产变化、保留的有效历史来源与待决事项。重复执行只处理新增变化，不重复总结或创建平行账本。

## 总结写什么

总结回答“这一轮实际留下了什么，下一轮应从哪里继续”，每项结论有路径、版本或原记录支持：

| 内容 | 要求 |
| --- | --- |
| 目标与实际结果 | 原目标、实际完成/取消范围、未实现范围；区分源码、验收、可运行交付与部署 |
| 版本与验证 | 输入及源码/产物/环境版本，必需验证结果和证据，未执行与限制；没有证据写未知 |
| 关键决定 | 采用及必要的放弃理由、适用范围、决定来源；仍有效的重要决定关联持久入口 |
| 长期资产变化 | 更新/复用的权威位置、来源及生效范围、替代关系；未实施建议留作候选 |
| 问题与经验 | 有证据的根因、有效方法及复用边界，关联缺陷/实验/回归；猜测标为待核验 |
| 遗留与承接 | 未关闭项、影响、主责、后续任务或 tracker 入口与状态；无承接时保持待整理 |
| 结束与归档 | 工作结束原因/日期、整理状态/日期、仍有效的迭代内来源与后续关系 |

允许简短或标明不适用，不虚构收益、决定、验证或通用经验。多迭代梳理的项目总结可写在现有项目索引的整理章节，复杂时放在 `records/reviews/<记录ID>.md` 并索引；它关联各迭代总结，维护当前知识与未解决冲突，不改写原始历史结论。

## 保存历史与可选迁移

归档引用已有测试报告与交接结论，不要求整理或保存全部过程日志，也不额外创建证据归档文档。

默认逻辑归档：已结束迭代保留 `iterations/<迭代ID>/` 原路径，项目导航区分活动、待整理与历史。架构和测试中已验证且仍有效的内容同步到项目级当前入口，不能因为迭代归档而标为 `archived`；普通修订由 Git 追溯，被替换的完整候选按需放在所属目录的 `archive/`，并记录替代关系。有效规格仍从专业索引直接可达；原始验收、发布和事件记录绑定当时版本，后续更正以补充说明保留时间与来源。

项目已有规则或用户明确要求物理迁移时，先核对引用和外部入口，再移动、修正相对资源/入站链接、索引及预览路径并验证；无法修正的外部链接提供兼容入口或明确迁移说明。不同时保留两份可独立编辑的现行文档。

归档不自动删除历史、必要证据或大文件。临时缓存按项目清理规则处理；需保留证据先转入持久位置。删除与保留周期沿用项目已有规则或用户具体授权，不从“归档”推导删除权限。
