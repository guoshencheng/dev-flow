# 设计确认、计划复核与自主实现

日期：2026-10-23。0.17明确文字用例提交、执行表及可选证明另存本地且不提交；不改变阶段和授权依赖。0.16澄清启动 Dev Flow 及咨询转设计时的通知时点，文档、展示与确认步骤集中在 Skill 入口“从目标推进到完成”。当前用户要求与宿主约束优先；已有有效流程确认、设计、授权、Review 和检查按实际覆盖复用。

## 按当前状态推进

恢复最终目标、路径依据、完整交付范围、当前阶段、有效输入和候选版本、决定、Review、检查及未完成项，循环执行“核对依赖 → 实际工作 → 更新唯一进度 → 继续下一步”。按[进度管理](progress-management.md)列出到最终交付和收尾的全部大阶段，包括未开始事项。混合任务逐范围裁剪并记录依据，不能通过拆分逃避整体集成。只读[状态核验器](stage-state.md)检查声明的一致性，不证明实际专业工作。

### 每次实际 Review 的最小记录

记录对象及输入版本、实际执行者和方式、原要求/有效依据、检查范围、发现与结论、阻断及未覆盖、修订候选和定向复核。Review 应由未主笔该对象的实际执行者完成；受限时如实标为自查及独立性缺口。用户明确要求独立 Review 时，不能以自查登记独立通过。派发和独立性操作见[subagent 协调](../../subagent-coordination/SKILL.md)，评审专业标准由相应[职责提示词](../../../agents/prompts/)及其参考维护。

设计、计划、用例或候选变化时只重审受影响部分，未受影响结论有依据时复用。正式发现、结论和问题闭环保存在项目权威记录，具体目录与索引使用[文档管理](../../document-management/SKILL.md)；原始运行日志不充当评审结论。

## 流程开始前的用户确认

按 [Skill 入口“从目标推进到完成”](../SKILL.md#从目标推进到完成)执行启动步骤：启动 Dev Flow 或用户从咨询转入设计/研发等阶段时，先核对同范围有效流程确认；没有时，首条进度说明先明确“拟定整体流程，待你确认后推进”。必要的只读了解用于形成草案，不能替代或拖延向用户展示草案和确认请求；不能在完成当前回复时只把“展示流程”留作下一步。已有有效确认时说明复用并继续，不重复等待。

每轮迭代先在独立 `Progress.md` 拟定覆盖最终目标的整体路径。确认前只做定位项目、必要的只读了解和流程草案，不先执行后续设计、实现、评审、验收或发布。向用户主动提供 Progress 可点击入口与简明摘要：目标/范围、路径与裁剪依据、全部大阶段、各阶段职责与依赖、验证、交付形态和整体结束条件。单纯创建文件或在聊天说“按流程执行”不等于已展示。

取得明确答复后，在 Progress 记录已展示的流程版本、答复来源/必要原话与覆盖范围，再推进后续阶段。没有答复、预选项和需求描述不视为流程确认。流程版本仅在范围、关键阶段、职责依赖或交付边界实质变化时更新；日常进度、证据补充或阶段切换不使确认失效。实质变化先更新受影响部分并重新确认，无关已授权工作继续。

流程确认表示认可怎样推进，业务设计确认表示认可行为与取舍，实施授权表示允许对已展示范围正式实现；三者分别记录。用户明确表示按已展示范围实施时可在同次答复合并，不再重复询问。仅说“流程合理”不能据此记录设计确认或实施授权。

接手既有活动迭代时，先把有效总体状态集中到独立 Progress，保留原始证据与真实确认来源。同范围仍有效的流程确认直接复用；没有可核验确认时展示剩余完整路径并取得确认后继续，不倒填为历史已确认。用户明确要求立即执行的故障恢复按其已授权范围处理，再确认后续修复路径；不以此扩大其他步骤授权。

## 首次实施的人工同意

首次进入本次正式实现范围前，展示路径依据、具体范围、可观察结果、验证与交付，取得用户明确实施同意。已有同一范围授权持续有效，跨会话、内部切片和授权内必要修复直接复用，不因记录格式重复询问。用户明确要求按已展示计划开始或继续时记录并执行；需求表达、局部布局答复、查看文档、未答复和预选选项不自动成为开工同意。快速路径同样需要该授权。

标准任务可在设计确认中明确合并为“计划 AI 复核通过后按此范围开始”。同一次答复分别记录业务预期/重要取舍确认与实施授权；技术设计和计划由 AI Review，不新增人工逐文件审批。完整正式 TC 在完整候选后维护，不作为开工前置。

等待依赖性决定时继续研究、受控实验、验证准备和独立已授权工作。改变范围、重要业务/契约或交付边界时只请求受影响决定与必要授权，无关范围继续。授权记录保留展示的对象/版本、答复覆盖与来源；AI 判断或核验器不能代替用户同意。推送、合并、发布、通知等外部动作不从实施授权自动扩大。

## 用户确认的范围

业务确认覆盖相关用户任务、规则、入口与状态、成功/拒绝/恢复结果、边界、设备和重要呈现取舍；技术对影响数据、权限、兼容、运行或交付的重要架构取舍提出选项与影响，内部代码细节由技术 Review。认可某端布局不等于确认全部规则或另一范围的实施授权。设计原型由产品/视觉走查，可点击或 Mock 不改变对象，也不等于实现验收。

实现后正式用例在已确认预期内细化时由测试维护并独立 Review，不新增例行 TC 人工审批。发现新业务含义、重要约束或规格歧义时，回到受影响决定；用户亲自体验的最终验收按约定保留。

## 产品/UI 候选的技术反馈

产品/视觉提出入口、形式和状态候选时，研发在确认之前根据当前代码、实际组件、接口和状态管理比较复用、变化范围和维护成本，架构按影响核对边界。无现有代码时使用已验证技术基线或受控实验并标明未知。产品/视觉回应价值与操作差异，必要的等待、错误、权限、数据保留和恢复反馈须承接。技术不能单方降低业务目标，设计不能忽略已证实工程约束；重要分歧由用户决定受影响取舍。

## 统一研发设计与 Review

研发统一主笔本轮架构与实现设计，引用现行架构/契约，讲清目标、现状、核心链路、模块依赖、接口与数据、权限、状态、异常恢复、兼容、验证及交付。专业写法见[研发设计参考](../../../agents/references/engineering/technical-delivery-design.md)。稳定的实现输出应双向对应原规则、AC、UI 和架构约束；计划、候选实现和已验证事实分别表达。

独立架构执行者 Review 技术合理性，产品核对原目标与行为覆盖，视觉核对相关页面/状态承接；阻断项由研发修订，原评审者定向复核。主设计引用有效的独立 Review、计划和技术收尾结论，不复制第二套总体进度。

## 实施计划与一次 AI 复核

研发依据已确认业务预期、经 Review 的统一设计和真实工程形成独立计划，写明步骤/依赖、写入者、集成、自测/回归、重要接口/数据/配置/兼容影响、启动和交付。未主笔者实际 AI 复核范围、依赖、工程入口、重要约束、测试保护与交付可行性，阻断项修订后复核。有效授权成立后连续实施。普通步骤调整可更新；重要假设失效时定向重审，业务或重要契约改变时走变更闸门。完整正式 TC 的维护、Review 和人工确认不作为计划或实施前置。

## 实施中的需求变更闸门

新增、删除或改变前置、入口、规则、可观察结果、失败恢复、重要接口/数据契约或交付边界时，先标明旧基线和影响范围，更新受影响 RULE/AC、设计输出/链路、架构约束和计划，完成相应 Review、确认与必要授权，再实现或修复。未改变行为/契约的内部实现与工具调整按影响验证，不虚构新业务决定。

业务含义与完成标准须在受影响实现前固定；已有用例/回归按影响修订，尚未形成的完整正式 TC 仍在完整候选后维护。旧候选、旧环境或局部测试不能关闭新范围；核心任务的入口、前置或结果改变时安排适用真实链路验证。

## 自主实现、调整与端到端验收

设计、计划和授权有效后连续实现、集成和自测，不因内部切片重复审批。研发随实现执行适用的静态、构建、局部行为/契约、回归和真实主链路检查；测试可提前反馈可测性和准备环境，但完整正式 TC 不前移。只有关键可行性、数据、权限或兼容风险确实阻断后续时，提前执行有具体目的、范围与停止条件的专项。原型、实验、Mock 和实际应用的证据边界分别记录。

### 实施与正式验收的边界

内部切片不设置逐片正式实现 Review 或验收门槛。局部修复按真实影响形成完整修复候选；未经完整集成、当前版本验证和交付的结果不能作为最终通过。

### 完整候选交接条件

- 已确认范围已实现，必要入口、模块与消费者已集成，核心任务可真实运行；必需能力未由占位、硬编码成功或 Mock 替代。
- 适用类型、构建、局部回归和真实核心链路自测已执行，已知阻断已处理；模拟、实验与未覆盖明确。
- 有效业务规则、AC、设计输出/链路、架构约束和计划与候选一致，已有用例/回归按影响更新。
- 源码候选、任务开始基线、相关未提交差异、实际入口、自测结果和限制可定位。Git 获取完整差异的方法见[git-workflow](../../git-workflow/SKILL.md)。
- 正式 TC 与正式验收尚未形成或执行，不影响此项研发交接，但仍是后续整体完成条件。

### 实现后正式用例、Review 与执行

完整候选形成后，测试从原产品、有效设计、确认基线及交付约定维护中文用例列表，写清实际操作路径和预期。全量/增量共用当前用例文档；策略、技术说明或既有映射只在实际需要时补充，不默认另建技术检查表。候选代码只帮助定位入口和观察点，不决定正确预期；遗漏的产品行为须反馈补齐。

用例覆盖正常、边界、拒绝、失败恢复、必要回归与实际交付；由非用例作者独立 AI Review 预期、覆盖、可执行性和 Mock/真实环境边界。已确认预期内细化通过后执行；新歧义或重要变化返回受影响确认。具体方法见[用例设计](../../acceptance-case-design/SKILL.md)和[验收执行](../../acceptance-execution/SKILL.md)。

### 集中检查与修复

完整实现 Review 检查任务开始基线至完整候选的全部变更及相关未提交内容，分别给需求符合性和实现质量结论；产品/视觉按影响核对业务流程与呈现。正式用例维护/Review 可与代码 Review 针对同一固定候选并行，正式执行依赖有效用例和可运行入口，交付检查还依赖实际产物/环境。

测试执行适用界面、API、数据、真实端到端和交付检查；运维核验启动、产物、实际发布和运行版本。问题附候选与证据反馈，研发按关联原因修复；评审者与测试在新候选定向复评原意见、原场景及受影响回归，最后核验整体集成。旧证据仅在未受影响时复用，不能凭“已修改”关闭阻断。

### 最小验证记录

每项必需检查保留候选/环境、实际入口、步骤或命令、结果和未覆盖；缺陷保留最小复现、预期/实际、修复候选及复验。文档位置和原始日志处理见[文档管理](../../document-management/SKILL.md)。静态阅读、模拟、本机运行、正式验收及目标部署分别陈述，不互相折算。

### 主会话的运行与结束

主 Agent 持续维护最终目标、依赖、唯一进度、确认、写入/资源边界和结果集成。专业阶段按实际可用能力派发；派出后推进其他独立工作或等待，收到结果先核对输入版本、实际差异和证据。单个任务完成、等待超时和用户询问进度不触发整体结束。实际派发/等待见[subagent 协调](../../subagent-coordination/SKILL.md)。

只在整体目标完成、用户明确暂停/停止，或自主调查后确实缺少必要决定/资源时交还本轮。强制中断保存未完成阶段、候选、运行任务和恢复入口。未知、失败、未执行及失效证据保持真实状态。

## 分支集成与执行者

流程在正式实现、Review 和交付前核对候选与基线，合并前核对必需 Review/检查是否仍有效；分支、worktree、提交、冲突及集成操作见[git-workflow](../../git-workflow/SKILL.md)。共享文件、环境、数据和发布目标指定唯一操作负责人；独立上下文不自动证明独立结论。推送、合并、发布沿用已有授权。

## 必需检查与完成结论

正式用例写清每个场景的操作路径与预期；每次测试执行的本地执行表先列全部所选编号，再逐项填真实结果，汇总范围内结论。复杂场景需要的技术检查、版本及环境按实际必要性说明，不把额外表单或附件当作常规前置。业务完成标准与必要交付已在设计/计划固定，不因 TC 后置删除。任一必需检查失败、受阻、跳过、未执行或判断所需的实际观察未完成，所属 TC 和整体不能通过。截图等证明附件可选，缺少附件本身不作为未通过理由；未实际完成验证不能记通过。用例列表与本地执行表按验收Skill分开维护，执行明细及附件不提交。构建、单测、服务访问或原型截图不证明未观察的实际链路。

结束前核对当前完整候选的实现 Review、全部必需 TC/专项、实际交付和必要资产同步。架构独立依据当前源码及验收/交付结果完成技术收尾，其他职责对自身专业结论负责。主 Agent 按[收尾流程](closeout.md)综合、保存和归档；必需检查尚未实际完成或缺少判断所需观察则保持未完成；截图等可选附件缺失不单独阻断。

## 项目沉淀与新上下文

阶段结果、Review、用例、运行与收尾结论保存到项目中的唯一有效来源，主设计关联独立 Review、计划和技术收尾的版本及简短结论；旧确认和证据保留原版本，不倒填历史。目录、索引、模板、预览和归档由[文档管理](../../document-management/SKILL.md)负责，专业内容由[职责提示词](../../../agents/prompts/)及相应操作 Skill 负责。新上下文从项目入口恢复当前有效范围、候选、证据和待办，不依赖上一轮聊天记忆。
