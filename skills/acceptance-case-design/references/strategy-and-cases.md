# 测试策略与正式验收用例

从用户原要求、有效产品/设计、可观察完成标准及交付约定推导场景，先查看项目已有用例和测试入口。早期反馈可测性与场景缺口；完整候选后维护正式用例并独立 Review。实现帮助定位入口，不决定正确预期。

## 用例怎么维护

默认在 `docs/dev-flow/acceptance/cases.md` 用列表维护当前有效用例并提交 Git；已有权威位置沿用。每条保留简单稳定编号、场景名称、操作路径和具体预期；需要特定身份、数据或状态时补一句前提。普通使用者能理解并照着操作即可。

按正常、边界、拒绝、失败恢复和真实风险覆盖，适用时检查权限、副作用、读回、刷新或重新进入。不要只写“正常/正确”，也不要只验证状态码或成功提示。无 UI 的 API/CLI 按实际调用者路径描述，不制造界面场景。

业务规则及设计来源可在已有记录引用；用户用例不堆内部字段或规则代号，不默认要求另一份技术拆解/CHK表。复杂专项、自动化断言或已有技术映射按实际需要维护，不能改变用例预期，也不能让技术文档成为阅读简单用例的前提。

## 全量与增量

全量按该文档的全部有效用例执行。增量仍修改同一列表：新场景追加、变化场景原位修订、停用场景注明原因；本轮选择新增/修改及受影响回归，用例不因只跑增量而丢失。

沿变化规则、共享组件/接口、数据所有权、消费者和历史缺陷判断相关旧场景。影响不清时扩大相关回归或保留待明确，不能把未执行当作通过。无需单独建立增量用例库、运行清单工具或重复完整用例文档。

## 按对象选执行方法

| 对象 | 验证重点与边界 |
| --- | --- |
| 组件/局部规则 | 沿用已有测试，说明隔离与模拟范围 |
| 页面交互 | 真实导航、输入、反馈、权限透出及恢复；Mock后端不证明真实后端链路 |
| API/数据 | 实际身份、业务状态、读写和拒绝副作用，成功码不等于完成 |
| 完整链路 | 用户入口、请求/业务处理、结果读回及约定的持久性/恢复 |
| 启动/交付 | 约定版本和目标环境实际完成核心任务，本机不冒充部署结果 |
| 专项 | 依据已有性能/可靠性/权限等目标选样本、条件和判据，不默认全专项 |

React、Next.js、Astro等沿项目技术约定使用真实入口和现有工具。工具形式不改变产品原型走查与实现验收的职责边界。

## 用例独立 Review

完整候选后，向未主笔用例的实际执行者提供原始要求、有效设计和当前用例，核对：

- 原要求及适用交付任务有对应场景；正常、边界、拒绝和恢复按风险表达。
- 操作路径和预期具体可判断，身份/数据等必要条件清楚；业务含义忠于有效来源。
- 全量列表完整，增量新增/修改能关联必要旧场景回归；停用有依据。
- 模拟/真实、局部/完整链路边界清楚；不能由当前实现缺项缩减原要求。
- 文档只保存用例定义，执行表及可选证明留在独立忽略目录；不强制额外技术表或附件。

记录实际输入、评审者、发现、修订及定向复核，自查不登记为独立通过。明确预期内细化通过后执行，不增加例行人工审批；新业务含义或歧义只回到受影响决定。
