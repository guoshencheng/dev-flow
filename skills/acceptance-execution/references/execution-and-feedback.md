# 执行、记录、反馈与复验

先读当前用例文档、被测版本和运行入口，沿用已有 runner 或实际操作方法。用例与执行记录分开：用例提交 Git，执行表及截图/录屏/日志等附件统一留在被忽略的 `.dev/` 或项目既有本地运行目录，不提交。

## 逐条执行与核对

本轮[完整候选条件](../../dev-flow/references/execution-contract.md#完整候选交接条件)成立后，选择全量有效用例或增量新增/修改及相关回归，先在本地表为每个所选编号列一行、默认“未执行”。记录实际日期、范围和被测入口，必要时补版本/环境。每完成一条及时填写，结束或中断时按编号查漏，不能只列已跑成功项。

表格默认用“通过 / 不通过 / 未执行 / 待人工验证”。无法执行在备注写清原因；底层runner的failed/blocked/skipped/not-run或重试信息如实放备注，不能因退出码0将未运行项算通过。中断后继续剩余项；有副作用但结果未知时先查实际状态，不盲目重复非幂等动作。

具体问题及时反馈。作者推进新候选时保留被测版本或暂停受影响项；修复后执行原场景与相关回归，在表中保留原失败及复验说明。后续轮次另建本地表，不改旧日期冒充本次执行。候选/环境变化后按影响复验，复用有实际依据的未受影响结果时注明原来源。

## 证明附件可选，实际观察要真实

截图、录屏、命令日志、接口返回或导出文件有就附在本地记录，没有可写“无”；不能仅因缺截图或附件判未通过。结果根据实际操作和用例预期判断，在表中用文字简述实际观察。未执行、没有完成必需观察或无法判断的项目保持未完成。

附件有无与验证边界分开：服务保存/读回不等于应用退出重开，Mock不等于真实外部依赖，成功码不等于业务结果。用例要求什么就实际观察什么，不强制每项都截图、真机、人工或E2E。仅在项目已明确需要交付某文件/影像时核对该交付物，不能把普通可选证明偷换为必交产物。

人工和AI填写同一本地表；AI不能完成的人工项先记“待人工验证”，获得明确的实际人工反馈后再填结果，可备注来源。“应该好了”等推测不能当作已验证。

## 缺陷与定向复验

| 发现 | 处理 |
| --- | --- |
| 实现不符合预期 | 反馈最小复现、预期/实际及影响，使用已有缺陷入口 |
| 脚本/数据准备错误 | 对照有效预期修正方法并重跑，保留原失败原因 |
| 身份/服务/依赖不可用 | 备注受阻原因与负责方，继续独立项；恢复后实际执行 |
| 业务或契约歧义 | 返回产品/架构的受影响决定，不能迁就实现修改预期 |
| 重试通过/不稳定 | 保留首次失败和复验说明，定位原因，不能靠增加重试次数关闭必需项 |

缺陷发现→研发修复待复验→执行原场景与相关回归→通过才关闭；失败重开，缺环境保持待复验。修复说明或研发自测不直接关闭问题。对缺陷保护有效性按[回归验证](../../regression-verification/references/test-first-and-regression.md)核对目标失败/修复后通过，不将脚本语法或环境失败当作业务复现。

## 记录与结束

采用[本地执行表](../assets/templates/acceptance-report.md)。本地表及附件不复制进可提交的用例、Progress或`acceptance/result.md`；Progress只维护流程进度和用例入口，面向用户说明实际结果及未完成项。独立Review、长期业务规则和复用测试是各自资产，不等于本轮执行表。

范围内必需用例和约定交付实际通过、阻断问题复验关闭，才报告通过；有失败为不通过，有未执行、待人工、受阻或必要观察未完成则保持未完成。报告的真实/模拟、代理操作/人工反馈、本机/目标环境边界如实说明。

本机记录跨机器不可得时，按当前需要转交本地材料或复跑，不假定他人能打开私有路径，也不默认把执行表提交Git。正式Agent接续按实际需要移交用例入口、候选、未完成项及本地记录取得方法，不用一张结果表冒充已接手。
