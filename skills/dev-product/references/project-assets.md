# 产品资产复用与持续维护

## 找到权威位置

先明确业务项目及根路径，从项目文档索引定位产品、交互原型、设计/UI 和技术入口，再读取项目 `AGENTS.md`、相关规格、代码或接口、设计资源与验收资产。已有权威位置继续维护，通过项目索引关联，不复制出第二套事实。

没有现行规范时，按共同[设计文档协议](../../dev-flow/references/design-document-contract.md)在 `docs/dev-flow/product/` 保存产品索引和 `features/<功能ID>/spec.md`；视觉规格位于对应 visual 目录，原型源码和共享证据分别关联。无需一次创建完整目录或所有角色的空文件。必要入口可以是一份短 Markdown 索引。

## 最小有效记录

可复用规格保留目标和适用范围、状态（现行/候选/待核验/已替换）、来源及版本、关联能力与验收编号、权威位置和验证范围。用户确认的要求与设计建议分别标记。

产品基线用于识别当前用户任务、业务规则、有效决定和待决问题；流程与状态详细规格作为下游执行入口；验收编号关联到规则与场景。记录源码或接口版本以及实际观察条件，不能仅写“最后更新日期”。

功能规格明确原型设计与场景、使用限制（实际数值、口径、边界、反馈）、透出逻辑（角色、对象、状态、配置下显示/隐藏/禁用/只读）、可执行授权，以及输入、校验、计算/筛选、状态变化、保存与输出等相关具体逻辑。每条规则关联来源、状态和稳定 RULE/AC；未知条件保持待决。参考[产品规格模板](../assets/templates/feature-spec.md)，按实际范围裁剪。

来源冲突或实现与有效决定不一致时记录差异。规格可以按授权更新，生产功能是否已同步由研发和测试证明。

## 参考、原型与设计模式怎样沉淀

保持项目已有权威位置。尚无规范时，可以在现有产品入口关联 `docs/dev-flow/` 中的参考/决定/验收记录，将可运行原型放在 `design/prototypes/<主题>/`；只创建本次需要的文件，不建立完整空目录树。

| 资产 | 保留内容 | 如何复用 |
| --- | --- | --- |
| 参考记录 REF | 来源、观察版本、任务、人群、证据类型、机制与不适用条件 | 下次先核验来源和任务条件，再借鉴相关机制 |
| 原型 PT | ID、版本、源码提交、启动命令、场景、规则/验收、模拟范围 | 从现行入口启动，复用未变场景，改变部分有对应新版本 |
| 反馈 FB | 原型/方案/状态、实际操作、观察、方式、影响与证据位置 | 判断设计问题或实现问题，关联决定与原问题复验 |
| 决定 DEC | 有效/候选/已替换、取舍理由、确认来源与受影响规格 | 已确认规则成为后续设计输入，保留被放弃方案的关键理由 |
| 交互模式 PAT | 解决的任务、适用条件、行为与状态、例外、组件/Token 来源、验收与证据 | 按条件复用，不能仅凭名称相同直接复制布局 |

可以将多个资产保存在一份设计记录中，通过稳定编号建立 REF → PT → FB → DEC → 规则/AC 的关联，无需按编号各建一个文件。视觉样式、交互语义和业务规则各自关联权威来源；代码组件进入项目组件库前由研发和视觉核验。

在项目已有文档中记录必要条件，也可以参考[原型讨论模板](../assets/prototype/review.md)。原型无需内置反馈功能；采用导出时，反馈文件只证明记录已经导出，保存到项目并关联决定与规格后才能用于长期复用。新版本保留追溯，但索引指向当前有效原型与规格，避免把历史记录全文追加到每次交接。

## 复用的有效性与推广

React 组件源码按共同[共享组件约定](../../dev-flow/references/ui-stack-and-components.md)进入同包 Git 工作区。项目优先采用已匹配的 antd/shadcn 基础组件，再核验共享组合；以复制或参考源码的方式在项目中维护，记录来源文件、提交或哈希、项目差异与复用场景。业务特有接口、权限和规则留在项目，经过适用性与行为验证的组合才提升为共享组件。共享源码后续变化按需比较、合并，项目验证过的通用改进再回收；不能把本机全局链接当成跨机器共享已完成。

按用户任务、频率、平台/输入方式、权限、数据规模、错误成本和真实契约检查相似性。匹配的模式直接沿用，差异形成明确变体；不适用时保留原因。用户新要求、规则、组件或平台变化时，定向标记受影响原型、截图、验证和回归待复验。

例如项目已有“所选项批量确认”模式，下一功能可沿用确认摘要和键盘规则；如果本次需要跨页选择或部分失败，则补齐范围与恢复语义，不能只替换标题。C 端预约中的“确认后查结果”也可供 B 端任务参考，但权限、数据量和恢复入口需要重新核验。

通用经验先作为候选：保留出现过的项目问题、适用范围、反例与可复现场景，再经过职责 Skill 的行为验证决定是否纳入。源码和项目事实留在项目中；全局 Skill 更新的是经过验证的方法或脚手架。未经观察的偏好和单次方案不自动成为全局默认。

## 连续任务如何使用

1. 任务开始从项目入口定位有效规格，核对当前用户要求、相关代码和接口条件。未知与过期部分先核查。
2. 无变化且仍有效的流程、规则、验收编号直接复用。变化部分建立明确影响关系，保留其他有效内容。
3. 更新相关资产的来源版本和验证状态；原有实际验证证据受到变化影响时标为待复验，不能只刷新日期。
4. 交接列出复用和更新资产、候选取舍、能力缺口，以及必要的下游验证。下一任务从文件获得这些事实。

产品候选不自动取代现行决定。保持当前生效版本与尚待确认内容可识别；历史文件或旧截图作为来源时标注适用条件。

普通修订由 Git 保留历史，已替换完整方案按共同 archive 规则记录原因和现行入口，移动时修正资源与反向链接。长期索引保存该项目的产品权威路径、原型源码、启动命令和场景；讨论/确认时临时 Vite 地址由[项目预览工具](../../dev-flow/references/document-preview.md)根据该项目服务与文件生成，渲染/原型行为变化后定向核验，普通文字修改检查内容与引用。

## 持续能力建设

P01、P02 维护用户问题证据、范围和取舍；P03—P06 维护流程、交互、验收和验证方法；P07、P08 根据真实反馈维护实验与演进决定。没有数据时保留未知，不制造研究结果。

项目能力记录区分“方法已定义”“隔离案例已验证”和“实际项目已验证”。依据共同成熟度规则登记，隔离案例不能代替真实用户或生产应用验证。能力缺口有来源问题、影响、主责与下一次验证方式。

重复问题先转为本项目的规格或回归；经过适用范围和代表案例验证的通用候选再进入 `dev-product`。与当前任务无关的调研、工具或全局规则建设进入待办，持续沉淀不能默默扩大范围。
