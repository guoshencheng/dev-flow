# 参考研究与交互方案创造

参考用于回答设计问题，记录适用条件和行为依据。先写下未知：用户是否能找到入口、怎样比较信息、怎么减少重复操作、异常后如何继续；再选可回答它的材料。范围清楚且项目已有有效模式时，直接复用，不以重新搜集参考作为前置门槛。

按用户指定的[UI 约定](../../dev-flow/references/ui-stack-and-components.md)，其他 C 端应用在设计与研发前先参考网上材料和目标平台规范。已有相关外部参考时核验当前有效性后复用；没有时实际浏览并形成参考记录，再进入实施。B 端以 Ant Design、C 端 Web 以 shadcn/ui 为基准，研究结果服务具体任务与呈现，不另造一套无来源的基础控件。

## 找到合适参考

先读本项目的现有流程、已确认设计、组件、反馈和运行界面。外部参考优先选择可实际操作的同类任务、相邻领域的同一行为，以及平台或设计系统官方模式；用户指定的参考单独记录。

| 材料 | 能提供的证据 | 应补充的检查 |
| --- | --- | --- |
| 现有应用与真实操作 | 入口、导航、反馈与恢复的实际行为 | 环境、版本、账号条件和被观察范围 |
| 产品官方演示或帮助文档 | 宣称支持的规则、步骤或模式 | 演示是否覆盖当前版本；未操作部分标为文档依据 |
| 官方设计系统、组件示例 | 组件意图、可访问性与状态约束 | 本项目任务、密度、平台和实现是否适用 |
| 截图、设计作品、图库 | 呈现、信息层级与视觉方向 | 无法从静态截图证明交互或可用性；记录行为推断 |

按“具体任务 + 行为/组件 + 平台”搜索，例如“批量选择 跨页 范围提示”“预约 修改时间 返回保留”“data table batch selection scope”。数量以覆盖关键问题为准。参考评估可以比较竞品和相邻领域，但应把观察转成对本项目的具体建议；团队审查和真实用户对比测试分别报告。[NN/G 竞品可用性评估](https://www.nngroup.com/articles/competitive-usability-evaluations/)

## 拆解与建立参考记录

记录 REF 编号、原始链接或项目资源位置、观察日期/版本、任务与人群、证据类型、入口/操作/反馈/恢复、可借鉴机制及不适用条件。截图注明对应页面与状态；推断和实际操作分开。

比较同一任务的机制，而不仅比较首页：信息在哪一步出现，谁要作出决定，哪些步骤可省略，默认是否可靠，数据何时生效，错误如何恢复。必要时用短表：方案、步骤、信息负担、错误成本、可实现依赖与适用边界。参考能说明存在某种做法，不能证明它在本项目必然有效。

已有参考变为失效版本时保留来源，更新当前适用性。引用、借鉴行为和直接复用代码/素材分别处理；直接复用遵循资产的实际许可与项目约束。

## 创造候选方案

从任务约束构造变化：减少不必要步骤；把信息或操作放到任务发生的位置；让比较、预览和确认更明确；将频繁操作批量化；补足恢复路径。优先使用用户熟悉的交互，有针对性地改变存在问题的环节。

| 已知问题 | 可探索的差异 | 需要验证 |
| --- | --- | --- |
| 用户在确认时漏看关键信息 | 同页摘要、独立确认页或模态中展示 | 能否注意到内容、回改是否保留、焦点是否合理 |
| 频繁重复处理同类对象 | 单项快捷动作、所选项批量操作 | 选择范围、权限、部分失败与恢复能否理解 |
| 表单复杂且用户熟悉度不同 | 有依据的默认、分组、必要的渐进展开 | 关键成本或必填项是否被隐藏，熟练用户效率是否受损 |

每个候选标明假设、相较基线的变化、保持不变的条件、依赖与验证场景。重要取舍可做 HTML 对比原型；清楚的局部变化无需强行产出多个方案。没有用户或实际应用时只报告设计假设与走查，不编造“用户更喜欢”或提升比例。

最后将 REF → 待验证问题 → 原型版本 → 实际观察 → 决定 → 规格/验收的关系保存到项目。未采用的机制保留简短理由，避免下一任务再次作出已被证据否定的尝试。
