# C 端与 B 端的产品交互设计

以下是本体系的设计判断指导，不是固定的行业结论。先确认用户任务、频率、熟练度、使用环境、协作关系、数据规模与错误代价；C/B 标签帮助提出问题，不自动决定平台、信息密度或视觉风格。一个项目可同时包含首次访客和高频专业用户。

## 共同起点

明确用户要完成什么、现有入口与业务对象、成功后的下一步。核心行为可发现、反馈可理解、错误可恢复；实际权限、数据与异步契约影响交互时先对齐。两类产品都要覆盖目标设备、键盘、内容长度和相关可访问性，不把易用性留给视觉阶段。

| 维度 | C 端常见需要关注的条件 | B 端常见需要关注的条件 |
| --- | --- | --- |
| 任务进入 | 首次认识价值、浏览与选择、低频重新学习 | 找到工作队列、对象、状态和待办上下文 |
| 信息与决策 | 清楚的价值、价格/条件、可信依据和比较 | 数据字段、状态、依赖、影响范围与例外 |
| 频率与熟练度 | 首次体验、自然学习、熟悉后减少打扰 | 重复任务效率、快捷操作、批量与个性化视图 |
| 权限与协作 | 身份、个人数据、授权与撤回等适用规则 | 角色能力、对象范围、交接、审核与可追溯记录 |
| 失败成本 | 不丢输入、结果可信、订购/预约等任务恢复 | 并发变更、部分失败、长任务、误操作影响范围 |
| 持续使用 | 本次目标完成后，合适的返回与后续入口 | 队列上下文、筛选/排序、恢复位置和运行结果 |

上表是检查视角，实际需求以项目证据为准。桌面 C 端可能很复杂，移动 B 端可能只需要完成一个审批任务。

## C 端如何落实

从核心用户任务安排首次可用路径。让内容、主操作和后果在发生选择时易理解；必需注册、隐私、付费或授权按真实业务要求出现，关键条件不以渐进展开隐藏。信息多时按任务分组，避免以装饰或过多教学阻碍使用。

示例：预约体验先看可用服务与时间，再检查关键条件并确认；成功后有查看与相关修改入口。新手需要任务中的提示，熟练用户可以复用可信偏好；记忆用户信息与自动提交分别决定。原型比较同一任务的步骤和理解成本，不仅比较卡片外观。

引导应服务首次任务，适用时通过操作学习，并允许跳过非必要说明；这是平台原则的参考，Web 项目仍需验证实际适用性。[Apple Onboarding 指导](https://developer.apple.com/design/human-interface-guidelines/onboarding)

## B 端如何落实

先画清业务对象、生命周期、角色权限和工作流。区分列表浏览、检索比较、详情判断和实际操作；必要时支持筛选、排序、视图与批量，但不能把所有数据操作默认放进一张表。数据表的搜索、排序、展开和批量机制有不同使用条件。[Carbon 数据表指导](https://www.carbondesignsystem.com/building-blocks/core/components/data-table/guidelines)

批量选择明确“当前可见项/当前页/全部符合筛选项”的范围；跨页、筛选变化和权限差异有清楚的语义。确认展示实际对象、数量、影响和相关不可逆后果。异步任务分清未提交、处理中、明确失败、结果未知与成功；部分失败展示实际结果，恢复依据接口能力，不假定全部回滚。

示例：管理员从待办模板中筛选、选择并发布；确认前可以调整范围，提交后按真实契约查结果。重开页面能否恢复上下文、筛选是否保存、快捷键是否适用，都由项目任务与能力决定。熟练用户的效率改进需要实际重复操作证据，不只靠压缩字号。

## 原型与验证侧重点

C 端原型可聚焦发现价值、选择、确认、完成与再次返回；B 端可聚焦真实数据量、定位对象、批量范围、权限差异、任务状态及恢复。两者都使用有代表性的内容长度、空/错误数据和相关目标窗口。

观察目标用户完成真实任务，区分理解错误、导航阻力、业务歧义与实现缺陷。有测量依据时再记录完成情况、耗时和误操作；没有真实样本不承诺提升指标。项目有效交互模式、例外与反馈关联到验收与下一轮设计。
