# 测试与验收

读取同包[总纲](../dev-flow/references/constitution.md)，一起安装 `dev-flow`。模型/强度由用户和宿主选择。未委派时由当前执行者读取本 Skill 承担工作，记录执行方式。用例、设计、报告和交接使用中文。

## 确定本次验收

先按[任务路由](../dev-flow/references/task-routing.md)区分任务：完整功能实施前由产品/设计明确并确认业务规则、边界、可观察完成标准和交付形态，研发计划包含自测与回归；完整正式用例及其 Review 不作为实施前置。bugfix 依据有效规格、问题证据和修复计划复验原场景及相关回归，在既有预期内补充覆盖并 AI Review。改变验收含义时只确认受影响部分。

先区分测试设计、实现验收和设计评审。产品/UI 文档与原型是读取的依据，默认流程/规则/交互/异常恢复走查由产品主责，呈现由视觉主责；测试早期检查可测性、场景覆盖与用例预期，实际验收面向可运行实现及交付候选。原型能操作、采用 Mock 或使用浏览器自动化，不会自动改变设计走查主责。用户明确指定测试检查原型时，按指定范围验证并注明模拟边界，不登记实现/交付验收通过。

## 需求变化与验证层级

用户在实现、验收或交接中新增、否定或改变前置条件、用户操作、业务规则、可观察结果、失败恢复或交付边界时，先进入[执行协议的需求变更闸门](../dev-flow/references/execution-contract.md#实施中的需求变更闸门)。先修订受影响的产品/设计预期与完成标准，并确认新增或有歧义的业务决定；已有回归/正式用例同步受影响部分并 Review。尚未形成的完整正式用例在候选完成后依据更新的预期编写。研发局部测试与核心链路自测随实现持续进行。

端到端验证不是所有修改的固定税负。以下任一条件成立时，至少安排一条从真实入口到可观察结果的 E2E，并覆盖相关正向/拒绝或恢复分支：

- 变化跨越两个或以上模块/层，或需要验证真实文件、媒体、外部服务、权限或数据存储；
- 变化包含刷新、重新打开、持久化、导入/导出、部署/启动或交付结果；
- 变化包含破坏性清理、不可逆操作、忙态阻塞、失败回滚或“允许生成但禁止交付”等边界；
- 用户反馈改变了核心任务的入口、前置条件或最终结果。

纯文案、局部样式、测试脚本、内部重构或既有契约内的局部修复可按影响做定向验证；是否裁剪及理由写入验收记录。E2E 可以采用桌面人工操作、浏览器自动化或项目已有真实链路工具，但 Mock、旧窗口、局部组件通过不能登记为真实 E2E 通过。

先明确业务项目及根路径，从项目入口读取实施前已确认的产品 RULE/AC、交互/UI、可观察完成标准、架构 ARC/契约、经 Review 的研发设计及交付约定；完整候选就绪后核对源码、实际入口、启动和测试条件，维护正式用例。已有有效用例直接复用；区分已确认预期、设计候选、实现事实、未知与失效证据。实现只提供执行路径，不能决定正确预期。

完整候选后，测试依据已确认预期编写行为用例，再维护关联技术验证拆解。用户文档用普通中文描述场景、前置、操作、具体可观察结果与覆盖边界；接口/数据/并发/自动化细节留在技术层。未参与编写的执行者独立 AI Review 两层覆盖、预期和证据对齐；既有预期内的细化无需例行人工审批，歧义或新增业务决定只确认受影响部分。无法独立执行时记录独立性缺口。测试维护/执行测试、给出缺陷证据并复验。产品维护业务含义，视觉维护呈现，架构维护技术约束，研发修复实现，运维维护运行入口。测试可修复选择器、数据或测试脚本，但改变已确认的业务、架构或验收预期须回到对应依据及受影响确认；不以实现现状反推正确预期。

研发随实现编写必要局部测试，验收负责覆盖、证据核验和实际复验。按[回归有效性核验](references/execution-and-feedback.md)检查目标行为失败/通过证据；事后补测不能仅凭新实现一次通过声称保护有效，旧错误实现仍通过的测试须识别并处理。

完整功能的正式验收在[完整候选就绪](../dev-flow/references/execution-contract.md#完整候选交接条件)后集中开展；此前可准备用例、数据、自动化和环境，不逐切片设独立验收门槛。界面/API/数据/E2E与专项支撑同一完整任务结论；具体缺陷立即反馈，按关联修复范围定向复验和相关回归。提前专项只按共同协议的明确例外开展。用例已补充、局部测试通过、E2E 已执行和交付已核验分开记录；必需 E2E 为未执行或阻塞时，候选只能报告为未完成/受阻，不能报告为完整验收通过。

## 按验证对象选择方法

- **策略与用例设计：** 读取[策略与用例](references/strategy-and-cases.md)，完整候选后从原要求和已确认完成标准形成正式场景，再对照经 Review 的研发设计与实际入口，关联层级、环境与通过条件；遗漏反馈产品/研发，不缩减原需求。独立 AI Review 后在既有预期内执行，歧义/新增业务只确认受影响部分。
- **可运行实现的前端与界面：** 读取[界面验证](references/frontend-and-ui.md)，验证行为、相关状态和业务透出、目标设备/键盘，以及与视觉共同核验实际呈现。使用 Mock 的页面/组件测试明确覆盖边界。
- **后端接口：** 读取[接口与数据验证](references/backend-and-api.md)，通过真实调用验证输入输出、权限、业务错误、数据不变量和读写结果；项目适用的重复、并发、兼容与恢复按契约补齐。
- **前后端 E2E 与交付：** 读取[完整链路与交付](references/end-to-end-and-delivery.md)，从实际入口操作界面，关联请求、响应和服务端结果，核验刷新/重新读取与相关异常恢复。采用真实项目交付形态，独立前后端分别核验目标；静态站不制造后端用例。
- **执行、失败与研发对焦：** 读取[运行、证据与复验](references/execution-and-feedback.md)。使用同一版本执行，定位实现/测试/环境问题，带证据反馈研发，修复后复验原问题和受影响回归。

优先沿用能满足要求的现有工具。新 Web 自动化默认 Playwright 处理浏览器/API 场景；React 局部行为采用兼容的 Vitest/Testing Library 或现有方案，工具与接入依据见对应参考。根据风险裁剪，只运行能证明本次结果的必要检查；完整用户行为不能只以单元测试或 HTTP 成功码验收。

## 通过条件与交接

必需用例在声明候选/环境实际通过，阻断缺陷经原场景及回归复验关闭，相关架构约束和约定交付成立，才报告范围内验收通过。未执行、失败、阻断、跳过、不稳定及 Mock/替身范围分别登记；没有所需工具/数据时明确缺口并继续独立工作。重试后通过不消除首次失败证据。

按[逐必需检查与完成结论](../dev-flow/references/execution-contract.md#必需检查与完成结论)先汇总每个 TC，再汇总完整候选及交付核验。按实际入口/观察点区分服务、原型、真实界面与交付证据，不把保存/读取、导出协调器或 HTML 展示升级为应用重开、系统分享或原生布局通过。采用[状态核验](../dev-flow/references/stage-state.md)时更新选定的唯一 Progress/索引状态权威；必需检查尚未闭合不能报告任务完成。

按[项目测试资产](references/project-assets.md)维护策略、用例、自动化、数据、缺陷和报告，关联项目产品/UI/技术入口。讨论歧义或新增业务预期时使用该业务项目的文档预览，Skill 方法不代替项目成果。交接给出结论与范围、候选/用例版本、实际命令与证据、缺陷/依赖、复用与更新资产；生产验收、工具案例与角色行为分别登记。

需要细化职责能力时，读取[能力目录](../dev-flow/references/role-capabilities.md)中的对应职责；实际验证范围以当前候选的执行证据为准。

本次阶段产物统一归入 `docs/dev-flow/iterations/<迭代ID>/` 的对应职责目录，由迭代索引关联版本、Review、确认与证据。项目级职责目录用于跨迭代的现行基线和复用资产；已有的 `docs/dev-flow/` 内权威位置通过迭代索引映射；目录外文档按共同文档协议整理迁入。详见[迭代目录协议](../dev-flow/references/design-document-contract.md)。
