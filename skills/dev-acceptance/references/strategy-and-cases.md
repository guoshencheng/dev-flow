# 测试策略与可确认用例

从本次有效 RULE/AC、UI 状态、ARC/接口数据契约、经符合性 Review 的[技术方案](../../dev-engineering/references/technical-delivery-design.md)及交付约定选择验证，先查看项目现有策略与测试入口。早期可以反馈场景/可测性，完整功能正式用例定稿同时对照原产品与经 Review 的 OUT/链路。按变更及实际影响裁剪，不要求每项任务跑完整矩阵，也不以覆盖率数字代替结果。

## 不同验收方案

选择方案前按共同[阶段与职责边界](../../dev-flow/references/constitution.md)确定对象。测试可以读取设计并反馈不可测/覆盖缺口，设计原型的体验与方案走查仍由产品/视觉主责；下表默认面向实现/交付候选，Mock 隔离测试是实现测试方法，不能仅据其存在把设计原型纳入正式验收。用户明确指定原型检查时单列该范围及模拟证据。

| 方案 | 适用与必需检查 | 能证明什么 / 证据边界 |
| --- | --- | --- |
| 领域/组件局部验证 | 算法、规则、表单及局部状态；现有测试或兼容 Vitest/Testing Library | 隔离的规则/交互，记录 DOM 模拟、浏览器和 Mock 范围 |
| 前端页面与交互 | React 页面导航、输入、列表、状态、权限透出；Playwright 或已有浏览器工具 | 实际浏览器行为；Mock API 下不证明后端、部署及持久化 |
| 后端 API/集成 | 实际 HTTP/项目协议入口、真实授权、业务规则、存储与必要依赖 | 接口/业务结果；内存或替身存储不能证明生产数据库约束 |
| 前后端完整链路 | 核心用户操作、真实请求响应、服务端结果、刷新/重新读取、恢复 | 声明环境的完整链路；标明尚未接入的外部依赖 |
| 可启动/部署交付 | 实际构建、准备环境、启动/安装/访问，并执行核心链路 | 具体产物及环境的交付；本机通过不登记目标部署通过 |
| 专项与回归 | 变更影响、历史缺陷，以及已有性能/可靠性/权限等目标 | 相关场景及测量条件；按真实需求选取，不默认开展全部专项 |

React 前端、Next.js 全栈、Astro 静态站遵守已定[技术约定](../../dev-architecture/references/technology-stack.md)。Next 覆盖服务端业务与渲染/客户端链路；Astro 验证构建后的页面、内容、资源和实际交互，有真实动态依赖才增加相应方案。单纯 API 项目以真实 API 业务链为 E2E，无需构造界面。

## 从目标到用例

为本次场景分配稳定 `TC-<ID>`，建立 `RULE/AC/UI/ARC ↔ OUT/链路 ↔ TC → 自动化文件/测试名或人工步骤 → 本轮证据`；使用项目已有 ID 与格式时保留权威映射。一个场景可有多层检查，各自说明责任与真实性，避免只重复断言相同成功结果。用例先依据权威预期，再看方案/实现的可测入口。

从每个拟交付页面/入口/功能沿真实用户/调用者行为形成完整链路用例，检查相关界面动作、请求响应、业务/存储结果、读回及异常恢复；从原产品规则再反查有无遗漏。技术方案没有包含的必需行为反馈研发/产品补齐并 Review，不因 OUT 清单缺项删除对应需求或用例。无 UI、纯静态或其他工程按真实入口到结果裁剪。

## 用户用例与技术验证两层表达

先按用户任务写用户验收用例，再拆解技术验证。用户确认可观察行为、结果与覆盖；技术语言和执行方法由研发/测试维护，经同一次用例 AI Review 检查两层对齐，不新增人工技术审批。

- **用户用例（cases.md）**：普通中文的场景、前置条件、顺序操作和具体预期。正常、边界、拒绝、异常及恢复按风险组织，一条用例有可独立判定的结果。说明刷新/重试等持久性行为，不要求理解内部协议。“正常、正确、稳定”不能单独作判据；缺少数值、提示或恢复规则列为待决，不自行编造。
- **技术拆解（technical-checks.md）**：TC 到稳定检查编号的映射，承接 RULE/AC/UI/ARC、OUT/链路、接口/数据、并发、故障注入、环境、执行入口和证据。业务预期引用用户用例；独立架构专项注明有效约束来源。一条用户用例可由多项技术检查共同证明。

用户正文不堆放规则代号、内部字段、hash/cursor/锁等术语、环境变量或测试命令；仅链接技术依据。纯 API、CLI 等按调用者入口表达，保留判断契约必需的名词并解释，不制造界面场景。可读化不删除失败恢复或降低技术覆盖；环境、模拟和未覆盖对用户的影响仍用普通语言说明。

既有项目优先复用权威位置并建立两层阅读入口；小任务可在同文件明确分区，默认展示行为部分，避免复制两份业务预期。

## 用例 AI Review 后再交人工确认

测试完成可读候选后，主 Agent 组织实际 AI Review，对照原产品/UI/架构、技术方案及其符合性 Review 核查：

- 拟交付 OUT/页面/功能/链路和本次原 RULE/AC 是否都有相关检查，缺口是否明确且已处理；覆盖不能只从方案单向推导。
- 预期是否忠于使用限制、透出/权限和业务逻辑，正常/边界/拒绝/失败恢复是否按实际需求落实，相关 ARC 是否有适当检查。
- 条件、身份、数据、操作和结果是否可执行/判断，是否覆盖从入口到最终业务结果，而不只断言 2xx 或界面提示。
- 模拟/真实依赖、本机/目标环境和交付验证边界是否清楚，阻断与未覆盖是否保留。
- 用户用例无需阅读技术方案即可理解，数据/步骤/结果具体，独立失败分支可分别判定；可读化未删异常与恢复。
- 每个用户用例的各项预期都有足够检查与所需证据，不能以局部成功替代最终结果；技术层没有改变或降低行为，独立专项有约束来源。
- 两层覆盖与环境边界一致；报告能由检查汇总到用户用例，必需检查失败或未完成不能汇总为通过。

产品核对语义/覆盖，研发核对技术产出/入口/可执行性，架构按需核对契约/约束。可用且获准时使用独立上下文，不能委派时记录主 Agent AI 自查，不声称独立。记录输入/技术方案/用例版本、实际执行者/方式、发现、通过/阻断及修正复核；方案遗漏回研发，不以更改测试含义迁就方案。

Review 通过后向用户展示拟交付页面/功能/链路和可读用例，确认场景、预期与实际覆盖，不要求审阅选择器/测试代码。按[执行协议](../../dev-flow/references/execution-contract.md)保留确认来源、范围及文档版本/指纹。人工确认及后续实施计划 AI 复核通过才进入正式编码；已有有效 Review/确认直接复用，局部任务只补受影响范围。候选、浏览预览、Agent 自查都不等于人工确认。

采用[策略模板](../assets/templates/test-strategy.md)、[用户用例模板](../assets/templates/acceptance-cases.md)与[技术拆解模板](../assets/templates/technical-checks.md)，适配到项目原有位置。项目讨论提供用户用例预览及技术依据入口；不预览 Skill 方法代替验收方案。

## 变化后的回归

沿用户链路、模块依赖、API 消费方和数据所有权识别影响；选择原问题、变化规则、共享组件/契约消费方和核心链路回归。局部文案不默认触发整仓 E2E，接口/权限/存储变化需相应集成与链路。记录未执行的必要项和依据，不能以时间不足将必需项改为补充。

性能、可靠性、可访问性、兼容或 AI 效果仅在本次约定/实际风险成立时增加相应环境、数据与判据，复用已有专业工具。结论限定到测量/观察范围；最终验收同时采用功能证据和适用架构约束检查。
