# 文档 Review

面向一个明确候选或一组有关联的文档组织一次 Review。按产物选择专业角度，汇总问题与结论，不按角色分别创建 audit、review 和总结。本文规定评审方法，不替代专业规格、流程确认、实施授权或实际验收。

## 确定对象和依据

先定位项目索引、待评文档与差异，明确本次目标、文件范围、候选版本和所处阶段。未提交候选可记录基线提交及文件差异或内容指纹。区分新方案、现行事实更新和历史记录：新方案对照有效要求与约束；现行事实更新同时核对实际代码/配置/运行来源；历史记录保留当时版本与限制，不按最新实现改写过去结论。

读取相关用户要求、已确认决定、上游规格和必要工程事实。发现来源冲突时指出冲突与影响，不能自行把最新实现当成用户批准的业务规则。材料缺失且影响判断时保留待核验项，说明需要什么才能判断；不以猜测补齐。

评审前必须读取被评对象对应的有效模板，核对必要内容与裁剪依据；用户指定格式或项目有效模板优先。没有对应模板时按产物实际用途判断，不新造强制模板。模板完整性与专业正确性分别核对，缺项或无依据的裁剪列为修改项，不为填表扩大工作范围。产品正文还须让读者按功能理解使用者、入口、操作、结果及就近规则；不强制统一小标题或全局规则大表。

## 按产物选择检查重点

只启用本次对象需要的角度。下表是检查入口，不要求每类文档都生成，也不要求全部六职责参与。

| 产物 | 主要依据 | 重点检查 | 适用专业角度 |
| --- | --- | --- | --- |
| 产品规格、业务流程与规则 | 原用户任务、有效业务决定、既有规则 | 目标与范围是否一致；正常、拒绝、失败和恢复路径；状态、权限、数据含义；验收预期是否可观察；未决是否被误写成已确认 | 产品主评，研发反馈可行性，测试反馈可测性 |
| UI 规范、页面/组件规格、原型说明 | 产品规则、有效 UI 方案、设计系统及原型 | 入口和操作闭环；内容与状态覆盖；交互与业务语义；组件/布局/响应一致性；说明与实际原型是否对应 | 视觉与产品，研发核对落地约束 |
| 统一研发设计、架构或数据/API 变更方案 | 有效产品/UI 输入、当前总架构、真实代码和消费者 | 边界、依赖和调用链；契约、事务和一致性；失败恢复、兼容与迁移；方案复杂度与目标是否相称；验证及长期文档同步项 | 架构主评，产品/视觉核对需求承接，运维按交付影响参与 |
| 实施计划 | 已评审设计、真实工程基线、约定交付范围 | 任务是否覆盖设计；顺序和依赖是否可执行；接口/文件边界是否明确；集成、自测、必要冒烟及后续验收安排；有无遗漏或无关扩张 | 未主笔者复核，研发/架构为主，按影响补充 |
| 正式用例、测试策略 | 原要求、有效产品/设计、受影响范围 | 预期是否独立于实现；正常、边界、拒绝与恢复覆盖；操作和观察是否可执行；回归范围是否合理；不把未执行写成通过 | 测试主评，产品核对业务预期，研发提供环境约束 |
| 运行指南、部署/回退方案及交付说明 | 实际环境、构建配置、产物身份、已授权交付目标 | 命令与依赖能否复现；源/产物/环境对应；配置与秘密边界；健康检查、失败停止和恢复；本地通过与线上生效是否混淆 | 运维主评，研发/架构核对运行契约 |
| 项目现行总架构、产品/UI 正文及索引 | 有效决定、最终候选、真实实现与交付事实 | 是否完成本轮有效变化回写；现行/目标/历史是否清楚；是否重复维护同一事实；目录分类、索引、相对链接与替代关系是否正确 | 按正文专业选择，组织问题由文档维护者汇总 |
| Review、验收结论、收尾或工作交接 | 被评对象版本、原问题、真实执行记录及接收条件 | 结论能否追溯；修复是否覆盖原问题；未执行和限制是否明确；是否把自查写成独立通过；交接的接收方、责任及下一步是否真实 | 按结论对象选择，不能靠报告自证通过 |

跨产物检查同一规则是否一致，例如产品权限是否贯通 UI、API 设计及用例，数据变更是否贯通消费者、迁移和恢复。指出具体冲突位置，避免各文档分别通过而整体矛盾。

模板从对应专业入口按对象定位：[产品规格](../product-specification/SKILL.md)、[视觉规格](../../agents/assets/visual/design-spec.md)、[研发设计与计划](../../agents/assets/engineering/)、[架构文档](../../agents/assets/architecture/templates/)、[正式用例](../acceptance-case-design/SKILL.md)、[验收结论](../acceptance-execution/SKILL.md)、[交付与恢复](../release-and-recovery/SKILL.md)。仅读取本次被评对象的模板；已有技术 Review 使用[研发 Review 模板](../../agents/assets/engineering/engineering-review.md)承载统一记录，不另复制一份记录模板。

## 执行与证据

默认直接读取源文档、差异、必要代码和配置。涉及排版、图示可读性或原型实际行为时，再按[文档检查方式](../document-management/references/document-preview.md#选择检查方式)检查实际呈现。渲染通过只证明呈现，文档 Review 不能替代运行测试或正式验收。

按当前流程核对独立性：要求独立 Review 时，由未主笔对象的执行者评审；作者检查明确记为自查。需要多专业参与时，按宿主能力与授权组织，参与者返回发现，由一个维护者汇总；不为每位角色建立持久 audit 文件。人员不可用时如实保留覆盖或独立性缺口，不虚构参与记录。实际派发使用 subagent-coordination，本 Skill 不自动要求派发。

先核对事实和逻辑，再整理发现。每个有效问题包含：文件/章节、证据或冲突、具体影响、修订要求及是否阻断当前阶段。建议与必修问题分开，不把措辞喜好升级为阻断。没有发现问题时说明已覆盖范围及限制，不为凑数量制造意见。

## 一次 Review 的记录和复核

同一评审对象/候选集合保留一份 Review，包含：

- 对象、基线/候选版本、评审依据与实际覆盖的专业角度。
- 评审执行者及独立性；按问题组织发现，必要时标注专业来源。
- 问题编号、位置、依据、影响、修订要求、阻断性与处理状态。
- 综合结论：通过、需修改或待核验；未覆盖范围和进入下一阶段的限制。
- 修订候选及定向复核结果，保留原问题和关闭依据。

核查现状作为 Review 的输入或发现，不另设固定 audit 阶段，也不因角色数量增加报告数量。确有长期维护价值的现状地图按原专业权威位置维护，由 Review 引用。

相关文档集合可共用一份 Review；不同阶段或独立对象的评审仍保留各自版本关系，不把设计 Review 与实现 Review 合并成一次全程通过。正确问题按证据修订；错误建议经核验后记录不成立或不采纳及理由；模糊意见先澄清，证据不足保留待核验。修订后针对原问题及受影响内容复核；范围发生实质变化时补充评审范围和候选，不覆盖旧版本的结论。

正式跨职责 Review 按[文档协议](../document-management/references/document-contract.md)保存：技术设计/计划默认在迭代 `engineering/`，其他对象跟随对应专业目录或既有索引。简单自查可直接返回结论；逐次日志留本机目录。移动、合并文件时同步引用，不另建平行权威正文。
