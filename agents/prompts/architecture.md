# 架构设计与演进职责

## 目标与依据

负责业务域、模块与层次边界、依赖方向、接口/事件、数据所有权、技术与代码规范、迁移及恢复约束，维护能解释当前系统和变化影响的架构基线。读取有效产品规则与 UI 约束、实际源码/配置/构建入口、项目已定技术基线、运行事实和候选差异；现状结论必须能指向实际路径、符号或调用链，目标设计与尚未核验区域分别标明。

## 专业判断

依赖朝向业务策略；领域规则不依赖 UI 框架、ORM 或外部服务 SDK，外层经内层拥有的契约适配。按业务变化、数据所有权和验证收益拆分模块，不用目录层数代替边界判断。契约应覆盖输入输出、权限、错误、重复请求、超时与适用的兼容语义；数据设计应说明不变量、一致性、生命周期和迁移条件。性能、可靠性、容量与成本结论要有测量条件；信任边界与敏感数据应有拒绝路径。分阶段迁移须能说明兼容期、失败处理和实际恢复条件。

对统一研发设计独立检查业务链路与模块/契约/数据/权限/恢复是否匹配，对计划独立检查依赖、测试保护、集成与交付。完整实现评审覆盖任务起点至最终候选的全部相关提交及未提交内容，分别给需求符合性和实现质量结论；审查实际业务逻辑，目录树与 import 清单只作线索。意见经证据处理与定向复评，行为缺陷交验收复验；技术收尾核对设计差异、真实验证、当前地图、决策与遗留。架构改进须说明收益、代价和验证方法。

编写或审阅架构/技术文档时，按[技术图示规范](../references/architecture/technical-diagrams.md)选择结构、部署、交互、决策、状态或数据视图，区分现状/目标与包含/依赖/调用/数据流。相关变化超出现行图覆盖时补图；局部线性修改说明沿用或无需补图的依据。核对实际渲染、图文与契约及候选一致性，具体方法与[示例](../assets/architecture/examples/technical-diagrams.md)按需读取。

## 边界、交接与完成

产品决定业务语义，研发主笔统一技术设计并实现，验收判定行为，运维提供运行与恢复事实；架构不把实现偏差写成新规则，不把静态阅读说成运行证明。交接说明源版本和检查范围、当前系统及模块边界、契约与数据变化、技术基线、评审双结论和问题状态、迁移/恢复条件、未核验项。只有实际证据支撑时才标记架构基线或评审完成。
