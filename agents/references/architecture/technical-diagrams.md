# 架构与技术方案的图示规范

架构主责维护，研发、验收与运维按需引用。适用于架构设计、当前系统/模块地图、端到端技术方案及技术收尾；文档合并或拆分不改变本规范。图用于回答结构、交互、决策、状态或数据问题，正文解释原因、约束和取舍，表格承接职责与具体契约。

## 服务端架构视图

面对 API 服务、消息消费服务或后台任务，项目总架构维护下列完整视图和清单，迭代研发设计引用其有效版本并表达本轮变化；图中语义和核对标准一致，维护范围不同。总架构默认在 `docs/dev-flow/architecture/design.md` 或项目已有权威位置，所有迭代架构变化统一在本轮 `engineering/design.md`，重大调整也不另建迭代架构设计。收尾将最终实现且有效的分层、Service/Usecase、时序和 ER 等变化同步回总架构，记录前后版本、来源候选及核验覆盖；源码已实现与已部署/生产生效分开。现状核验地图是总架构章节或支撑资料，引用同范围权威图和清单，不另维护完整副本。

以本次影响为边界，迭代局部变化引用总架构有效图并补目标/变化部分，注明覆盖和未知，不重画整个服务；总架构尚未建立时明示缺口，收尾按实际可核验范围建立。可在同一文档内分节，复杂服务可按域拆支撑资料，由总架构总览关联，不平行复制权威资产。

### 整洁架构分层图与源码映射

按[整洁架构](clean-architecture.md)辨认接口适配、应用、领域、基础设施及装配入口，提供分层图和层次/职责/目录或关键符号映射。分层图使用 Mermaid，以分组和同层模块展示 Service/Usecase、领域规则、内层端口和外层实现的归属；源码依赖复杂时另画依赖图，分别说明端口实现和装配关系。源码依赖向内，运行中 Service 经端口调用持久化实现不代表内层依赖 ORM；不能只画 `Controller → Service → 数据库` 就声称完成整洁架构梳理。

框表示逻辑层/模块，与进程、部署服务的边界分开；Service 也不等于独立部署单元。物理目录可以合并，图中只画实际存在或明确设计的职责。现状有缺层、直接依赖或耦合时如实标出，并与目标图区分；不为了符合图例新增空目录、Repository 或转调层。

### Service / Usecase 业务操作清单

优先按应用 Service 组织业务能力；项目直接用 Usecase 时按真实名称与方法列出。至少记录：业务操作、入口/API/事件、责任 Service/Usecase 及方法、输入/结果/错误、领域规则与端口协作、源码位置、业务时序和模型/schema 引用。一个 Service 的多个操作分别可追踪；同一链路被多个入口复用时可引用同一时序。

区分应用 Service、领域服务和技术客户端。没有独立 Service/Usecase 时写出业务逻辑实际承接的接口/模块及限制，不能仅列 HTTP 路由或把不存在的层当作现状。

### 具体业务逻辑时序图

每条本次范围内核心 Service/Usecase 业务操作提供或引用时序图，参与者贯通入口、业务编排、领域规则、端口实际实现及相关数据/外部系统。消息表达具体动作和结果，例如“检查订单归属”“计算合计”“原子保存订单及明细”，避免仅写“处理业务”“调用 Service”。Service 内部关键判断可用自调用及 `alt`、`opt`、`loop` 表达，复杂算法再补流程图；流程图不替代核心业务时序。

按实际逻辑标出适用的身份与权限责任、校验/拒绝、状态或数据变化、事务边界与提交点、外部失败、超时/重试/补偿及返回结果。失败语义与契约一致，提交结果未知不能画成确定回滚；异步受理与最终成功分开。简单 getter、纯透传或与核心链路同构的操作可归组或说明裁剪依据，不机械地给每个方法画图；不能以“Service 在同一进程”省略其核心业务逻辑。

### 数据模型关系与 ER 图

设立数据模型关系小节，默认用 ER 图展示范围内核心实体、主键、适用外键、关系基数与可选性，并说明数据所有权、关键唯一/一致性约束及生命周期。区分领域模型与持久化模型，必要时说明映射；图中区分逻辑引用与实际数据库 FK，跨服务 ID 引用不能自动推导为跨库外键。

关联双方字段、联合键、多对多及外键/逻辑关联的具体表达见[ER 关系表达方法](../../../skills/technical-diagrams/references/diagram-method.md#er-关系的字段与约束)。

完整字段、类型、索引和迁移以权威 schema/模型定义为准，图只保留理解关系所需的属性。ER 图与时序中的读写对象、事务约束及 Service 的数据所有权对应；关系表不能替代应有的 ER 图。无持久化、无实体关联或非关系模型无法适当用 ER 表达时，在本节写明事实及依据，改用模型结构/嵌套关系图或表说明；不编造关联。局部仅加普通字段可引用有效 ER/schema 并解释影响。

上述要求随既有 Review 检查，不增加单独审批；[服务端三视图示例](../../assets/architecture/examples/technical-diagrams.md#服务端整洁架构分层与业务数据示例)只供改写，不能视为项目已有架构。

## 关键架构关系的无图阅读

**即使不看图，也能从正文或表格读出关键架构关系。**适用于结构/依赖图。不能把图示源码或图例当作关系说明；正文或表格须直接给出关键模块名称、关系类型、主体/对象与方向。无需枚举所有 import，覆盖当前范围中影响边界、依赖倒置和装配选择的关键关系即可。

| 关系类型 | 正文或表格必须说明 | 方向与事实边界 |
| --- | --- | --- |
| 分层与包含 | 模块属于哪一层/业务域，哪个容器包含哪些模块，各自职责、目录/关键符号 | 明写“模块A属于应用层”“服务进程包含A/B”；逻辑层、进程与部署归属分开，不靠上下位置推断 |
| 源码依赖 | 依赖方、被依赖模块/类型/函数端口、用途、源码依据及关键依赖限制 | 明写“A依赖B”或“A → B（源码依赖）”；区分实际依赖、允许依赖和禁止反向依赖，运行调用不自动证明源码导入 |
| 端口实现 | 实现者、所实现的端口、端口所属层/拥有者及源码符号 | 明写“外层实现A实现内层端口P，P由应用层拥有”；函数、对象结构、回调等按真实形态说明，无显式interface不强造类或接口 |
| 装配与注入 | 谁在何处创建/选择哪个实现或工厂，将其传给哪个消费方的参数/字段/边界，适用环境/选择条件及代码依据 | 明写“bootstrap创建A并传给Service的repository参数”；源码引用、创建/绑定、传入和运行调用分别说明，不能只写“依赖注入” |

用既有层次职责表配合关系清单，或等价完整的短段落；关系清单至少记录“关系类型、主体、关系对象、具体含义/注入目标与条件、依据及状态”。同一对模块若存在源码依赖、实现和注入等多种关系，分别表达。没有独立端口、装配根或注入时记录实际直接创建/全局取用等事实及适用说明，不为填表新增抽象；未经核验的参数名、条件或边保持未知/待核验，不从图中猜出代码事实。

图与配套文字/表格使用相同名称、覆盖、版本和现状/目标/未知状态，关联真实源码/有效设计。正文写出简短关键结论，详细关系可引用同一可访问文档链路中的权威章节及版本；不能仅留图片链接或“见图”。项目总架构及其支撑资料只维护一个现行关系来源；迭代研发设计引用基线并描述新增、调整、移除与沿用，收尾将图和文字关系一并同步，避免多份事实漂移。

Review 先暂时跳过图和 Mermaid 源码，只读正文/表格复原各层归属、谁依赖谁、谁实现什么、谁把什么传给谁，再对照图和代码/契约检查名称、关系类型、方向、条件及状态的双向一致性；文字缺失关键关系或与图冲突须修订。通过此检查说明文档提供了独立于图像的语义，不承诺所有 AI 会自动打开附件或引用。
