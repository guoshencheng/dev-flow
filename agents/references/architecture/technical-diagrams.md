# 架构与技术方案的图示规范

架构主责维护，研发、验收与运维按需引用。适用于架构设计、当前系统/模块地图、端到端技术方案及技术收尾；文档合并或拆分不改变本规范。图用于回答结构、交互、决策、状态或数据问题，正文解释原因、约束和取舍，表格承接职责与具体契约。

## 先确定问题，再选择图

先用一句话写出读者需要理解的问题，再按下表选图。同一主题有多个问题时分图表达，不将所有节点和关系塞进一张总图。

| 要回答的问题 / 适用触发 | 首选图 | 必须表达 | 裁剪与拆分 |
| --- | --- | --- | --- |
| 系统由什么组成，各部分在哪里、如何连接？新系统、跨端/服务/网络边界变化 | 分区、分层架构总览图 | 用户/外部系统、主要运行单元与职责、数据存储、包含边界、关键连接与协议 | 同层保持相近粒度；复杂系统按系统上下文 → 运行单元 → 局部组件逐层展开，只画本次需要的层级 |
| 某能力由哪些模块承担，允许怎样依赖？模块边界或依赖方向变化 | 模块/组件依赖图 | 模块职责、公开边界、源码依赖方向，必要的端口/实现与装配关系 | 与运行调用图区分；局部无结构变化时引用有效现状图即可 |
| 代码运行在哪些机器/进程，跨什么网络或信任边界？部署、连通、权限边界变化 | 部署拓扑图 | 环境、节点/进程、运行单元归属、网络/信任边界、连接发起方、协议与相关持久化 | 总览能清楚承载时合并；节点/副本/网络细节较多时单独画，不把逻辑模块当成独立部署单元 |
| 多个参与者按什么顺序协作，何时返回或异步完成？跨模块/服务调用、回调、事件、超时、重试或补偿是理解重点 | 时序图 | 触发者、参与者、消息顺序、关键响应、同步/异步语义、相关失败与恢复 | 每张聚焦一条业务链路；异步受理与最终成功分开，只有持久化后才能画提交成功 |
| 哪些条件决定走哪条路径？分支、校验、循环、人工操作或算法步骤是理解重点 | 流程图；职责交接重要时使用泳道 | 开始/结束、动作、判断条件、分支标签、失败/退出与重试去向 | 简单直线过程用有序文字即可；跨参与者的等待/先后问题优先时序图 |
| 对象有哪些稳定状态，哪些事件允许它转换？任务/订单/连接等生命周期或合法迁移变化 | 状态图 | 状态、事件/守卫条件、终态、失败/取消/恢复，适用时标明禁止转换 | 状态表示持续事实，动作写在转换上；不以流程图代替合法转换约束 |
| 数据归谁，实体之间怎样关联？新增/调整实体关系、基数或所有权 | ER 图 | 实体、主外键/关系、基数，必要的可空/唯一与拥有者说明 | 字段类型和校验以 schema 为准；仅增普通字段时直接引用 schema，不强制 ER 图 |
| 数据从哪里来，经过什么处理，在哪里保存或越过信任边界？转换、敏感数据或读写路径是重点 | 数据流图 | 数据源/汇、处理、存储、带数据含义和方向的连线、相关边界 | 数据流向不等于源码依赖或调用时序；不承担精确先后和事务语义 |

选图依据是关系语义与理解难点，不是文件数量或“技术方案必须放几张图”。命中表中触发且有效现状图不能覆盖时，应补图；局部、线性、边界清楚的修改可用文字/表格，并简短说明沿用图或无需补图的依据。服务端架构梳理须同时遵循下节的明确视图要求，不能以“结构未变”省略尚不存在的服务基线。不为低风险修改凑齐全套图。

同时存在复杂条件和多方协作时，以主问题选主图，必要时补另一视角。例如：时序图讲提交任务的跨端协作，状态图讲任务从排队到取消的合法转换。两图使用一致名称，并在正文交代彼此关联。

## 服务端架构视图

面对 API 服务、消息消费服务或后台任务，项目总架构维护下列完整视图和清单，迭代研发设计引用其有效版本并表达本轮变化；图中语义和核对标准一致，维护范围不同。总架构默认在 `docs/dev-flow/architecture/design.md` 或项目已有权威位置，所有迭代架构变化统一在本轮 `engineering/design.md`，重大调整也不另建迭代架构设计。收尾将最终实现且有效的分层、Service/Usecase、时序和 ER 等变化同步回总架构，记录前后版本、来源候选及核验覆盖；源码已实现与已部署/生产生效分开。现状核验地图是总架构章节或支撑资料，引用同范围权威图和清单，不另维护完整副本。

以本次影响为边界，迭代局部变化引用总架构有效图并补目标/变化部分，注明覆盖和未知，不重画整个服务；总架构尚未建立时明示缺口，收尾按实际可核验范围建立。可在同一文档内分节，复杂服务可按域拆支撑资料，由总架构总览关联，不平行复制权威资产。

### 整洁架构分层图与源码映射

按[整洁架构](clean-architecture.md)辨认接口适配、应用、领域、基础设施及装配入口，提供分层图和层次/职责/目录或关键符号映射。图中优先展示 Service/Usecase、领域规则、内层端口和外层实现；标明源码依赖、端口实现及注入关系。源码依赖向内，运行中 Service 经端口调用持久化实现不代表内层依赖 ORM；不能只画 `Controller → Service → 数据库` 就声称完成整洁架构梳理。

框表示逻辑层/模块，与进程、部署服务的边界分开；Service 也不等于独立部署单元。物理目录可以合并，图中只画实际存在或明确设计的职责。现状有缺层、直接依赖或耦合时如实标出，并与目标图区分；不为了符合图例新增空目录、Repository 或转调层。

### Service / Usecase 业务操作清单

优先按应用 Service 组织业务能力；项目直接用 Usecase 时按真实名称与方法列出。至少记录：业务操作、入口/API/事件、责任 Service/Usecase 及方法、输入/结果/错误、领域规则与端口协作、源码位置、业务时序和模型/schema 引用。一个 Service 的多个操作分别可追踪；同一链路被多个入口复用时可引用同一时序。

区分应用 Service、领域服务和技术客户端。没有独立 Service/Usecase 时写出业务逻辑实际承接的接口/模块及限制，不能仅列 HTTP 路由或把不存在的层当作现状。

### 具体业务逻辑时序图

每条本次范围内核心 Service/Usecase 业务操作提供或引用时序图，参与者贯通入口、业务编排、领域规则、端口实际实现及相关数据/外部系统。消息表达具体动作和结果，例如“检查订单归属”“计算合计”“原子保存订单及明细”，避免仅写“处理业务”“调用 Service”。Service 内部关键判断可用自调用及 `alt`、`opt`、`loop` 表达，复杂算法再补流程图；流程图不替代核心业务时序。

按实际逻辑标出适用的身份与权限责任、校验/拒绝、状态或数据变化、事务边界与提交点、外部失败、超时/重试/补偿及返回结果。失败语义与契约一致，提交结果未知不能画成确定回滚；异步受理与最终成功分开。简单 getter、纯透传或与核心链路同构的操作可归组或说明裁剪依据，不机械地给每个方法画图；不能以“Service 在同一进程”省略其核心业务逻辑。

### 数据模型关系与 ER 图

设立数据模型关系小节，默认用 ER 图展示范围内核心实体、主键、适用外键、关系基数与可选性，并说明数据所有权、关键唯一/一致性约束及生命周期。区分领域模型与持久化模型，必要时说明映射；图中区分逻辑引用与实际数据库 FK，跨服务 ID 引用不能自动推导为跨库外键。

完整字段、类型、索引和迁移以权威 schema/模型定义为准，图只保留理解关系所需的属性。ER 图与时序中的读写对象、事务约束及 Service 的数据所有权对应；关系表不能替代应有的 ER 图。无持久化、无实体关联或非关系模型无法适当用 ER 表达时，在本节写明事实及依据，改用模型结构/嵌套关系图或表说明；不编造关联。局部仅加普通字段可引用有效 ER/schema 并解释影响。

上述要求随既有 Review 检查，不增加单独审批；[服务端三视图示例](../../assets/architecture/examples/technical-diagrams.md#服务端整洁架构分层与业务数据示例)只供改写，不能视为项目已有架构。

## 架构总览的构图要求

分区、分层的容器框适合表达“公网控制面 → 内网执行端”等整体结构。外框表达真实包含或部署/信任边界，内框表达运行单元或模块；名称旁用短句说明职责。先呈现整体，再在正文或局部图展开关键模块。

- 区域标题写明边界含义，例如公网/内网、浏览器/服务端、进程或业务域。不要只写“上层/下层”，也不要把业务域、进程和机器的外框当成同一种边界。
- 嵌套只表示包含；上下排列只表示布局或分层。需要表达依赖、调用或数据流时明确画边并注明语义，不以位置代替关系。
- 同一层的节点粒度保持一致。总览可以在一个运行单元内展开关键组件，但必须标明它们属于内部模块，不能让读者误认为各自独立部署。
- 连接标明实际含义，例如“HTTPS：提交任务”“事件：任务完成”。有区分价值时标明协议、读写或同步/异步；不填无依据的技术细节。
- 连接发起方向、业务消息方向和响应方向分别表达。例如 Worker 主动建立 WSS，控制面可在已建立连接上派发任务；双向消息不能说明双方都开放入站端口。TLS 加密也不能自动推导为双向身份认证。
- 存储放在实际拥有/访问它的边界内，并画出读写者；数据库画在编排器下方不代表网关请求必须穿过数据库。外部服务放在对应外部边界，不省略影响方案的真实依赖。
- 使用有限的线型/颜色并配图例；颜色只辅助分类，名称、边框或标签也能表达含义。避免大面积装饰、交叉线和缩小文字；超出阅读宽度或连线难追踪时拆图。

参考图片的分区、层级和留白可以复用；其技术组件、协议和部署决定不能直接复制为项目事实。图的正确性优先于对参考外观的还原。

## 每张图的最小配套说明

图紧邻解释它的正文，在图题或相邻短段写明以下内容；已有文档元信息可以引用，不另建图示台账。

1. **问题、范围与状态**：图要回答什么；是现状、目标还是迁移中间态，适用哪个版本/范围。现状与目标宜并列分图；合图时明确标出新增、调整、移除和沿用。
2. **节点与连线语义**：框代表机器、进程、模块还是状态；箭头是源码依赖、运行调用、消息还是数据流；必要图例。响应、异步消息、实现关系的线型不得只靠读者猜测。
3. **依据与约束**：正文关联真实代码/配置、API/schema 或有效设计及相关 ARC/OUT/链路。候选和待验证连接明确标记；示意省略项写明，不把目标当作已实现事实。
4. **读图结论**：用一两句解释读者应理解的边界、关键路径、失败恢复或重要取舍。图不能替代接口定义、权限规则、事务边界和验证证据。

## 在文档中的放置与维护

| 文档位置 | 图示要求 |
| --- | --- |
| 项目总架构 / 迭代研发设计 | 总架构维护项目系统全貌及实际分层/清单/时序/ER；迭代引用输入版本，只描述本轮变化及目标图，收尾按实际结果回写总架构 |
| 核心业务链路 / 技术实现方案 | 按触发补时序图或流程图，连到最终可观察结果及相关失败恢复；生命周期或数据关系变化另补状态/ER 图 |
| 总架构现状核验与模块地图 | 作为总架构章节或支撑资料，引用权威图/清单并补源码/路径及核验覆盖；不另立同范围基线，不把静态阅读升级为运行证据 |
| 实现 Review / 技术收尾 | 对照最终候选复核图中边界、连线和状态；实际有效变化同步项目总架构及支撑资料，记录版本/范围/证据，未实现目标保留在迭代研发设计及明确目标区 |

默认优先可版本管理的 Mermaid 文本，现有项目工具更合适时沿用。流程/时序/状态/ER 等可直接嵌入 Markdown；嵌套布局难以清晰表达时可用可编辑 SVG、Draw.io 或其他项目工具，保留源码并关联同版本可查看的导出。不可只交付无法维护的截图，也不要求为简单图引入新绘图依赖。

复制图示时采用[技术图示示例](../../assets/architecture/examples/technical-diagrams.md)，替换为项目真实边界和契约，不能保留示例的虚构组件或行为。图示源码放在所属文档或相邻资源目录，遵守[项目文档协议](../../../skills/document-management/references/document-contract.md)，不在多个文档复制维护同一现状图。

修改后检查语法和相对资源/引用；新增或调整图的布局、类型、标签时在实际采用的渲染器中查看，确认中文、边界、箭头、文字和阅读宽度。语法通过只能证明可解析，不能证明布局清楚或技术正确。目标渲染器不支持时提供已核验的同版本 SVG/图片，明确限制。

## 图示 Review 检查

并入已有方案/实现 Review，不增加单独审批。检查并记录实际发现：

- 图型是否回答了本节的问题；需要补图的结构、交互、状态或关系是否仍隐藏在长段文字中？
- 现状/目标、部署/模块、包含/依赖/调用/数据流是否区分？同一节点在各图和正文中是否同名、同职责？
- 连线是否有依据，方向与语义是否正确？相关鉴权、提交点、异步最终结果、失败恢复是否与契约一致？
- 图是否与正文、模块表、schema 和实际候选一致？未知和省略是否明示，现状是否有来源？
- 服务端文档是否有可追踪的层次/源码映射、分层图、Service/Usecase 操作清单、核心业务时序和数据模型 ER 图或有依据的不适用说明？三种视图是否使用相同业务命名，并与操作入口、所有权和实际读写一致？
- 实际渲染是否可读，中文是否完整，标签是否截断，交叉线是否影响追踪？检查范围和未验证部分是否如实登记？

误导边界、通信/依赖方向、业务结果或状态转换的问题按实际影响阻断相应方案；修图不能代替补齐缺失契约或实现。只改排版且不影响理解的建议不扩大为新的审批门槛。
