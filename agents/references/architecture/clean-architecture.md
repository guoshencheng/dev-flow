# 整洁架构与细化拆分

整洁架构的基础是业务策略独立、源码依赖向内；跨边界的数据不携带外层框架类型，运行调用方向通过依赖倒置实现。层数可以变化。依据 [Robert C. Martin 的原始说明](https://blog.cleancoder.com/uncle-bob/2012/08/13/the-clean-architecture.html)。端口与适配器让同一应用通过不同入口、存储或测试驱动运行，见 [Alistair Cockburn 原文](https://alistair.cockburn.us/hexagonal-architecture)。下列拆分与项目维护方法是本体系的工程约定，按实际任务采用。

## 两个维度分别拆分

先识别业务能力及其拥有的规则、数据和用例，再描述每个模块承担的架构层次。业务域回答“负责哪类业务含义”，层回答“在策略与机制之间承担什么职责”。业务域、目录、进程和部署服务可以多对多，不因一张表或一个目录就宣布独立限界上下文，也不默认拆微服务。

拆分一个模块时给出：稳定 ID、职责及不负责事项、所属域/支撑能力、真实目录与入口、规则/用例、数据所有权、公开契约、允许依赖、验证入口。边界应使一种业务变化尽量在少量相关模块闭合；跨域重复修改、互相写表、循环依赖和无主规则是核查线索，结论还需源码和实际影响。

## 策略与机制的职责

| 部分 | 应负责 | 边界判断 |
| --- | --- | --- |
| 领域 `domain` | 业务概念、值对象、状态转换、不变量、计算和领域策略 | 不导入 UI/HTTP/ORM/SDK；纯函数也能承载领域规则，不强制类与聚合 |
| 应用 `application` | 用例编排、授权策略、事务/幂等要求、调用端口、业务结果 | 依赖领域与本层契约；不直接创建外部客户端，不依赖传输/存储对象 |
| 接口适配 `adapters` | Controller、Presenter、页面/ViewModel、外部数据转换、端口实现 | 将框架输入/输出转为内部语义；不隐藏应共享的业务不变量 |
| 基础设施 `infrastructure` | 持久化、消息/任务驱动、外部 SDK、配置与可观察性接入 | 技术实现满足端口；与适配层可按规模合并物理目录，职责仍可辨认 |
| 装配入口 `composition` | 创建依赖、注入实现、注册路由/任务、启动 | 可同时认识各层；不承载业务规则；无需为了注入引入 DI 容器 |

在本约定中，SQL/ORM 查询、存储映射属于外层持久化适配，可以位于 infrastructure 下。不要仅因命名不同就报告违规。源码依赖例如 `application → domain`、`adapters/infrastructure → application/domain`；内层通过自己需要的端口调用外层实现。端口按消费者的业务需要定义，在拥有该需要的内层维护，避免包罗所有底层方法的接口。

API DTO、数据库行、UI 表单值、领域对象用途分别明确；必要边界显式转换，简单稳定字段可复用但不得引入反向框架依赖。不能只把外层类型 `re-export` 到内层来声称解耦。错误与可重试结果在边界转换，底层异常不直接成为业务契约。

## 目录示例与跨域调用

有多个稳定业务能力的工程可参考下列局部结构；名称、语言和目录不是强制标准：

```text
src/
  modules/
    orders/                # 订单业务能力
      domain/              # 订单状态和不变量
      application/         # 下单、取消等用例及其端口
      adapters/            # 路由、页面映射或其他入口
      infrastructure/      # 存储、外部服务实现
      public.*             # 对外契约
    billing/               # 结算业务能力，有独立数据所有权
  platform/                # 运行技术能力；内层不反向引用其具体实现
  bootstrap/               # 装配与启动
```

跨域调用遵循声明的公开用例/事件/查询契约，不能直接导入另一域的存储实现、私有实体或写其数据。需要同步事务时先确定不变量和事务所有者；可靠事件、补偿、幂等只有在真实失败语义要求时采用。共享内核只收纳稳定且共同拥有的业务概念；无关工具和框架封装不要混入业务共享层。

## 不同工程的比例

- **React Web：** View/组件/Hooks 与展示状态处于外层；规则、用例可用普通 TypeScript 独立验证；网络、浏览器存储、第三方 SDK 通过适配使用。局部展示计算可以留在 UI，涉及使用限制、价格、授权和状态转换的规则按业务所有权放置。客户端权限显隐不能替代服务端执行授权。继续采用共同 Vite/React 和 Ant Design/shadcn 约定。
- **API、CLI、批处理或库：** HTTP/命令/任务都是入口，复用相同用例；库先辨认公开业务契约与插件/IO 适配，不制造没有用途的启动层。
- **小型 CRUD/原型：** 可以同文件组织独立函数和显式注入，仅分离实际业务策略与 IO；纯数据透传不强建 Repository、事件总线和四层空目录。仍保持明确数据拥有者和依赖方向。
- **遗留工程：** 先记录实际耦合及业务影响，新增/受影响逻辑遵守依赖规则，逐步围住旧实现形成适配边界。暂未消除的偏差登记范围、原因、风险和退出条件；不能把已确认约束静默豁免。

每个抽象说明它隔离哪种变化、如何验证、增加什么维护成本。仅以“符合模式”“目录更漂亮”为理由的重构不进入必需交付。针对本次范围选择实际 import/构建边界、独立用例测试、真实适配集成和数据/权限等检查；模拟可验证策略，实际适配可用性另行验证。
