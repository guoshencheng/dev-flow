# 〈功能名称〉实施计划

| 项目 | 内容 |
| --- | --- |
| 有效输入 | 〈产品、研发设计及重要决定的实际链接、版本与范围〉 |
| 方案 Review | 〈报告及对应结论、对象版本〉 |
| 计划版本与负责人 | 〈版本、日期、实际执行者〉 |
| 执行位置与基线 | 〈项目、工作目录、分支、开始基线及相关已有修改〉 |
| 总体进度 | 〈独立 Progress 的实际链接；计划不另记整体状态〉 |

本篇安排怎样实施，不重复六章研发设计。默认采用以下七章，内部表格按实际复杂度裁剪；单执行者或无 UI/数据变化时不制造空分工或空表。计划中的目标文件、接口、测试和分工标明尚未形成/派发，不冒称已有能力或实际结果。

## 一、实施目标与前置条件

用一段话说明本轮完整结果，引用业务完成标准、有效设计和最新范围决定。核对文档中的旧时点描述是否已被新授权或范围替代，不按旧稿继续扩建。

| 前置/边界 | 当前依据与实施要求 |
| --- | --- |
| 授权与交付 | 〈有效实施授权来源/范围，交付源码/产物/部署；外部动作依已有授权〉 |
| 工程与既有改动 | 〈实际入口、依赖、现有回归及需要保留的他人修改〉 |
| 环境与数据 | 〈必要服务、实际目标、配置来源、真实/替身边界及未满足条件〉 |
| 本轮支持与暂缓 | 〈最新范围、排除项、旧系统兼容是否需要，以及暂缓验证的后续入口〉 |

同范围有效授权直接复用，未取得的范围保持待实施；计划复核本身不新增人工技术审批。缺少条件时说明影响，继续不依赖它的已授权工作。

## 二、实施步骤与依赖

### 写入分工与接口先行

| 写入者/负责人 | 文件或模块边界 | 对外契约、依赖及集成责任 |
| --- | --- | --- |
| 〈实际或待派发执行者〉 | 〈唯一写入范围〉 | 〈交出的接口/数据/结果及接收方〉 |

多人协作时说明共享契约、生成文件及集成由谁维护，其他作者通过负责人协调，不覆盖他人改动。共享构建目录、服务、数据库或测试数据的变更指定操作负责人；需要独立 Review 时作者与评审者分离。实际派发方法按 subagent 协调执行，不把计划分工登记为已派发。

### 连续实施顺序

| 步骤 | 实施内容与依赖 | 主要文件/负责人 | 完成后可验证的结果 |
| --- | --- | --- | --- |
| 1 | 〈先稳定的契约或基础能力〉 | 〈真实/目标路径与写入者〉 | 〈可检查的业务或技术结果〉 |
| 2 | 〈依赖上一步的模块与适配〉 | 〈位置与写入者〉 | 〈接入实际装配后的结果〉 |
| 3 | 〈入口、消费者及完整集成〉 | 〈位置与集成责任〉 | 〈真实操作到持久结果/读取〉 |

步骤用于连续实现，不设置逐片正式验收或逐片人工批准。保持契约、服务、适配、入口和消费者的衔接；必要集成随实现进行，不等最后才发现未接入模块。

### 数据与兼容改造（适用时）

| 域/对象 | 必须落地的变化 | 顺序、恢复及验证要求 |
| --- | --- | --- |
| 〈本轮受影响数据〉 | 〈schema/关系/配置或明确无需存量转接〉 | 〈生成、迁移/切换或新数据验证；适用时安排回退〉 |

引用有效设计中的兼容取舍，区分旧系统存量、新系统后续历史和已有数据保留；不默认建设导入、双读双写或迁移框架。无需数据改造时删除本节。

### UI 与后端/消费者对接（适用时）

| 用户操作及入口 | DTO/API/事件、服务与写入者 | 集成后的可观察结果 |
| --- | --- | --- |
| 〈产品功能的真实操作〉 | 〈既有或目标入口、业务承接者〉 | 〈候选读取/选择/保存/生效/刷新读回，或消费者结果〉 |

用该表核对必要能力是否有真实操作和装配路径，不能只列存储字段或 helper。无 UI 时改为调用方/消费者对接；简单流程可引用设计对应章节，不重复完整接口定义。

## 三、测试保护与持续集成

| 覆盖目标/已有保护 | 新增或复用的检查 | 所需结果与边界 |
| --- | --- | --- |
| 〈关键业务行为、原缺陷或重要约束〉 | 〈测试位置、复现方式或实际操作〉 | 〈可观察通过标准、真实/模拟边界〉 |

| 检查入口与工作目录 | 执行条件/用途 |
| --- | --- |
| 〈实际命令或待形成路径〉 | 〈依赖、目标环境、定向/集成/全量覆盖〉 |

说明类型、构建、必要回归及主链路自测的时机和负责人，维护能发现目标问题的断言，不镜像实现堆测试。范围明确暂缓某类检查时选用不混入该类检查的入口，说明哪些结论仍不能给出；不直接照搬项目全量命令或固定测试数量。

多执行者共用运行资源时说明隔离与串行边界，测试前核实际进程/产物版本及数据目标，清理只处理自有资源。原始命令、退出码、候选及未覆盖在项目约定运行记录保留，本文写安排，不预填通过。用户本次指定的执行模型或限制属于实例安排，不固化到通用模板。

## 四、完整候选与验收安排

| 完整候选必须包含 | 形成条件 |
| --- | --- |
| 功能覆盖及实际装配 | 〈本轮必需用户操作/调用入口 → 服务/适配 → 持久化或外部结果 → 读取/消费者已贯通；引用第二章对接及设计，不另造正式 TC〉 |
| 核心行为与恢复 | 〈必要权限、拒绝、失败重试/结果未知及持久性自测达到有效设计标准〉 |
| 完整差异与自测 | 〈实际任务基线至当前候选及相关未提交内容、构建与必要检查、已知问题和未覆盖可定位〉 |
| 交付操作说明 | 〈代码/产物、配置与数据、启动/停止/恢复、实际入口和环境边界可复现〉 |

范围必需项未实现时继续开发；中断交接如实说明，不能把源码快照或检查目录名称当作完整候选。固定候选后，独立架构检查完整变更，验收依据原要求及有效设计维护正式用例并独立复核，开展本轮约定的验收及交付核验。完整 TC 不是实施前置，研发自测不代替正式验收。

关联缺陷组织修复，在新候选定向复评、复验及受影响回归；旧证据仅在业务预期、代码依赖和环境仍覆盖时复用并说明依据。暂缓或退出本轮的检查保留来源及适用性，不改写历史结果，也不按旧范围分母宣布当前验收通过。

## 五、计划 AI 复核引用

引用独立 Review 的计划轮次，注明对象版本、实际执行者、方式、覆盖、结论及未关闭问题。作者自查如实标记；实际复核通过及其他前置、有效实施授权成立后连续实施，不新增用户逐文件或逐片审批。

## 六、执行与重要调整

**当前进展引用：**〈唯一 Progress 中的当前步骤、候选与下一项责任〉。

**重要调整：**〈变化、原因、有效来源与影响范围〉。内部步骤调整更新本计划；业务、重要契约或交付变化先同步受影响产品/研发设计和必要 Review/确认，再实施受影响范围。最新范围及时替代旧执行要求，不靠交接文本独自承担新决定；原记录保留，已有回归/TC 按影响维护。

**交接：**〈实际交出方、接收方及下一动作〉。提供最终源码/候选、模块/接口/数据变化、自测与未覆盖、运行和遗留，供架构技术收尾、验收与运维接续；工作中断与完整候选交接分别表达，不预填完成。

## 七、引用与关联文档

- 产品规格、原始决定与追溯：〈实际链接、版本及范围〉。
- 六章研发设计、字段字典及方案 Review：〈实际链接及有效结论〉。
- 项目总架构、已有测试与运行依据：〈实际入口及适用部分〉。
- 计划复核、唯一 Progress、后置正式用例及架构技术收尾：〈已形成的实际入口；未形成保留真实状态〉。

模板路径采用时替换为项目实际相对链接；引用权威来源，不复制第二份设计、总体状态或原始日志。计划编制、派发、代码完成、自测、正式验收及部署分别判断。
