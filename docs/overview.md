# dev-flow 总纲概述

更新日期：2026-10-21。对应[总纲 v0.29](../skills/dev-flow/references/constitution.md)。

dev-flow 是以 Codex 为主的多角色研发协作体系，目标是逐步替代 superpowers，形成稳定、高效的研发 harness，交付符合用户要求的成果。协议覆盖需求、设计、实现、测试、交付、运行、维护与退役；不同研发对象和任务种类通过可扩展路径逐步支持，并分别记录已定义和实际验证的能力。

## 协作结构

主 Agent 维护目标与范围、选择工作路径、协调依赖和冲突、综合证据并推进交付。六类专业职责按当前任务需要参与：

| 职责 | 核心责任 |
| --- | --- |
| 产品与交互 | 用户任务、信息架构、流程与交互状态、业务规则和验收目标 |
| 视觉设计 | 布局、Tokens、组件及其状态、设计系统与实际渲染检查 |
| 架构 | 整洁架构、技术与代码规范基线、业务域和模块契约、代码业务复核、研发复盘与现状维护 |
| 研发 | 设计期实际代码/成本反馈、统一架构与实现设计、独立计划/AI 复核、连续实现和自测修复 |
| 测试验收 | 完整实现后依据原业务预期/有效设计维护正式用例，独立 Review 后执行验收、交付核验和复验 |
| 运维与交付 | 启动、安装、发布、运行观察、恢复与退役 |

总纲提供共同协议；专业 Skills 承载职责方法；主 Agent 协调完整进度与集成，标准跨职责专业工作默认由实际可用且允许的 Harness subagent 执行；项目保存自己的有效知识与长期资产。核心协议保持工具无关，Codex 的会话设置、委派能力和工具接入由宿主适配，流程不要求原生角色注册。

## 三个首要交付目标

1. **严肃的 UI 与交互设计。** 明确真实用户任务、相关界面状态与异常恢复，设计与实现相互关联，分别用实际操作和实际渲染验证。
2. **连续实现与整体验收。** 研发持续集成和自测，完整候选再集中实现 Review 与正式验收；具体问题即时反馈，按关联范围批量修复并定向复评、复验，最后核验整体交付。
3. **准确的端到端交付。** 按本次范围交付可启动源码、可安装产物或实际部署，在干净工作副本或目标环境完成核心用户任务。规划或评审任务以对应成果验收结束。

路径按任务种类、风险和阶段裁剪。实施中发现需求变化时，先进入受影响部分的需求变更闸门，更新规则、统一研发设计和计划；已有用例同步受影响部分，尚未形成的正式用例在完整候选后维护，再恢复受影响实现；共享文件或接口有明确写入责任，独立任务在可控范围内并行，集成成果重新验收。证据对应当前候选版本，未执行、失效与未知结果明确记录。用户需要作出关键决定时提出具体问题，已有授权范围内持续推进。

完整功能依次为：建立覆盖最终目标的整体进度 → 产品/UI 候选与真实代码技术反馈 → 研发统一架构/实现设计及独立跨职责 Review → 业务完成标准和重要取舍确认 → 独立实施计划/AI 复核及有效范围授权 → 连续实现、集成、自测 → 完整候选实现 Review、正式验收用例维护/独立 Review → 验收执行与交付核验 → 关联修复及定向复评/复验 → 架构技术收尾与整体结束。技术在产品/UI 确认前比较入口、形式和状态的实际代价，产品/视觉回应业务价值；任何职责都不能单方改动已确认业务。正式完整 TC 不再是实施前置，研发测试保护仍持续；用例预期来自原要求，不能迁就代码。具体规则见[执行协议](../skills/dev-flow/references/execution-contract.md)。

本轮研发技术文档由 `engineering/design.md` 统一主笔架构与实现，`engineering/review.md`、`engineering/implementation-plan.md`、`architecture/closeout.md` 各自独立，主设计关联有效版本与结论。总体阶段由一个 Todo/持久 Progress 或既有索引维护，包含尚未开始的后续工作、当前目标和下一步，其他文档仅引用/投影。旧项目有效权威可映射复用，不强迫复制或重命名。

内部切片不作为独立交付验收门槛。主会话派发后继续执行、集成或实际等待，不能因阶段结果或等待超时提前结束。验证采用必要记录和已有工具，历史整理与无关工具维护默认后置。本次规则已有安装、原生派发及隔离代表场景证据；真实业务 UI 项目的完整执行效果仍待验证。

首次正式实现前展示具体范围、结果、验证和交付并取得用户同意，快速路径也不得省略；标准路径可将实施授权明确合并到设计确认。已有同一范围授权持续有效，内部技术计划仍由 AI 复核。Plugin 0.2.0 的状态核验会检查授权是否关联有效范围，但没有宿主强制拦截；影响与证据见[本轮记录](../reviews/2026-10-12-implementation-authorization.md)。

## 持续建设与项目沉淀

正常交付包含代码与文档收尾，也可直接说“开始收尾”补做。[收尾入口](../skills/dev-flow/references/document-archive.md#一条指令收尾当前迭代)恢复当前项目和本轮，按[代码收尾](../skills/dev-flow/references/git-and-worktree.md#代码收尾)整理实现、完整 Review、必要验证与相关成果保存，并同步资产、总结、遗留和入口；无其他约定时形成本地提交，远端动作按已有授权执行，核验后逻辑归档。明确仅文档整理时裁剪代码动作，缺少必需结果时保留真实未完成状态。

每个职责和体系部分持续维护专业方法、能力现状、验证案例与改进待办。每个项目持续保存产品规则、交互与设计系统、架构契约、工程与回归资产、启动与运行方式：任务开始读取并核验，过程中更新；用户可以手动触发架构与测试联合维护检查，也可以授权定期检查；检查后把最新有效架构和稳定回归用例同步到项目级当前基线，再对迭代和被替代候选做逻辑归档，下一任务实际复用。通用经验经过适用范围和行为验证后再进入 Skills 或工具。

主 Agent 先明确当前业务项目，在[项目文档索引](../skills/dev-flow/references/design-document-contract.md)定位产品、交互原型、设计/UI、技术及相关验收/交付资料的实际位置、状态与版本。设计讨论和确认通过该项目的文档与原型入口提供预览，Skill 保留通用方法和工具，项目成果保存在所属项目；维护 Skill 默认不逐篇预览其参考文件。

架构在相关实施变化和交付后参与，依据实际源码核对业务规则、依赖与数据所有权，更新目录模块地图、职责及业务域/层次，给出有证据的合理性评价与改动建议。局部修复按影响裁剪，必需偏差继续修复，可选演进入待办；现状、目标和未知分别维护。
