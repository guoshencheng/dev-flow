# 产品与交互 Agent v0.4

日期：2026-10-07。原生名称：`dev_product`。专业 Skill：`dev-product`。模型与推理强度采用用户本次指定、宿主派发默认或父会话设置，职责文件省略固定值。

## 为什么先与视觉职责分开

产品与交互负责用户任务、信息架构、页面语义、操作与状态、业务规则和验收目标。视觉负责布局、Tokens、组件呈现、响应规则与实际渲染。两者共同负责用户体验，视觉反馈可以推动产品改进，产品也可以用线框或原型表达交互。

分开的作用是明确问题归属和交接质量，逐个增强专业能力。小而清晰的修改允许同一执行者承担两类职责，保留交互预期与视觉依据；不要求每次任务都启动两个 Agent。当前建设产品职责，视觉配置按总纲下一步建设。

## 可操作原型、设计参考与复用

v0.4 明确[HTML 原型与设计稿指南](../skills/dev-product/references/html-prototyping.md)的默认流程：AI 根据本次需求构建或修改页面，选择现成 HTTP 工具、项目开发服务或必要的框架脚手架，实际启动、查看与讨论，再按反馈持续修改。优先复用项目工程；独立静态页面可直接使用 Python 标准库 HTTP 服务。静态设计稿检查渲染，可操作原型还需检查核心行为。

v0.3 提供的[示例工具](../skills/dev-product/scripts/prototype.py)保留为可选起点。内置 C 端预约与 B 端批量任务，支持确认方案对比、状态切换、模拟提交、异常恢复与反馈 JSON；所有示例均为候选和模拟。项目页面按本次目标生成，不要求沿用示例业务、布局、讨论面板或反馈导出功能。

[参考研究与方案创造](../skills/dev-product/references/reference-research-and-ideation.md)提供按问题搜索、实际任务拆解、机制比较和候选验证的方法。[C/B 端设计指导](../skills/dev-product/references/consumer-and-business-design.md)从任务、频率、熟练度、数据、权限与错误成本选择模式。[项目资产协议](../skills/dev-product/references/project-assets.md)补齐参考、原型、反馈、决定、模式和验收的关联、失效与跨任务复用。

随包示例服务只发布原型 public/ 目录，其反馈需要复制或下载保存到项目；其他工程可直接在项目文档记录反馈。设计讨论以任务和待决问题为起点，经过实际查看或操作与反馈更新页面，再将有效决定写回权威规格；用户界面偏好、原型操作、真实用户证据与生产验收分别记录。

## 建设验收

配置与专业 Skill 静态检查后，分别验证宿主加载与实际行为。使用连续的隔离项目案例检查初次设计、写入边界、未验证事实的报告，以及新上下文对既有规格的复用和变更核验。对应案例与结果保存在 `evals/dev-product/`，保留实际调用方式和局限。

角色发现与模型选择需要原生派发证据；使用主 Agent 或通用子 Agent 读取同一专业 Skill，只能证明专业指导在该执行方式下的行为，不能代替原生角色加载验证。产品设计产物通过，也不表示真实界面或用户可用性已通过。

## 调用与后续建设

使用 `$dev-flow` 组织协作，产品任务读取 `$dev-product`。当前可通过专业 Skill 执行；原生 `dev_product` 需要在目标宿主完成发现、派发和实际模型设置核验。全局源文件通过链接维护，代码与具体项目知识仍保存在各项目。

下一次真实项目试点应提供现有界面、工程入口和实际运行条件，检查设计是否能被视觉、研发和测试持续反馈修正。后续建设视觉 Agent，采用相同的配置、专业指导、资产协议和行为验证结构。
