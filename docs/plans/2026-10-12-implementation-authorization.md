# 实施授权与流程裁剪调整

## 目标、范围与确认

本轮基线为 `fbb81fdf0195ef635d71625516a39d0915cde912`，开始时工作区干净，任务分支 `codex/implementation-authorization`。主 Agent 单独维护共同协议、研发入口、状态核验器、模板示例、测试与交接；未委派，不登记独立 Review。

用户先要求评估流程判断，随后确定：即使判断可以走快速路径直接实施，也要先取得人工同意。已展示候选规则为“判断路径 → 准备方案并核对前置 → 展示实施摘要 → 用户同意 → 正式实现”；标准路径可明确合并确认，已有实施授权持续有效，关键范围变化只重确认受影响部分。用户回复“好，继续推进”，授权本轮规则落实及按仓库约定验证、更新本机插件。

## 方案与验收预期

1. 先按行为、交互和契约变化判断路径，再按规模和可逆性裁剪；新增且未确定的行为不能归为内部实现选择。快速路径须引用具体有效基线与验证依据。
2. 首次正式实现必须有明确实施授权。摘要包含路径依据、具体范围、预期结果、验证和交付；需求表达或单项设计答复不自动授权实施。准备、研究和诊断可继续，正式实现等待同意。
3. 标准路径可以在设计/用例确认答复中明确包含开始实施；计划仍只经 AI 复核。已获授权的同一范围、普通修复和跨会话恢复不重复询问；行为、重要契约或范围变化更新受影响输入与授权。
4. 在现有 confirmation gate 增加 `authorizes` 范围 ID 列表；实施前依赖必须关联有效、passed 的授权确认。普通设计确认、AI Review、无关范围确认、未纳入实施前依赖或标为不适用均不能替代。输入版本失效仍按现有机制阻断；工具不解释用户原话、不证明实际语义、不拦截操作。
5. 占位模板保持 pending；示例提供合成授权记录；只评审/文档探索且不包含正式实现的范围无需实施授权。旧状态 schema 仍为 1，缺少显式授权会保持未就绪，不能倒填历史同意。

## 实施顺序与验证

先新增授权缺失、无效/未关联、混合范围与合并/历史授权的测试并取得目标失败，再修改核验器；同步共同协议、研发方法和示例，运行阶段与隔离安装测试。补充快速路径与新增行为的行为评测输入，未执行的模型行为保持 not-run。

发布候选使用 Plugin 0.2.0、总纲 v0.25、执行协议 v0.12；不兼容影响是正式实现的核验新增授权前置，旧记录须引用真实实施同意或等待答复。同步两端清单与职责入口，新文件纳入 Git 后执行打包、安装和 check。Kimi 清单随包同步，原生安装/重载未执行时如实报告。

## 实施前 AI 自查

对象为上述方案与本轮现行代码/协议，执行者为主 Agent，自查方式。核对了正常需求/局部修复的路由、确认 source/quote/coverage 与依赖机制、合并确认和有效历史复用、无正式实现范围、安装版本与源码指纹流程。发现现有快速路径条件偏宽且核验器只检查已声明前置；通过优先级说明和必需授权检查补齐。保留技术方案/计划的 AI Review，不增加内部技术文件人工审批。无尚未处理的阻断项，本轮实现可开始。
