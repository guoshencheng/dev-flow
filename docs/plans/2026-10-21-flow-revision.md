# 研发协作新流程

本方案承接本轮已确定的四篇文档结构，并按最新要求调整执行节奏：产品/UI 设计期间加入基于现有技术和代码的交叉 Review；专业工作默认更多派发给 Harness 原生 subagent；完整功能实现后再维护、Review 并执行正式验收用例，包含交付核验；通过 Todo 或 Progress.md 保持可恢复的总体进度。

本方案已用于实际改造；源码、安装和验证结果分别保存。完整范围与当前状态统一从[整体计划与进度](2026-10-21-flow-revision/Progress.md)恢复，涵盖方案、插件改造、验证、安装、运行验证和收尾。

## 一、完整功能的执行顺序

| 阶段 | 执行与交叉 Review | 产出及进入下一阶段的条件 |
| --- | --- | --- |
| 1. 建立全局进度与恢复基线 | 主 Agent 确定任务场景、交付范围、当前阶段、已有成果与未知；派发技术执行者检查实际代码和工程入口 | Todo/Progress 展示完整阶段、当前目标、下一步和负责人；已有基线先核实再复用 |
| 2. 产品/UI 候选与技术反馈 | 产品分析业务目标和行为，视觉细化布局/交互；技术基于真实模块、组件、接口和状态管理比较候选形式与成本，产品/UI 修订 | 经跨职责讨论的候选；重要取舍有事实与替代方案，业务完成标准清楚 |
| 3. 研发设计与交叉 Review | 研发在一篇设计中编写架构与实现方案；独立架构执行者 Review，产品/UI 核对业务目标、行为与呈现承接 | 独立 Review 文档记录意见、处理与结论；阻断项关闭，用户确认受影响的业务规则、边界、可观察完成标准、适用体验与重要取舍；已有有效决定直接复用 |
| 4. 实施计划与实施授权 | 研发独立编写计划；架构复核依赖、变更范围、测试保护和交付可行性 | 独立计划及有效 Review；已有同一范围授权复用，必要授权可与设计确认明确合并；完整 TC 不再是实施前置 |
| 5. 连续实现、集成与研发自测 | 研发按稳定契约分派可独立实现的工作；集成、自测和必要回归随实现持续进行，主 Agent 维护整体状态 | 完整功能已实现、已集成、核心任务可运行且研发必要自测通过，形成可追溯候选 |
| 6. 实现 Review 与正式验收用例维护 | 独立架构执行者 Review 完整代码变化；测试基于原产品、有效设计和完整候选维护正式验收用例；产品/UI 核对业务覆盖、实际体验及状态必要性 | 评审与用例均绑定版本；用例经独立 AI Review，遗漏回查原需求；实现只提供执行路径，不能决定正确预期 |
| 7. 验收执行与交付核验 | 测试执行界面/API/数据及适用的真实 E2E；运维准备并核验约定启动、产物或部署；测试执行交付相关用例 | 功能验收与交付核验均有当前候选证据；具体问题反馈研发并复验，不能用“功能实现完成”代替交付通过 |
| 8. 架构技术收尾与整体结束 | 架构独立形成技术收尾，核对设计差异、Review/验收/交付结果和长期资产；主 Agent 集成结果并保存、总结及按条件归档 | 主设计引用有效 Review、计划和收尾；遗留有承接；必需结果闭合后才结束整体任务 |

相关工作在输入稳定且无写入/环境冲突时可以并行。例如产品调研与技术基线调查、完整候选的实现 Review 与验收用例维护。正式验收执行依赖有效用例及可运行候选；需要目标环境或产物的交付用例等相应交付对象就绪后执行。

发现问题后沿“证据 → 对应职责处理 → 修订候选 → 定向复评/复验 → 更新整体结论”循环。变更业务结果、恢复方式或重要契约时先更新受影响设计与决定，再继续受影响实现；待维护的正式 TC 在实现完成后据有效基线补齐，已存在的回归/TC 则同步受影响部分。

## 二、跨职责 Review 如何落到具体问题

### 产品/UI 设计时，技术提前检查

技术执行者必须实际读取受影响代码与工程约束，说明检查范围和版本，至少回答：

- 功能放在不同入口、页面或交互形式中，分别需要修改哪些模块、接口和共享状态？
- 哪个方案能够复用现有组件和链路，哪个方案引入新的跨页同步、异步协调、持久化或迁移？
- 每个新增状态是否由真实业务、请求、数据或权限条件触发，用户是否需要据此采取不同操作？
- 成本、复杂度和维护影响来自什么事实，替代方案是否仍满足业务目标与可访问性等现行要求？

例如同一项编辑能力，“在已有详情页复用编辑器”与“在列表中支持多行同时编辑”可能涉及不同的数据加载、草稿拥有者与并发保存设计。技术应指出具体差异和依据，产品/UI 据此比较业务收益与实现成本，而不是只得到“都能做”的结论。

### 状态 UI 的必要性共同判断

对有争议的状态，记录触发条件、用户价值、操作差异、实现成本与建议。视觉/产品提出状态的业务或交互理由，技术说明真实系统是否存在该状态及如何实现。

没有真实触发、没有决策价值且只增加复杂度的设计可以合并或移除；实际等待、错误、权限拒绝、数据保留和恢复等必要反馈要有完整承接。技术建议调整入口或交互时，同时给出满足原目标的替代方案。改变用户已确认行为或重要约束时，由用户决定受影响部分，任何职责都不能单方面缩减需求。

### 技术方案与最终实现也接受业务视角核对

- 研发设计：架构检查结构与契约；产品检查是否达成业务目标、是否遗漏功能与恢复；视觉检查页面/状态与组件承接。
- 完整实现：架构检查完整差异；产品检查实际流程与功能透出；视觉检查真实渲染和交互；测试验证可观察结果。
- 交付与收尾：运维提供实际运行事实，测试给出验收/交付核验结果，架构整合技术一致性与长期资产，主 Agent 综合整体完成条件。

每条 Review 明确对象版本、执行者、事实、影响、建议、处理结果和定向复核。发现写到独立 Review 文档，由主文档引用；独立 Review 持久保存重要发现、结论及未关闭项；普通运行日志与逐次重试过程留在本机目录，不将“过程默认本机”解释成不保存本轮正式 Review。结论有分歧时依据目标、代码和实际证据解决，重要取舍才交用户决定。

## 三、默认使用 Harness 原生 subagent

### 主会话与专业执行分工

主 Agent 负责总体进度、范围、依赖、用户决定、派发、集成和最终完成判断。标准功能、跨职责任务中的产品研究、UI 设计、技术调查、研发设计、独立 Review、验收与架构收尾，在宿主可用且允许委派时默认交给专业 subagent，覆盖设计到收尾各阶段。主会话直接完成明确的局部编辑、协调与集成；对大任务选择不委派时，在进度记录说明具体原因。

当前会话使用实际提供的 Harness `collaboration` 能力。通用协议按宿主实际工具派发；无法使用时明确记录降级和独立性缺口，不以角色名称冒充独立执行。

### 派发与上下文控制

- 按职责和对象分派，提供原始目标、必要 Skill/文件路径、有效版本、待回答问题、可写边界、成果位置与完成条件。
- 优先传递精简任务包与权威文件位置，让执行者直接读取必要原文，避免默认继承整段聊天历史；主会话接收结论、依据、产物链接、问题与下一步的简短回报。
- 同一领域执行者可按需复用；正式评审自己未参与编写的对象时采用独立上下文。设计、计划和代码的作者不能把自身检查登记为独立 Review。用户明确要求独立评审而宿主无法提供时保留待评审状态，不能用自查替代通过。
- 同一文件明确唯一写入者；评审者先只读并提供发现，作者修订后由评审者复核。跨文档结果由协调者更新主设计引用，避免多个执行者争写同一入口。
- 依据实际槽位控制并发。依赖任务顺序推进，可分离任务并行；共享分支、端口、数据和发布目标分别有负责人。
- 派发、等待超时或单个子任务完成不是主任务结束；主 Agent 继续独立工作、集成或调用宿主等待工具，核验子任务成果后推进下一阶段。

## 四、正式验收用例后置

### 实施前固定的内容

产品/研发设计中明确业务目标、关键规则、边界、可观察的完成标准及交付形态，实施前取得受影响业务预期的有效确认，已有确认直接复用；必要风险先调查或做受控实验。研发计划说明自测与回归方式。实施前不要求测试职责先维护完整正式用例、操作步骤、数据与自动化，也不再等待一轮完整 TC 人工确认。

### 实现后维护与执行的内容

测试面对完整候选，先读取原要求及有效设计，再检查实际入口和实现，维护正常、边界、拒绝、异常恢复、必要回归及交付用例；用例的预期必须回指原规则。独立 AI Review 检查业务覆盖、执行可行性和证据层级，通过后执行。

既有明确预期内的用例细化由测试维护并 Review，不新增例行人工审批。发现原规则有歧义、新行为或与确认预期冲突时，明确待决事项并只确认受影响部分，其他独立检查继续。需要用户亲自体验的最终验收按原约定保留。

研发的局部测试、缺陷复现、契约检查和回归继续随实现开展；正式验收用例后置不代表全部测试后置。测试可以提前提供可测性意见或准备通用环境，不把这些准备变成新的实施门槛。

正式用例、Review、验收执行和交付核验分别有状态。未覆盖、失败、阻断和跳过均保持真实记录；当前候选必需检查未闭合不能完成。候选变化后按影响复评/复验，不能把旧候选通过直接用于新版本。

## 五、按场景裁剪执行框架

| 场景 | 默认执行框架 | Subagent 与进度管理 |
| --- | --- | --- |
| 完整新功能/多端交互 | 产品/UI 与技术交叉 Review → 统一研发设计/Review → 计划/复核 → 实施 → 正式用例维护/Review → 验收及交付 → 架构收尾 | 按领域实际派发，作者与关键评审分离；维护完整阶段 Progress |
| 基线内缺陷修复 | 复现/诊断 → 简短修复计划/复核 → 修复与自测 → 补齐必要验收用例并复验/交付 → 定向资产更新 | 研发执行，独立 Review/复验按风险分派；短任务用 Todo 或简短 Progress，复杂根因增加调查任务 |
| 局部文案/样式/内部重构 | 引用有效预期 → 影响分析与相关职责核对 → 修改 → 定向检查/交付 | 按收益使用执行者和评审者，不启动全套六职责；沿用有效文档，不生成空模板 |
| 数据迁移/重要契约变化 | 在标准流程上增加契约、消费者、兼容/切换/恢复设计及关键风险验证 | 架构、研发、运维/测试按边界参与；关键可行性/恢复实验可以提前，正式整体验收仍在完整候选后 |
| 运行故障 | 恢复当前服务并核验 → 定位根因 → 修复与回归/交付 → 复盘承接 | 一个操作负责人，独立调查可并行；Progress 显示影响、恢复状态、下一步与未完成修复 |
| 探索、流程设计与纯文档 | 问题/目标 → 专业调查 → 综合方案 → 独立 Review → 内容/引用或实验验证与交接 | 按专业问题分派；记录当前讨论/验证边界，不虚构实现或生产验收 |

## 六、Todo 与 Progress.md 的管理方式

### 先选一个状态权威

开始时探测当前 Harness 实际可用的任务管理能力。单会话短任务有可用 Todo 时直接维护 Todo；没有时使用简短 Progress.md。多阶段、大功能、跨会话任务默认用本轮 `Progress.md` 作为持久恢复入口，原索引链接它；原生 Todo 如同时使用，只投影当前行动，不再人工维护第二套总体状态。设计主文档、实施计划中的当前阶段/执行进展同样只引用或由该权威投影；文档本身的候选/有效状态与 Review 结论仍在各自原记录维护，不能混同为任务进度。

当前会话可用原生 subagent，未发现可用的原生 Todo 更新工具，因此本轮实际使用 Progress.md。不能把聊天正文或不存在的 Todo 工具当成已建立进度管理。

采用现有结构化状态核验时，状态块与相关版本统一放在选定的权威文件，由索引引用；核验器读取实际权威路径。若宿主或现有工具只接受索引路径，则保留索引为权威，把 Progress/Todo 用作生成或引用视图，不能复制两套人工维护状态。源码已确认 `check_iteration.py` 接受显式 Markdown/JSON 路径，未硬编码 index 文件名；落地时仍需补 Progress 路径夹具和新流程依赖回归。

### 开始就展示全局

进度范围对齐用户的最终目标，并覆盖从当前起点到最终交付与验证的完整工作；不得只列本次回复已经完成的事项。阶段完成和整体完成分别判断，尚未开展的后续工作必须保留为待开始。

先列完整大阶段并判断哪些已有有效结果、当前在哪里、哪些不适用或有未知。尚待调查写“待核验”，不为完整框架预先宣布完成。若任务起点不在设计阶段，直接恢复已验证前置和剩余工作。

### 每次阶段变化都更新

派发/回报、阶段切换、确认、阻塞、候选或有效基线变化、修复复验，以及结束前均更新当前目标和下一步。依据完成条件与实际来源切换状态，不能只把执行者的“完成”照搬为整体完成。

最小格式如下，路径采用项目现行文档约定：

```markdown

- 当前阶段及阶段目标：……
- 当前动作与执行者：……
- 下一步及进入条件：……
- 阻塞/待决、需要用户处理的事项：……

## 总体里程碑（列出全部阶段，包含尚未开始的后续工作）
| 阶段 | 状态 | 负责人 | 完成条件与有效成果 |
| --- | --- | --- | --- |
| 设计与技术反馈 | …… | …… | …… |
| 研发设计/Review | …… | …… | …… |
| 计划/复核 | …… | …… | …… |
| 实现与自测 | …… | …… | …… |
| 正式用例/Review、验收及交付核验 | …… | …… | …… |
```

## 八、从现行插件切换时的改造范围
