# UI 方案确认与实施边界设计

本稿版本 1，依据用户对多个 UI 改动未确认案例的反馈及本会话“继续推进”授权形成。总体状态见 [Progress](../Progress.md)，计划见 [实施计划](implementation-plan.md)，[独立 Review D1](review.md#design-r1)已通过。插件的流程架构权威为 [总纲](../../../../skills/dev-flow/references/constitution.md)，职责维护源为 `agents/prompts/`；没有独立项目总架构，本轮仅核对现有流程/职责/核验边界。

## 一、本次要完成什么

新增或改变 UI 方案时，用户应在对应正式实现前看到可审阅候选并决定取舍。功能范围授权、AI 走查、组件复用、构建或测试通过不能推定用户已认可后来生成的 UI。恢复已确认设计、落实用户明确指定的调整，应沿用真实有效依据，不增加重复审批。

本轮是插件协议与方法维护，不建设业务界面，不逐项判定未提供原记录的历史案例，也不为每个 CSS 数值增加人工审批。

## 二、当前整体思路

现有执行协议把 UI 确认包含在业务确认与重要取舍中，变更闸门侧重行为/契约；视觉职责强调实际渲染，自主实施又允许授权内连续调整，因此纯呈现方案可能漏掉用户决定。当前状态核验器仅检查已声明依赖，无法从文件差异判断有无 UI 改动。

权威规则集中在执行协议“UI 方案展示与用户确认”新节。总纲、路由和 Skill 入口引用它；主 Agent 负责范围判断、展示、真实答复及正式实现入口核对，产品/视觉形成候选，研发承接已确认方案，独立 Review 核对来源及偏离。专业规格、Progress 和计划各自记录其已有职责内的必要依据，不新增平行确认台账。

核验继续采用 schema 1 的 confirmation、inputs、coverage、after：UI 方案确认纳入实施前依赖并绑定所展示的有效版本；同次答复明确包含授权时可合并。补充模板、状态协议和人工漏项核对，不改算法或宣称自动阻断全部 UI 改动。单纯增加可省略的布尔字段也不能识别漏报，暂不扩展 schema；未来若需要强制机器检查，应另行设计必填范围分类和迁移策略。

## 三、核心业务流程

### 3.1 判断本轮 UI 变化

| 情形 | 依据与下一动作 |
| --- | --- |
| 新增或改变 UI 方案 | 包括布局、层级、导航、入口位置、组件形式、文案含义、状态呈现、响应和视觉风格；即使功能或接口不变，也展示受影响候选并取得确认 |
| 恢复有效已确认设计 | 指明设计版本、用户来源及本次偏差；恢复不引入新取舍时复用确认及有效实施授权 |
| 用户明确指定的调整 | 明确目标和范围的直接指令可作为设计决定及相应实施授权；有必要时展示前后差异帮助核对，不强制再问同一句；未指定的新增取舍仍单独处理 |
| 已确认规范内的实现细节 | 按已确认 Tokens、组件规则落实，未产生新可见方案取舍时连续实施；不能以“只是样式”“现成组件”包揽新风格或新布局 |
| 无 UI 变化 | 在 Progress 写明依据，裁剪 UI 候选/确认，不创建空规格或原型 |

### 3.2 候选制作、展示与确认

设计阶段可在已确认流程和设计范围内制作隔离原型、Storybook 场景或受控候选，用于取得 UI 确认；不得把候选制作直接算作正式实现授权，也不先替换正式产品路径再追认。

向用户展示可访问的预览、已实际渲染的截图或受影响区域前后对比，按变化覆盖关键状态和目标设备；简单局部调整可复用现行页面，不强制新建工程。说明版本、影响、待决及模拟限制，仅给源码、文件路径或文字说“UI 已完成”不算展示。记录真实答复、所展示版本和覆盖；沉默、超时、AI 走查及功能范围“继续实现”不能替代后来才形成的 UI 决定。

用户已明确委托自主决定某范围 UI 时，引用其来源与边界并在范围内推进，不制造确认循环。该授权不能从一般实施要求推定。

### 3.3 正式实现与实施中变更

进入相关正式实现前核对：UI 分类与依据、有效候选展示/答复或明确复用/委托、其版本和覆盖，以及实施授权。已有授权只在仍覆盖时复用；新增未决部分保持待确认，其余已授权工作继续。

实现中改变已确认布局、形式、风格、关键状态或响应方案时，更新受影响候选并请求受影响决定；内部重构、恢复已确认设计及已确认规范内实现细节不重复审批。最终对当前页面与确认基线核对偏离，实际视觉检查与用户确认分别记录。

## 四、状态与记录模型

不新增数据库或状态 schema。Progress 保留本轮 UI 分类、有效版本、展示入口、用户来源及覆盖，复杂时引用现有规格决定区。视觉规格保留候选/确认基线、预览和必要状态；计划入口检查上述依据；独立 Review 检查漏项。

结构化状态使用现有 confirmation gate（建议 stage 为 `ui-design-confirmation`），绑定 UI artifact 实际版本，纳入对应 scope 的 `before_implementation` 或其依赖。恢复/明确指定/委托可引用真实原决定，无 UI 不造 gate。已有核验可发现已声明 gate 的 pending、覆盖不足、版本失效，但不能检查未声明 UI 分类、实际展示或答复真实性。

## 五、兼容性、风险与待决

- 拟在另一活动迭代完成 0.7.0 后升级 0.8.0：本轮明确扩大纯视觉方案的必须确认边界，按 0.x 流程收紧递增 minor；总纲升 0.34、执行协议升 0.18，与插件版本分开。
- 旧项目按真实有效确认/明确指令/委托复用，未知保留待确认，不追溯重写历史或重新索取仍有效授权。
- 共同文件和安装由主 Agent在实际基线核定后顺序处理，保留另一迭代已有内容。若对方尚在写入，先制作本轮局部候选/补丁，不并发改共享文件或安装。
- 不改安装脚本、状态算法、能力声明或用户全局指引；生成的两宿主职责入口通过现有生成器同步。

## 六、验证和交付方式

独立设计/计划及完整候选 Review 检查规则一致性、可执行性、过度确认与遗漏。代表场景覆盖新页面未确认、纯样式新风格、恢复基线、用户精确指令、实施中偏离、无 UI、授权内细节、隔离原型和明确自主委托；隔离执行观察实际请求确认及文件结果，证据留本机忽略目录。文字场景推演与真实执行分别记录。

运行宿主生成一致性和包资源检查、既有阶段核验回归及打包/角色测试，安装前新文件纳管；双清单版本、README、插件文档及生成入口一致。执行本仓库 `install`、`check`，记录源码与缓存指纹。Kimi 仅生成入口，原生安装/重载未执行则明确保留限制。

交付后将通用结论写回协议、职责与模板；设计/计划及本轮验证记录是实例资料，模型配置不进入通用规则。完成说明提供 Progress、版本、实际验证和发现刷新限制。
