# Dev Flow 流程调整实施计划

本计划把[新流程方案 0.3](../2026-10-21-flow-revision.md)落实到插件源码、模板、验证和安装。方案 0.3 是当前输入；[独立 Review](../../../reviews/2026-10-21-flow-revision-review.md)通过的对象是方案 0.2 和四篇 0.4 讨论模板，不能把旧结论扩写为对 0.3 或本计划的评审。源码候选、已安装版本与检查结论分别记录，当前事实从 Progress 和原始验收结果恢复。补充 Review 已独立核对本计划 0.2、Progress 及方案 0.3 的进度规则，结论与修订记录见同一 Review 文档；整体执行状态以 Progress 为准。

本轮阶段、执行者、派发、阻塞和下一步的唯一进度入口是 [Progress.md](Progress.md)，由主 Agent 维护。本计划只写任务、依赖与完成条件，不另记当前阶段。P1 的已完成事实与 P2 的实际状态均以 Progress 及原始成果为准。

## 输入基线与阶段总览

P1 已形成方案 0.2、四篇模板 0.4，并完成针对这些版本的独立 Review；方案随后增加整体目标与进度范围，成为当前 0.3 输入。P2 编写和评审本实施计划，实际进度见 Progress。

| 阶段 | 交付要点 |
| --- | --- |
| P1 方案与讨论模板 | 提供已评审的设计输入，并识别随后 0.3 的增量。 |
| P2 整体实施计划与 Review | 形成可执行拆解，独立核对依赖和完成条件。 |
| P3 共同协议改造 | 统一新阶段顺序、实施前置和完成规则。 |
| P4 专业职责与 Harness 执行 | 更新六职责方法、默认派发与交接。 |
| P5 正式模板与状态/工具适配 | 落地模板、唯一状态权威和新路径夹具。 |
| P6 完整候选 Review 与后置验收 | 集中审查、执行检查、修复与复验。 |
| P7 版本升级与安装核验 | 依据兼容影响定版、同步清单并核验安装。 |
| P8 运行验证与架构收尾 | 新会话发现、代表场景及长期资产交接。 |

依赖主线为 **P1 → P2 → P3/P4 → P5 → P6 → P7 → P8**。P3/P4 仅在同一输入版本和文件唯一写入者明确时并行。P6–P8 发现问题时回到受影响任务，形成新候选并重做失效的 Review 或验证。

## P2 整体实施计划与独立 Review

`P2-01` 由研发执行者编写本计划，核对方案 0.3、四篇讨论模板、仓库约定和现行代码入口。`P2-02` 由未参与本计划主笔的架构或研发执行者独立 Review 范围、依赖、文件边界、验证与交付；作者处理发现，评审者定向复核。完成证据是绑定本计划版本的 Review 结论及阻断项闭环，主 Agent 将结果写回 Progress。此项技术 Review 不增加人工审批。

## P3 共同协议改造

- `P3-01`：流程执行者修改 `skills/dev-flow/SKILL.md` 及 `skills/dev-flow/references/constitution.md`、`task-routing.md`、`execution-contract.md`。实施前确认受影响业务规则、关键边界、可观察结果、重要体验取舍及具体授权；完整正式 TC 的维护、Review 和执行移到完整实现之后，研发自测与必要回归继续随实现进行。
- `P3-02`：同步 `design-document-contract.md`、`stage-state.md` 和实际受影响的收尾/工程协议。明确四篇文档关系、权威来源、候选失效、变更闸门及验收/交付完成条件。

**依赖与评审：** P2 Review 通过后开始。独立验收和架构执行者对照方案 0.3、现行协议与源码差异交叉 Review；写入仍由指定作者负责。

**完成条件：** 所有入口使用同一阶段顺序，旧的“完整 TC Review/人工确认后才能实施”门槛已消除，但设计层预期确认未丢失；裁剪、确认覆盖、候选与交付规则一致。保留逐文件差异、引用检查、发现处理和定向复核证据。

## P4 专业职责与 Harness 执行

- `P4-01`：产品、视觉、架构、研发、验收、运维执行者分别修订各自 `skills/dev-*/SKILL.md` 与必要 references。设计期产品/UI 接收真实代码和成本反馈；研发主笔统一设计及独立计划；架构审设计和完整实现并做技术收尾；验收在实现后维护、Review、执行正式用例；运维核验实际交付。
- `P4-02`：Harness 执行者修订 `skills/dev-flow/references/subagent-guidance.md`、`codex-agent-configuration.md` 和确实受影响的宿主入口源说明。写清领域任务默认派发、窄上下文任务包、作者与独立评审分离、唯一写入者、共享资源、主会话等待与跨会话恢复。派发遵循当次用户和宿主模型约束，不固化模型或假设存在 Todo 工具。

**依赖与评审：** 与 P3 使用方案 0.3，可按互不冲突的文件边界并行；共同定义由主 Agent 先裁决。未参与对应文件主笔的领域执行者核对原始要求、专业 Skill 和完整差异。

**完成条件：** 六职责与总纲交接闭合，具体 Review 有对象版本、执行者和独立性；原生派发、主 Agent 自查及尚未实测的能力分别记录，不把入口存在当成派发验证。

## P5 正式模板与状态/工具适配

- `P5-01`：文档执行者将四篇讨论模板按实际用途落到相应 `skills/*/assets/templates/`，更新受影响的索引和链接；增加按需使用的 Progress 模板或示例，不强制短任务创建完整文档组。
- `P5-02`：状态执行者确定每个业务场景的**一个**结构化状态权威。索引若持有 `dev-flow-state`，Progress 只作导航；若 Progress 持有状态，索引只引用它，核验器读取实际权威路径。主设计与实施计划只引用或投影总体进度。
- `P5-03`：研发与验收执行者调整 `skills/dev-flow/scripts/check_iteration.py` 的必要行为、状态示例和 `tests/test_iteration_checks.py` 夹具；覆盖新标准路径、基线内修复、输入/候选失效、验收或交付缺项及选定权威路径。脚本仍只核验声明记录，不能代替语义 Review 或真实操作。

**依赖与评审：** P3/P4 的共同约定集成后开始。独立评审对照模板、状态说明、脚本和夹具，检查双写、遗漏前置及失效场景。

**完成条件与命令：** 正式模板与链接指向实际文件，结构化状态只有一个维护位置；`python3 -m unittest discover -s tests -p test_iteration_checks.py -v` 通过，新增夹具和 Review 结论可查。

## P6 完整候选 Review 与后置验收

- `P6-01`：主 Agent 将 P3–P5 集成为可追溯完整候选。未参与相关主笔的架构、产品及验收执行者对照方案 0.3、原要求和全部实际差异做集中 Review；不以各文件自查拼成完整结论。
- `P6-02`：验收执行者基于有效方案与完整候选维护本轮正式验收检查，先由独立上下文 Review 覆盖与可执行性，再运行适用的工具、模板样例、文档链接及端到端检查。运维核对实际交付入口。
- `P6-03`：研发按关联问题修复，原评审者或独立验收者定向复评/复验；每次候选变化先判断旧证据的有效范围，未执行、失败和跳过保持真实状态。

**依赖与完成条件：** P3–P5 已集成。完整差异 Review 与必需验收检查绑定同一当前候选，阻断项关闭；工具契约、独立行为、新会话发现及真实项目证据分开登记。运行 P5 的核验器测试和受影响组件的实际检查。若安装脚本有改动，再运行 `python3 -m unittest discover -s tests -p 'test_plugin_installation.py'`，检查隔离打包、缓存/来源和用户配置保留。

## P7 版本升级与安装核验

- `P7-01`：主 Agent 对最终候选复核兼容影响，冻结正式发布版本；为完整候选 Review 可提前预置候选版本号，该动作不代表安装或 P7 完成。本轮替换实施前置可能属于 0.x 不兼容变化，届时递增 minor 并说明旧项目迁移；当前不预定发布版本。同步 `plugin.json`、`.codex-plugin/plugin.json`、总纲协议版本及实际受影响的 `README.md`、`docs/plugin.md` 说明。
- `P7-02`：新文件先纳入 Git 管理；版本执行者运行 `python3 scripts/sync_host_agents.py --write`，再运行 `python3 scripts/sync_host_agents.py --check`，核对生成的 Kimi 清单与职责入口。
- `P7-03`：在同一源码候选上运行 `python3 scripts/manage_plugin.py install` 和 `python3 scripts/manage_plugin.py check`；独立运维或架构执行者核对启用状态、八个 Skills、包/缓存位置及源码指纹。

**依赖与完成条件：** P6 的完整候选 Review 与必需检查通过。版本取舍、生成检查、安装/check 输出和源码候选一致。安装后改包内文件须重新验证、构建、安装；不得以同一版本缓存交付不同内容。Kimi 按 `docs/plugin.md` 的原生安装/重载流程独立处理，Codex check 不等于 Kimi 已更新。

## P8 新会话验证与架构收尾

- `P8-01`：在新会话核验当前已启用的 Skill 与实际 Harness 派发能力，必要时重启宿主；记录版本、入口、派发结果及失败原因。安装检查不替代这项验证。
- `P8-02`：领域执行者在隔离代表场景验证设计期技术反馈、独立 Review、实现后用例/验收、基线内修复、候选失效、Progress 恢复和主会话持续运行。以 `evals/dev-flow-stages/README.md` 为评测入口；给执行者任务、项目资产和 Skill，不给预期答案。真实业务项目若可用则另行验证并记录，未执行时明确留为缺口。
- `P8-03`：架构执行者依据当前源码、完整 Review、测试和安装/发现结果做技术收尾，更新能力现状与长期资产，记录遗留；主 Agent 汇总最终交接并更新 Progress 和项目入口。

**依赖与完成条件：** P7 安装完成后核验新会话；代表场景针对实际发现的能力运行。分别保留工具契约、原生派发、独立行为、新会话发现、真实项目的结果及边界，不互相折算。交接说明版本、源码/缓存、实际检查、未执行项和后续承接；约定必需项未通过时整体进度保持未完成。

## 协作与验证边界

主 Agent 保持范围、依赖、唯一写入者、集成与完成判断。专业任务优先使用实际可用的 Harness 原生 subagent；任务包包含原始目标、专业 Skill 绝对路径、有效输入版本、候选、问题、读写边界、成果位置和停止条件。评审者从原始输入与完整候选核对，不凭作者摘要宣布独立通过。当前任务派发遵循用户指定的 `gpt-6-luna / max` 或 `gpt-6-sol / medium`，实际选择只记入本次运行事实。

首次正式实现授权、业务预期确认、推送/PR/合并和发布各自依已有有效授权与宿主限制处理；技术计划与 AI Review 不新增人工审批。`sync_host_agents.py --check` 验证生成入口，`manage_plugin.py check` 验证 Codex 安装，核验器单测验证声明契约；三者都不能证明新会话运行、专业行为或真实项目交付。
