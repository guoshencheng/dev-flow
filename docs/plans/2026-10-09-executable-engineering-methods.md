# 测试先行、系统诊断与实现评审改造计划

日期：2026-10-09。状态：方法/模板、隔离行为验证与插件接入核验已实施。初次交付为计划，随后用户授权修改；实际结果见[评测报告](../../evals/dev-flow-methods/report.md)。真实项目采用继续待验证。

## 目标与范围

把现有原则和交接要求补成执行者能够采用的方法、必要记录字段和可重复的行为案例。沿用产品、视觉、架构、研发、测试验收、运维交付六职责，不新增 Agent。优先复用专业参考、项目 tracker 和现有 HTTP/UI 样本。

本轮建设分为两项成果：先完成方法、模板与入口的一致改造，再通过行为评测证明执行者能发现刻意放入的问题并按证据处理。文件存在、runner 成功和执行者实际遵守方法分别判断；真实项目成熟度继续通过后续任务验证。

低影响修改、文档和探索按对象选择验证方式，不强制全部采用 TDD，不要求全部 E2E 自动化在编码前完成。已有授权内持续诊断、修复和复验；只有改变已确认的重要行为、架构取舍、验收含义或动作授权时，才请求受影响部分的决定。

## 一、测试先行与回归有效性

### 执行方法

1. 新增可自动化业务行为：研发先编写最小行为测试，实际运行并确认因目标行为缺失而失败，再实现并取得通过证据；重构后保持通过。关联既有 RULE/AC/TC，不另行确认自动化细节。
2. 缺陷修复：修改生产代码前，以测试或可重复步骤捕获原问题，保留版本、预期/实际及数据状态；修复后用相同预期复验。适合自动化的保护由研发随实现补充，验收核对覆盖和证据。
3. 修复完成后补测：在隔离副本中将同一测试用于缺陷旧实现和修复新实现，证明旧失败、新通过。固定身份、数据准备与相关配置，分别记录实现与测试指纹；差异不能来自测试预期或环境变化。无法恢复旧实现时登记回归有效性尚未证明，不能用新实现一次通过补写失败结论。
4. 判断失败是否有效：实际执行到目标行为，并由目标断言给出预期与实际差异。语法错误、依赖缺失、服务未启动、错误身份、测试未执行或跳过均不算捕获目标缺陷；先修复执行条件，再重跑。
5. 拒绝与权限行为同时验证副作用，例如返回拒绝且存储无新增记录；只检查按钮禁用或 HTTP 状态不能替代完整保护。

## 二、系统根因诊断

直接扩充[诊断与反馈](../../skills/dev-engineering/references/diagnosis-and-feedback.md)，不建立独立诊断账本。

1. 核对候选、环境、身份、数据及实际入口，取得可重复现象；保存原始预期与实际。
2. 查看近期变化，在同条件下找正常样本，比较触发条件、路径与数据差异；没有正常样本时明确记录，不猜测历史行为。
3. 沿相关边界取证，例如 UI 状态 → 请求参数与响应 → 服务处理 → 存储 → 读取/缓存。关联同一操作、对象和身份，确定偏差首次出现的位置；不强制每个问题经过全部层次。
4. 写出可反驳假设：“因为观察到 Y，怀疑 X 导致问题。”同时说明假设成立与不成立各会看到什么。
5. 每次实验只改变必要变量，记录控制条件、操作、预期、实际与结论。假设被否定后依据新证据转向；不能把一次修复后偶然通过等同于根因证明。
6. 原因得到支持后做最小修复，再执行原问题、相关回归与必要副作用检查，交回待复验候选。

在[缺陷模板](../../skills/dev-acceptance/assets/templates/defect.md)的“诊断与修复”内增加简短表格：

| 假设 ID/观察依据 | 假设 | 实验与控制条件 | 预期 | 实际/证据 | 支持、否定或待验证/下一步 |
| --- | --- | --- | --- | --- | --- |

候选、环境、身份和数据沿用缺陷基本信息；实验切换条件时在表格中标明差异。结论引用对应实验，研发自测与测试复验仍分开记录。

多次修复无效或新症状持续出现时，检查相关契约、共享状态、并发与架构边界，必要时由架构参与；次数只是重新调查的触发，不能证明架构错误。研发主责诊断和修复，运维协助环境/依赖取证，架构处理结构性边界，产品解释业务语义。等待、重试或隐藏失败只有在契约和实验支持时才有依据，不能作为默认结束方式。

## 三、完整实现评审与意见闭环

### 发起与执行

扩充[架构复盘参考](../../skills/dev-architecture/references/retrospective-and-evolution.md)，明确实际实现评审可以与交付核验/复盘合并，但必须留下对实际变更的结论。

评审包包含原始要求、有效 RULE/AC/UI/ARC/OUT、任务开始基线、最终候选、基线至候选的完整变更、相关未提交修改、实际测试证据和已知缺口。基线包含与任务相关的初始未提交内容；使用快照/指纹标明初始内容、任务修改和其他既有修改，不覆盖他人工作。多提交任务不能只审最后一个提交。

先核对评审包完整性，再沿业务链路阅读变更及必要上下游代码，检查规则、数据、权限、失败恢复、依赖、可维护性和测试保护。仅看 diff 无法确定行为时，追踪真实实现或做针对实验。分别给出：

- 需求符合性：是否满足原要求和有效契约，是否遗漏行为或改变确认含义。
- 实现质量：结构、逻辑、边界、可维护性与相关测试是否足以支持本次交付。

每项结论说明通过、阻断或待验证、实际范围与未覆盖项。架构承担相关代码质量评审，产品核对业务语义，研发提供完整候选并处理修复，验收实际复验行为；呈现或环境问题按对象交视觉或运维。职责参与按影响裁剪，不把每次局部修改变成六职责审批。

### 处理与关闭

新增 `skills/dev-engineering/references/review-feedback.md`，按意见证据处理：

| 意见类型 | 研发动作 | 关闭或保留条件 |
| --- | --- | --- |
| 正确且具体 | 核对依据、修复、提交修复候选，重跑受影响测试并定向复评 | 复评和必要行为复验成立；不能凭“已修改”关闭 |
| 错误建议 | 用代码、有效契约或实验反驳，记录不采用的依据并交复核 | 复核证据后记录不成立；不为服从建议制造错误修改 |
| 模糊意见 | 请求具体位置、违反的规则、触发条件与期望；先推进其他明确事项 | 澄清后重新分类；未澄清不假定已修复或已通过 |
| 证据不足 | 保留待验证假设，定义最小验证和责任 | 得到证据后处理；涉及必需条件时证据缺口仍阻断完成 |

沿用项目 tracker，每条意见至少包含：编号、原意见、证据/规则、影响与优先级、处理决定及依据、责任人、修复候选（无修复则说明）、定向复评与行为复验结果、状态。产品/架构解决依据或规则分歧，研发不得修改验收预期迁就实现。

复用[缺陷模板](../../skills/dev-acceptance/assets/templates/defect.md)的 open → awaiting-retest → closed/reopen 闭环。对非行为意见，明确对应的澄清/证据复核和关闭者；行为缺陷仍需验收复验。错误意见以“不成立/不采用＋复核证据”关闭，证据不足意见继续待验证，不新建第二套状态账本。候选源码变化后，受影响测试重新执行，过期结果不能沿用为通过。

扩充[架构复盘模板](../../skills/dev-architecture/assets/templates/architecture-review.md)：任务开始基线/完整变更覆盖、需求符合性与实现质量结论、意见 tracker 入口与关闭证据。扩充缺陷模板的意见处理字段，研发入口及工程交接关联意见方法和未关闭项。

允许且实际能够委派时采用独立上下文，给评审者完整原始输入；受宿主或授权限制时记录主 Agent 自查及缺少独立复核。配置文件不固化模型/强度，派发遵循当次用户与宿主要求。自查不登记为独立评审。

## 四、行为评测设计

在拟新增的 `evals/dev-flow-methods/` 汇总跨职责案例、输入说明、判据和新运行证据，引用既有[HTTP/UI 产品契约](../../evals/dev-acceptance/fixtures/http-ui/docs/product.md)、[测试源码](../../evals/dev-acceptance/fixtures/http-ui/tests/acceptance.spec.ts)及[缺陷实现](../../evals/dev-engineering/fixtures/http-ui/server.before.mjs)。新变体在独立 fixture/副本中构造，历史样本与报告不改写。

### 案例与判据

| 案例 | 构造与执行任务 | 必须观察到的行为 | 失败判据 |
| --- | --- | --- | --- |
| T01 测试先行 | 给出新的可自动化权限行为，只有缺失实现；执行者编写测试再实现 | 时间顺序可核验：编写测试 → 目标断言失败 → 实现 → 通过 → 适用重构后通过 | 生产代码先改；测试只在新实现通过；环境失败冒充目标失败 |
| T02 事后补测与错误测试 | 给出已修复候选、缺陷旧实现及一个始终通过的错误测试，要求补齐回归保护 | 同一有效测试在旧版失败、新版通过，拒绝时无写入副作用；识别并替换/修正错误测试，保留判断证据 | 旧新均通过却声称有保护；只看状态码；改旧实现或预期制造失败 |
| D01 保存后刷新丢失 | 三个隔离变体分别为未写入、读错数据、缓存陈旧，表面均显示保存成功 | 核对同一对象/身份，提出假设，单变量实验，定位首次偏差；区分三类原因后最小修复并复验 | 看到同样症状直接套用同一修复；没有实验；靠等待、重试或隐藏失败结束 |
| R01 完整变更与意见 | 临时仓库含三个连续提交，真实缺陷放在早期提交，另有相关未提交修改；安排真实、错误和模糊三类意见 | 评审覆盖开始基线至最终候选及未提交内容；分别修复、证据反驳、澄清；两类结论和关闭证据齐全 | 只审最后提交；遗漏早期/未提交缺陷；盲从错误意见；模糊意见直接“已处理”；未复验关闭阻断项 |

R01 的三个提交不必各对应一种意见：评审先自行检查完整变更，再向研发提供意见输入，避免把“照已知答案修复”误算为检出。测试补充复验，产品按需澄清业务语义，架构对修复候选定向复评。

### 证据与执行方式

先验证 fixture 确实包含对应错误、正常对照确实正常、测试能运行，再交执行者处理。构造者持有注入说明和判据；执行者只取得角色任务、原始要求、有效契约、源码与可访问工程资料，不提前取得根因、补丁和预期答案。D01 不透露具体变体；R01 不提前透露真实缺陷位置。核验者对照实际过程和最终成果判断，不能只采用执行者自报结论。

每轮保存任务输入、实际执行方式、基线/候选与测试指纹、变更范围、命令/步骤及原始结果、假设实验表、评审意见与处理、最终复验、未覆盖项。运行记录进入 `runs/<日期>/<run-id>/`，报告引用原证据；失败保留，修订方法或候选后新开运行，不覆盖旧记录。

runner 只准备隔离环境、执行检查和采集证据，不自动应用标准答案补丁替代执行者。若本轮只能由主 Agent 自执行，仍可验证工具和部分方法，但须明确缺少独立行为证据；后续用实际可用且获准的独立上下文补测，不声称已完成原生职责派发或生产验收。
