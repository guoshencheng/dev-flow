# 文档审阅与呈现检查效率优化设计

版本 1；原始要求是降低文档自查/Review 中例行 Computer Use 的成本，用户明确要求按已展示方向优化。总体进度见 [Progress](../Progress.md)，复核见 [Review](review.md)，执行见 [实施计划](implementation-plan.md)。

当前结果：规则源码及两端职责入口已实现，C2 独立 Review 和适用验证通过；首阶段仅交源码。用户现已授权接续 0.7.1 版本与本机安装，当前实际结果见 Progress，不改变已通过的规则设计。

## 一、本次要完成什么

文档内容审阅默认直接读取源文档、差异、对应模板及必要代码。按本次变化和检查目标决定是否需要呈现或交互观察，再选择足以回答问题的工具。已有真实视觉/交互检查要求保留；不通过减少工具调用把未检查项目登记为通过。

## 二、当前整体思路

当前文档预览参考已规定普通文字修订不逐篇打开浏览器，但架构/研发职责直接要求“核对实际渲染”，图示规范及模板也缺少明确的证据复用入口；文档管理交接无条件列“真实 Web URL”，容易让阅读入口变成自查前置。

在文档管理 Skill 中给出默认原则，在其现有预览参考中维护检查选择的具体方法；公共约束给最短原则及引用，架构/研发职责将语义检查与必要呈现检查分开。图示规范和调用模板引用该方法，视觉职责的文档模板核对不再被解读为例行启动浏览器。

这是现有指令调用关系的局部调整，无系统模块/部署/数据链路变化，沿用当前 Skill → 参考及职责 → 模板结构；不新增技术图或工具，避免为解释无需渲染的规则新增渲染任务。

## 三、核心业务流程

1. 从任务和差异定位检查对象。规则、逻辑、模板、引用和图文/源码一致性直接读源内容；可本地解析的资源路径与引用直接核对。
2. 新增或改变图示、复杂排版、渲染方式/资源加载，或存在显示缺陷/用户明确要求时，针对受影响对象实际观察呈现。用户明确限定文本 Review 时按范围执行，必要视觉结论保留未覆盖；交互原型和阅读器行为仍要实际操作。
3. 图与相关渲染条件未变，且已有可定位、仍有效的同版本呈现证据时复用；仅有图文件或历史截图但缺少有效范围，不推定已通过。首次交付但没有有效呈现检查的图示仍需观察。
4. 按问题选择工具：用户明确指定浏览器、Computer Use 或文本检查范围时优先遵循。其余任务中，内容读源文件；路径/链接用本地或 URL 工具；静态视觉问题可用目标渲染器导出或浏览器自动化截图并实际查看。涉及嵌入宽度、字体、资源或目标阅读器兼容时使用对应环境，呈现证据需关联同一对象版本及适用的阅读器条件。只在已有工具无法充分观察或必须操作实际 GUI 时使用 Computer Use，不把它设为必经步骤。
5. 提供用户阅读入口与 Agent 自查分开：项目设计交付沿用现行阅读入口约定，核验 URL 不等于必须在浏览器逐篇查看；本轮纯方法维护用源文件链接。未受影响内容不因作者/评审者不同而自动重复渲染。

## 四、数据库与数据模型设计

不涉及数据库、状态 schema、能力清单或安装算法。复用已有 Review 字段记录对象版本、检查范围、实际方式、证据来源与未覆盖，不新增强制表单或逐次证明文档。

## 五、兼容性/风险/待决事项

- 这是兼容方法维护：降低无收益的重复操作，保留语义 Review 和必要呈现/交互检查。总纲与文档协议版本不因操作方法澄清而改变。
- 避免以“直接读源”为由跳过新图视觉检查，也避免将导出图片通过当作目标阅读器嵌入已通过。
- 工作区已有其他迭代的暂存候选；本轮仅覆盖明确 hunk。生成入口由脚本按当前源生成，候选指纹变化时重核受影响范围。版本/安装不得覆盖其他迭代的候选或交付同版不同内容。

## 六、验证和交付方式

先独立复核本设计与计划，实施后对明确差异做独立 Review。用普通文字修改、只改图外文字、新图/长标签、渲染条件变化、仅提供链接、用户限定文本检查、用户要求浏览器及交互原型等代表任务验证检查选择；将合理工具决策与真实 GUI 执行区分。

复用 `sync_host_agents.py --write/--check` 及现有原生入口/隔离打包测试检查链接和资源。未改 UI 或阅读器，不启动 Web 服务，也不执行 Computer Use。具体源码/版本与安装状态在 Progress 据实记录；不推送或合并远端，不执行 Kimi 原生安装。
