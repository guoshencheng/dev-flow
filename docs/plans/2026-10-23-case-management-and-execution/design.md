# 测试用例文档维护方案

用例和执行情况分开维护，存放与提交边界如下：

| 内容 | 建议位置 | 是否提交 Git |
| --- | --- | --- |
| 用例文档：名称、操作路径、预期结果 | `docs/dev-flow/acceptance/cases.md` | 提交，长期维护，全量和增量共用 |
| 本轮执行表：是否通过、实际结果、备注 | `.dev/runs/<本轮>/acceptance/result.md` | 不提交，保留在本地 |
| 截图、录屏、日志等执行证明 | 与本轮执行表同目录或其附件目录 | 不提交，保留在本地，可缺省 |

以上为建议路径，不要求为本方案建立实际项目用例或执行记录。AI 和人都可直接读写相应 Markdown 文档。

## 一、用例文档（提交 Git）

按功能分组列出用例。每条写清名称、操作路径和预期结果；需要特定身份或数据时，在操作前补一句前提即可。保留简单编号，方便本地执行表引用。用例文档只维护测试内容，不填写某一轮是否通过或执行证明。

以下只是格式示例，没有执行这些测试：

### 偏好设置

- **TC-001 保存后刷新仍然保留**
  - 操作路径：登录 → 打开设置 → 修改显示名称为“小明” → 保存 → 刷新页面。
  - 预期结果：显示保存成功，刷新后显示名称仍是“小明”。
- **TC-002 空名称不能保存**
  - 操作路径：打开设置 → 清空显示名称 → 点击保存。
  - 预期结果：提示名称不能为空，原来的名称没有被修改。
- **TC-003 人工检查提示是否清楚**
  - 操作路径：打开设置 → 修改名称并保存 → 查看成功提示。
  - 预期结果：提示清楚可见，使用者能理解已经保存成功。

### 全量与增量怎么维护

- 全量：执行文档中全部有效用例。
- 增量：仍维护同一份列表，新增场景就追加，行为改变就修改原用例；本轮执行新增、修改及相关回归用例。
- 本轮选哪些用例，在执行表上方写明编号即可；需要时在列表里临时标注“本轮新增/修改”。
- 不再适用的用例注明“已停用”和原因；全量时不执行已停用项。

## 二、执行情况（单独保存，不提交 Git）

每轮在本地新建一份执行记录文档，用表格引用用例文档中的编号和名称，上方写明日期和本轮范围。先列出本轮要执行的用例，默认标为“未执行”；每完成一条就更新对应行，中断后继续剩余行。旧轮次留在各自本地记录中，避免把上次通过当作本次执行。执行表和附件都不写回用例文档，也不纳入提交。

**本次执行：** 日期填写实际日期；范围填写“全量”或“增量：TC-xxx、TC-yyy”。

| 用例 | 是否通过 | 实际结果／备注 | 截图或其他证明（可选） |
| --- | --- | --- | --- |
| TC-001 保存后刷新仍然保留 | 未执行 | — | — |
| TC-002 空名称不能保存 | 未执行 | — | — |
| TC-003 人工检查提示是否清楚 | 待人工验证 | — | — |

填写方式：

- 是否通过：填写“通过 / 不通过 / 未执行 / 待人工验证”，避免用空白或“否”混淆失败和未执行。
- 实际结果／备注：简单写实际看到了什么；失败写清哪里与预期不同，无法执行写清原因。
- 证明：截图、录屏、日志、接口返回或生成文件都可以，有就附链接，没有可以写“无”。**证明可选，没有附件也可以根据实际观察填写通过或不通过。**
- 人工验证：直接按用例文档操作，填写本轮本地执行表；AI 无法完成的人工项先留“待人工验证”，收到人的明确结果后再填写。
- 复验：重新执行原路径，在备注保留原问题和复验情况；后续轮次使用新的执行表。

执行结束时，对照本轮选中的编号逐条看表，检查有没有漏行、未执行或待人工验证。结果如实写明；没有实际执行的用例不标通过。

## 三、与 Dev Flow 怎么衔接

- 测试验收职责维护可提交的用例文档；每次执行另建本地记录，已有自动化或浏览器工具的结果也回填到本地表中。
- 正式用例的维护时点沿用 Dev Flow；本方案只简化文档表达和执行记录。
- Progress 保留流程进度和用例文档入口；执行表、逐项结果和截图等附件留在本地，不复制到可提交的用例或其他文档中。
- 执行记录统一放入被 Git 忽略的 `.dev/`；项目已有其他本地运行目录时沿用，并确保执行表及附件都被忽略。

本轮只修订设计文档。当前设计来源与核对记录见 [Progress](Progress.md) 和 [调整记录](review.md)；先前工具方案保留为[历史设计](archive/design-v4.md)。
